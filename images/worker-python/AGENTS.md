# images/worker-python

## Purpose

The worker image of stage `direct` for AgentCore: `agentd`, the promoted Cline fork,
OpenCode 1.18.32 (not in the direct family), the Python tool set of `images/tools`, the python 3.12
toolchain and the language tool set (Node 24 and the pinned JS tools; Go, the JDK, Maven and the slim Rust set with the C toolchain it links through
for `LANG_FAMILY=direct`) on Amazon Linux 2023 (arm64).

## Ownership

Owned by `images/AGENTS.md`. Built only by `images/codebuild/worker-python.yml`.

## Local Contracts

- Base image pinned by digest; every binary the build spec stages (agentd, cline, opencode,
  gitleaks, uv, rg) is checked against its SHA-256 build argument inside the image, and
  the pins are recorded in `/opt/harness/pins.json` and image labels.
- Everything under `/opt/harness` is root-owned and not
  writable by group or other. Binaries arrive
  through `COPY --chmod=0755` and the build inputs through bind mounts, so no layer holds a second
  copy.
- The engine's PATH (`AGENTD_ENGINE_PATH`) holds `/opt/harness/gate-tools/lang/bin` (node, npm,
  pnpm).
- The small shell tools a repository's own check script reaches for: `diffutils`, `patch` and `jq` are in the Dockerfile's package list for every family (under 2 MB together), and `pip` and `pip3` at `/usr/local/bin` are
  copies of the wrapper `images/worker-python/pip`, which runs `/usr/bin/python3.12 -m pip` (python3.12-pip ships the module and no command). A session without them printed `missing diff`, `missing patch`, `missing jq`
  and `missing pip` for `command -v`.
- The goal plugin bundle, the harness's observer plugin and their lock are copied to `/opt/harness/engine/plugins/`: about 16 KB, no `node_modules`, the cap untouched. The goal folder is not in
  the repository: the build spec runs `scripts/engine-fetch build goal-plugin --platform linux-arm64` and `verify` into the `build` directory of the checkout before `docker build` (the pinned esbuild binary, no package manager; every file must equal
  `engine/plugins/lock.json`), and the Dockerfile copies the goal folder from there. After the build the spec runs the 14 checks of the goal plugin's state machine and the observer's checks against the shipped files, with the image's own Node.
  agentd checks the files against `lock.json` and places them under the engine's read-only configuration directory at the start of a run.
- Licences: the image carries `LICENSE` and `NOTICE` of the repository and the Apache-2.0 text of Cline (the LICENSE the goal plugin fetch brings, the same text for the fork binary and the plugin) under `/opt/harness/licenses/`
  (read-only). A change of either root file changes the image key (`scripts/lib/digests.py`).
- Users: `harness` (uid 900) and `agent` (uid 901); the engine runs as `agent`.
- Size gate: the platform counts the compressed bytes of the image's layers in ECR (about 2,048 MB), not the unpacked size. The build spec fails the image above 1,800
  MB compressed (1 MB = 1,000,000 bytes; read back from ECR with `ecr:DescribeImages` after the push, so base-image drift cannot cross the platform's limit unseen) and
  above 3,200 MiB unpacked (a loose ceiling that keeps growth visible; checked before the push, so a far larger image is never pushed). `image-size-gate.sh
  <unpacked|compressed> <bytes> <ceiling>` makes both checks and prints `IMAGE-GATE PASS|FAIL <kind> ...`; a size it cannot read fails. Tags are immutable: an image
  that fails the compressed gate stays in ECR under its tag, and `image.json` is not written. `scripts/lib/deploy.py` reuses a tag it finds without reading its size,
  so after a failed gate change an image input (which moves the key) before deploying again.
- Entry point `agentd serve` on 0.0.0.0:8080 (AgentCore Runtime contract).
- The native services of `images/services/install.sh` (PostgreSQL 16, MariaDB 11.4,
  Valkey 9, mailpit), uid `svc` 904 and `/var/lib/harness-services` (0711), installed after the
  package installs; `pins.json` records the services manifest's SHA-256. Only PostgreSQL is started in a session (`ham-services`);
  MariaDB, Valkey and mailpit are a trim candidate (`images/services/AGENTS.md`).
- Direct family: the Dockerfile takes `LANG_FAMILY`, the build argument, with default `python`; `scripts/deploy.sh` passes `LANG_FAMILY=direct`; `harness.family`, the family label, follows the argument. With `LANG_FAMILY=direct`, `tools/lang/install.sh /opt/harness/gate-tools/lang direct` installs the python family's Node 24 and JS tools, Go 1.27.1 (`go`, `gofmt`), Amazon Corretto 21.0.12.12.1 (`java`, `javac`, `jar`), Maven 3.9.16 (`mvn`) and the slim Rust set (the Rust bullet below), each using its arm64 SHA-256 in `lang.lock`; it leaves out golangci-lint, gosec, Gradle, JaCoCo,
  SpotBugs, FindSecBugs, google-java-format, ktfmt, llvm-tools and cargo-llvm-cov because nothing in this line runs them. One image serves the thin line because it receives one prompt and cannot choose a language before the session starts; the samples `web` (TypeScript and Python), `events` (Go), and `enterprise` (Java 21, Maven) all run in that worker. The direct family image measured 1,780 MiB unpacked before Rust, with the container runtime in and OpenCode out (1,798 MiB before that change), with RabbitMQ and its helper (1,729 MiB without), measured with `docker image inspect` in
  CodeBuild ARM for one build, against 1,313 MiB for the python family image that stage `direct` built first; the increase over the python image was +485 MiB: Go 215, JDK 214, Maven 11 and Erlang with RabbitMQ 69, unpacked sizes by `du` less shared layers. Its ECR compressed size was 699,273,205 bytes against 450,979,685 for the python image. The Rust set and the C toolchain add an estimate of about 745 MiB unpacked (the Rust prefix is 611,764,777 bytes and cargo-nextest 26,979,328 bytes on x86_64, about 546 MiB together once each component is scaled to aarch64 by the ratio of its
  pinned archive; gcc with its 32 dependencies is 199 MiB by the Amazon Linux 2023 aarch64 repository metadata) and about 260 MB compressed: about 2,525 MiB and 960 MB for the image. The first CodeBuild ARM build records the real numbers; the size gate above holds them. `AGENTD_ENGINE_PATH`, the engine's PATH, orders `/opt/harness/bin`, `/opt/harness/gate-tools/lang/bin`, `/usr/local/bin`, `/opt/harness/gate-tools/bin`, `/usr/bin`, `/bin`; the fourth entry adds uv, ruff, mypy, bandit, pip-audit, diff-cover, and gitleaks; placing it after `/usr/local/bin` keeps python3 at 3.12 with
  pytest, ahead of `/usr/bin` and its python3 3.9; Maven finds java and cargo finds rustc through PATH. The Dockerfile runs `go version`, `java -version`, `mvn -v` and the Rust tool versions in the built image with the lang bin on PATH; the build spec checks that `cc` and `ld` exist and that golangci-lint, Gradle, cargo-llvm-cov and llvm-tools do not.
- Rust and C toolchain: with `LANG_FAMILY=direct` the image runs a Rust repository's `cargo build`, `cargo test`, `cargo nextest run`, `cargo clippy` and `cargo fmt`. `tools/lang/install.sh` installs the slim Rust set under `/opt/harness/gate-tools/lang/rust` (rustc, cargo, rust-std, clippy and rustfmt of rust 1.98.1, the version of the repository's `rust-toolchain.toml`; cargo-nextest 0.9.146 in `/opt/harness/gate-tools/lang/bin`), each by its arm64 SHA-256 in `lang.lock`, and links `rustc`, `rustdoc`, `cargo`, `rustfmt`, `cargo-fmt`, `cargo-clippy` and `clippy-driver` into `/opt/harness/gate-tools/lang/bin`, which the engine's PATH holds. The real files stay in `/opt/harness/gate-tools/lang/rust/bin` because rustc finds its standard library relative to its own file. No rustup runs, and a repository's `rust-toolchain.toml` is ignored by the standalone cargo. llvm-tools (198 MiB on x86_64) and cargo-llvm-cov stay in the full `rust` family: no run measures coverage. rustc
  links through `cc`: the Dockerfile adds `gcc`, `binutils` (the linker `ld`) and `glibc-devel` (the C library's start files and headers) to its package list for the direct family only; the python family adds none. On Amazon Linux 2023 `gcc` also pulls `make` (with guile), `cpp`, `kernel-headers` and `amazon-rpm-config`: 33 packages, about 199 MiB installed, 60 MB as rpm files. The same gcc compiles the C of build scripts (the `cc` crate for aws-lc-sys) and, since Go enables cgo when it finds a C compiler, Go's cgo is no longer off. The build runs `rust-check.sh <image> <rust version>` before the push (the version is the aarch64 `rustc` row of `lang.lock`): a throwaway container as uid `agent` that checks the versions, that `rustc --print sysroot` through the link names the real prefix, `cc` and `ld`, then builds, runs, tests (`cargo test` and `cargo nextest run`), lints and format-checks a dependency-free crate with `cargo --offline` in about 10 seconds, so a missing
  linker, C library file or standard library fails the build, not a run. Crates reach the session through the package proxy (`crates/pkgproxy`); this directory only installs the toolchain.
- Broker and services helper: `images/worker-python/broker.lock`, the pinned download list, records SHA-256 hashes for the RabbitMQ team's Erlang/OTP 26.2.5.19 RPM for Amazon Linux 2023 (aarch64) and RabbitMQ 3.13.7 generic-unix tarball. The RPM hash matches the release digest; the tarball release provides only a GPG signature, so its hash was computed from the download; RabbitMQ 3.13 supports Erlang 26.0 to 26.2. For `LANG_FAMILY=direct` only,
  `images/worker-python/install-broker.sh`, the broker installer, runs from the Dockerfile with `images/tools/fetch.sh`; it downloads through `fetch_pinned`, checks hashes, installs the RPM through `dnf` with its libraries, uses the pinned base image's required `libcrypto OPENSSL_3.4.0`, unpacks RabbitMQ into `/opt/harness/services/rabbitmq`, and checks that `erl` reports OTP 26 and the tarball holds rabbit 3.13.7. Every image includes `/opt/harness/bin/ham-services`,
  the local services helper, from `images/worker-python/ham-services.sh` on the engine's PATH; sessions have no Docker, and the helper starts PostgreSQL and RabbitMQ for a project's tests. `ham-services postgres` starts PostgreSQL 16 on `127.0.0.1:5432`, using `initdb`, user `app`, trust authentication and database `app`. It opens no Unix-domain socket: the server gets `-c unix_socket_directories=` (an empty value). A socket path holds at most 107 bytes and the
  helper's directory in a session (`/var/lib/agentd/<run>/direct/report-<id>/tmp/ham-services/postgres`) is deeper than that, so a socket file there would be 128 bytes and the server would stop at once; clients name the host, as `DATABASE_URL` does (`psql -h 127.0.0.1`). A server that exits before its port opens is reported at once: the end of its log, then a last line `postgres exited right after it started (<its FATAL message>); see <log>`. `ham-services stop` sends
  PostgreSQL an interrupt (a fast shutdown; a terminate waits for every open connection) and waits up to 10 seconds for it to remove `postmaster.pid`. `ham-services rabbitmq` starts RabbitMQ on `127.0.0.1:5672` with node `rabbit@localhost`; its Erlang port mapper and distribution port also bind to `127.0.0.1`; user `app` gets a random per-run password from `/dev/urandom`, or `BROKER_PASSWORD` when set, stored in a `0600` file. `ham-services env` prints export lines
  for `DATABASE_URL`, `BROKER_PASSWORD` and `BROKER_URL`; `status` and `stop` report and stop services; the helper runs as the calling engine user, refuses root, and stores session-only data under `$TMPDIR/ham-services`, the engine's local temp directory; these values match the three sample prompts' Compose services: `postgres:16`, user `app`, database `app`, trust, `127.0.0.1:5432`; `rabbitmq:3.13`, user `app`, `127.0.0.1:5672`. Erlang and RabbitMQ add 69 MiB to the
  direct family image.

- Container runtime: the direct family image carries rootless Podman so a sample's Testcontainers tests run in the session (the first enterprise-sample run failed the clean room because the session had no Docker). `containers.lock` pins the podman-static v6.1.4 linux/arm64 archive and seven files by SHA-256 (podman, crun, conmon, netavark, aardvark-dns, rootlessport, catatonit; no fuse-overlayfs, no pasta, no runc) and the one offline image, `docker.io/library/postgres:16` (arm64, PostgreSQL 16.15, source `public.ecr.aws/docker/library/postgres@sha256:ca0bd484...`, the image id pinned too). `containers-assets.sh` runs in CodeBuild before `docker build` (direct only): it checks every file, pulls the image by digest and exports it as ONE layer (`postgres-16.rootfs.tar.xz`, 90 MiB, plus the Docker config json), because the vfs storage driver copies every layer (the 14-layer image costs 3.8 GB of the VM's 8.8 GB disk, the flat one 0.48 GB). `install-containers.sh` installs them at `/opt/harness/containers` (root-owned, not writable by others) and checks the hashes again; `containers-check.sh` checks each installed binary's SHA-256 in the built image. `/opt/harness/bin/docker` is Podman's client on the session socket. `ham-containers` (every image; a small Python 3.12 program) is the engine's way in: agentd runs `ham-containers up --user agent` as root at the start of a run; it returns at once with `/var/run/docker.sock` (a front socket owned by the engine user, mode 0600) and a small idle root-side supervisor. The runtime starts lazily: the front answers `/_ping` immediately (with the `Libpod-API-Version` header of the pinned Podman, so `docker` prints no
  warning) and wakes the supervisor on the first request that is not a ping; the supervisor then maps the namespace and starts Podman, which imports the baked-in images first (about 12 s), and the front holds that request until the runtime is up. A session that never uses Docker starts no Podman (`ham-containers status` says `backend=idle`). The runtime is Podman's Docker-compatible API service running as the engine user's uid inside a user, mount and PID namespace that `ham-containers` maps itself as root (the session runs with `no_new_privs`, so newuidmap cannot raise privileges): namespace root is uid 901, ids 1 to 65536 are host 200000 to 265535, no id maps to host root, and the process that serves the engine never holds host capabilities. It uses the vfs driver, a netavark bridge in a rootless netns with rootlessport for published ports, and a stub for pasta. `down` ends it. The session's limits shaped this (probe on a copy of the stage runtime, kernel 6.1.161, 2 vCPUs, 8 GB, root 8.8 GB): user, net, mount and PID namespaces, veth, bridge and overlay as a lower layer work; there is no TUN, FUSE or loop device, `/proc/sys` is read-only until a fresh `/proc` is mounted in the PID namespace, the root file system is an overlay (the kernel refuses an overlay upper on it) and tmpfs has no user xattrs. No registry is reachable (Docker Hub, public ECR, mirror.gcr.io, Maven Central and GitHub are dropped by the firewall; the account's ECR and S3 answer), so a pull of an image that is not baked in fails at once (a closed local proxy port, and `docker.io` is blocked by name); Ryuk is off (`TESTCONTAINERS_RYUK_DISABLED=true`) and the host is 127.0.0.1; a
  published port binds to 127.0.0.1 only (`default_host_ips` in `containers.conf`; Testcontainers asks for every address, which would expose the test database on the session's VPC interface), and the smoke script fails on a wildcard listener. Other tags and images need an ECR pull-through cache (backlog). The direct image leaves out OpenCode (176 MiB), which the one-engine release never runs: the Dockerfile installs it from a bind mount for the other families only, and the build spec runs its version check for them only (it still downloads and hashes it, one plain pinned step for every family); the direct family has no `/opt/harness/bin/opencode` (the `harness.pins.opencode` label and `pins.json` entry stay). The change is net 18 MiB smaller: OpenCode out 176 MiB, the runtime in 158 MiB (seven binaries 67 MiB, the postgres rootfs 90 MiB as xz, scripts and config under 1 MiB); the CodeBuild ARM build measured 1,780 MiB (ECR compressed 699,273,205 bytes against 639,629,868).

## Child DOX Index

None.
- `ham-research`: the engine-neutral client of agentd's loopback research API. `ham-research search`, `fetch`, `repo`, `wait`, `index [--md]`, `limits`, `check` and `verify` send the route's request bodies to `HAMH_RESEARCH_URL` and print metadata only (item id, origin, licence, size, local path, SHA-256); third-party text is wrapped in a delimiter that changes on every call, marked untrusted, stripped of control, bidirectional and zero-width characters, and a search prints at most 8 KiB. Exit codes: 0 done, 2 usage, 3 refused by policy, 4 a limit, 5 upstream, 6 pending, 7 integrity. With `HAMH_RESEARCH_URL` unset it says "research is off for this run (code disabled)" and exits 3; an address that is not a loopback `http://127.0.0.1:<port>` is refused.
- `ham-nobody-exec`: gives the engine of an Instances session the user "nobody" and a private IPC namespace. The Instances container refuses `unshare`, `setns` and every write of `uid_map` and allows `clone3` with new user and IPC namespaces and the write of `gid_map`. The helper makes a child that way; the child writes `setgroups deny` and `gid_map` `1000 <gid of the parent> 1` and no `uid_map`, checks that it reads as the overflow user (65534), that no user id is mapped and that both namespaces are new, then executes the program it was given with the exact environment the helper had. The kernel still knows the child as its parent's user, so files it writes stay readable by agentd. The helper stays as the parent: it forwards SIGTERM, SIGINT, SIGHUP, SIGQUIT, SIGUSR1 and SIGUSR2 and exits with the child's status, and the child dies with it (`PR_SET_PDEATHSIG`). Exit 125 with `ham-nobody-exec: refused: <reason>` is a refusal; there is no fallback to the parent's identity. `--check` does the setup and prints `ham-nobody-exec: ok euid=<n> egid=<n>`. agentd puts it in front of `agentd sandbox-exec` in the `landlock` mode when `AGENTD_ENGINE_IDENTITY` is not `root` (`crates/agentd/src/sandbox/AGENTS.md`); the microVM never runs it. The build spec runs it once without arguments and wants its usage text (a container build has no user namespaces).
- The Dockerfile links `/opt/harness/bin/cah-research` to `ham-research`. It links `/opt/harness/bin/cah-services` to `ham-services`. One `RUN` creates both links after both helpers are copied. User-edited rules and compatibility pack texts name `cah-research` and `cah-services`. The containers helper and the nobody-exec helper have no compatibility links. Only `agentd` calls those helpers. `images/codebuild/worker-python.yml` checks both link targets with `readlink`. It also checks that the research link runs. `COMPAT-CAH-DATA` ends at VERSION 6.00.

# lifecycle

## Purpose

The pack steers and measures. It forces nothing, and it never changes the outcome label of a run: the harness-side scorer reports on the delivered zip and does not decide when Cline is done. The contract comes in three texts, `full` (the eight steps), `quick` (a short path for a small change in an existing repository) and `auto` (both
behind a flow statement), and the setting `run.lifecycle_flow` picks the one `ham rules init` installs.

## Ownership

Owned by the root contract. This directory holds the pack, its lock, the history of the pack's earlier texts, its lock tool, and the source of the contract texts (`contract.src`) with the tool that renders them (`contract.py`). The client copies of the contract are `crates/ham-core/assets/lifecycle-rules.md` (the `auto` text),
`lifecycle-rules-full.md` and `lifecycle-rules-quick.md`, owned by `crates/ham-core/AGENTS.md`. The code that installs the pack and sends it with a run belongs to the `ham-core` pack module, the `ham` crate, the control plane and agentd, and is not built here.

## Local Contracts

- `pack/` is shipped content: `pack/AGENTS.md` (the contract: the `auto` text, at most 11,600 bytes; `contract.py` writes it, nobody edits it by hand), seven skills under `pack/.agents/skills/lifecycle-<name>/SKILL.md`
  (research, context, tdd, build-test, loop, delivery, check; the delivery skill also holds `pack/.agents/skills/lifecycle-delivery/references/dox-root.md` and `pack/.agents/skills/lifecycle-delivery/references/dox-notice.md`; each `SKILL.md` at most 60 lines, frontmatter `name` equal to the folder and a `description`
  of at most 1,024 characters, nothing else) and the stdlib-only scripts `pack/.agents/skills/lifecycle-check/scripts/lifecycle_check.py`
  (Python 3.8 or later; it reads the records and the git history of a run and writes nothing) and `scanner_kit.py` (Python 3.8 or later; the scanner kit with semgrep, bandit and the secret-shape check). `scripts/dox_lint.py` leaves `pack/` alone
  (`SHIPPED_CONTENT`): its `AGENTS.md` is the file that ships, not a DOX document.
- Engine-neutral (the harness's `ham-research` command is no engine's tool: any engine that can run a command calls it): no pack file names an engine or one engine's tool (`cline`, `.clinerules`, `.cline`, `run_commands`, `use_skill`,
  `spawn_agent`, `opencode`, `kiro`), every file is ASCII, and artifact paths are relative to the repository of the run. Placement is
  the job of the code that sends the pack, never of the pack.
- No customer text, account id, credential, token or signed URL in any pack file; no persistent password (root invariant 8). The pack
  quotes sources at most 25 words and copies no licensed text except the DOX framework text and its MIT notice (the two reference files of the delivery skill, `dox-root.md` and `dox-notice.md`; `NOTICE` at the repository root carries the entry).
- `pack.lock.json` holds `version` (X.Y.Z) and `files`: the SHA-256 of every file under `pack/`, keyed by the path relative to `pack/`.
  `lock.py` checks it (no flag) and writes it (`--write`; `--version X.Y.Z` bumps
  the version). A change to any pack file bumps the version in the same commit.
- `pack.history.json` lists, for each path of the pack, the SHA-256 of every earlier text of the file and the last pack version whose lock held it: `{"files": {"<path>": {"<sha256>": "<X.Y.Z>"}}}` in the canonical form (sorted keys, two-space indent, final newline). It sits beside the lock, outside `pack/`, so the lock does not list it and a change to it is no pack change (no version bump, no change of the pack digest or the image key). `ham rules init` reads it (`crates/ham-core/src/pack.rs` embeds it): an installed file whose SHA-256 is listed under the same path is an unedited earlier text and is replaced by the current one, and any other file is the user's and is kept (a text listed under another path never counts, and `ham lifecycle init` into a repository replaces nothing). `lock.py --write --version X` appends the old lock's hash, with the old version, of every file whose text changed; without a version change it appends nothing; `--earlier PATH=FILE` (repeatable, only with a new version) also lists the text in FILE as an earlier text of PATH with the old version, because the pack lists the `auto` contract only and the `full` and `quick` texts of the version being replaced are named this way (`--earlier AGENTS.md=fixtures/lifecycle/pack-earlier/<old version>-AGENTS-full.md.txt --earlier AGENTS.md=fixtures/lifecycle/pack-earlier/<old version>-AGENTS-quick.md.txt` at a version bump; `install_rule` looks them up under `AGENTS.md`); every write drops a hash that is the current text of its path, and a hash keeps the latest version that held it. `lock.py --backfill-history` rebuilds the file from the git history of `pack.lock.json` (every lock state older than the current version, merged side branches included; it needs a full clone): run it once, and to settle a merge conflict in the file, never edit the file by hand. It knows lock states only, so the texts that joined through `--earlier` (the `full` and `quick` texts of earlier versions) are not in what it writes; the history tests `test_the_history_holds_the_three_1_3_0_texts_of_the_contract` and `test_the_history_holds_the_three_1_4_0_texts_of_the_contract` fail when they are missing, and the lines come back from `git show <commit before the backfill>:lifecycle/pack.history.json`. The check (no flag) fails on a missing file, any form but the canonical one, a hash that is not 64 lower-case hexadecimal characters, a version that is not X.Y.Z or not older than the lock's, and a current text listed as earlier. Write the lock of a version from the lock of the last released version (`git show <tag or merge>:lifecycle/pack.lock.json > lifecycle/pack.lock.json`, then `--write --version X`) when several commits of one version change pack files, so the history gains each released text once and no draft; `--backfill-history` would list the drafts of the earlier version as well.
- The records sit in the hidden folder `.ham` unless the repository holds the file `.ham/records`, whose first value line (blank lines and lines that start with `#` are skipped) is `off` or a folder that takes the place of `.ham`. A folder `F` puts the records in `F/lifecycle`, `F/research` and `F/context`. `off` writes none of them. Any other value (absolute, `..`, a part that starts with `-` or is `.git`, a character outside letters, digits, `.`, `_`, `-` and `/`, over 100 bytes) ends the run with `BLOCKED: .ham/records holds <what>`. The grammar is in three places that read `fixtures/lifecycle/records-locator.json`: `crates/agentd/src/direct/records.rs`, `parse_locator` of the self-check script and the contract. The self-check script reads the folder (first line `LAYOUT records in <folder> (from .ham/records)`; none without the file) or, with `off`, prints `LAYOUT
  records off (from .ham/records)`, marks LC-1, LC-2, LC-3, LC-5, LC-6 and the order part of LC-8 `NA: records off` and runs LC-4, LC-7 and the secret scan; an unusable value is `LIFECYCLE-CHECK ERROR .ham/records ...` and exit 2. LC-5 reads a `RUN` row with failed tests and a note that says PASS for itself (`NEW-FAILURES PASS`) as agentd's observation does, in the script (`note_says_pass`) and in the scorer (`records::note_says_pass`), so the self-check never asks the model to fix a row the card does not call red; `fixtures/lifecycle/pass-notes.json` holds the cases all three read. No `config.toml` key: the setting belongs to the repository, `config.toml` to the user, and a run has no request member for it. The earlier texts of the contract, the delivery skill, the loop skill and the script are in `fixtures/lifecycle/pack-earlier/`;
  `crates/ham-core/tests/pack_history.rs` and `crates/ham/tests/pack.rs` show that `ham rules init` replaces them when unedited. The harness chooses the folder once per run and, when it is not `.ham`, names it in the first line of the prompt (`Records folder of this run: <dir> ...`); `lifecycle_check.py` makes the same choice from the state of the repository. The fallback to the folder of earlier runs is compatibility code (see the rename bullet below); no reader looks in two folders.
- Contract texts: `contract.src` defines `full`, `quick` and `auto` in ordered `%% <texts>` blocks. `auto` is `pack/AGENTS.md`, identical to `crates/ham-core/assets/lifecycle-rules.md`, and is at most 11,600 bytes. `full` and `quick` are `crates/ham-core/assets/lifecycle-rules-full.md` and `lifecycle-rules-quick.md`. The `Outside this checkout.` paragraph applies to all three: work requiring another repository, deployment, credentials or person is out of scope, not a blocker. The session searches for none of these, changes nothing outside the repository, completes available work and writes `NOT DONE: <item> - <why>; <what someone must do>`. The quick path covers bounded fixes, small changes and doc edits in an established repository with existing commits and an `AGENTS.md` or README. It reads applicable contracts, reproduces the problem, watches a test fail for each changed behaviour, runs focused tests and all runnable repository checks after the last edit, saves output under `/tmp`, updates affected docs and commits only task files with what, why and proof, without `--no-verify`. It creates no `.ham` records or separate red-test commit. New projects, cross-module features, new dependencies or interfaces, unresolved design questions, uncertainty and growing tasks take the eight steps.
- Flow trailer: The final commit message ends with a blank line and `Flow: quick` or `Flow: full` as its very last line. The `auto` flow paragraph states: "End the message of your final commit with a blank line and then, as its very last line, `Flow: quick` or `Flow: full`, naming the path you took (`Flow: full` if a quick task grew into the eight steps)." Q5 states: "End the commit message with a blank line and then, as its very last line, `Flow: quick`." Step 7 states: "End its message with a blank line and then, as its very last line, `Flow: full`." `quick` names only its own trailer; `full` names only its own. Backticks delimit the instruction, not characters to copy into the trailer. `lifecycle-delivery` places the DOX body line, a blank line and the Flow line in that order. Git parses the final trailer; prose following it or sharing its paragraph defeats that shape. agentd reads the engine's final commit at run end, excluding any harness commit, with a fallback to a Flow line at the start of the last message. It records `quick`, `full` or `none` beside the label. `ham` displays it on the delivery card, in `EVIDENCE.md` and in `evidence/direct.json`. Neither `lifecycle_check.py` nor the scorer checks it, and it determines no outcome.
- Missing tools: The shared `Outside this checkout.` paragraph states: "A missing tool that stops only some checks, or a check this session cannot run, is no blocker and no failure: commit the change, run the checks that can run, write a NOT RUN line in your last message for each check it stops, and finish; the goal is complete for the part that can be done." Each unavailable check gets `NOT RUN: <command> - <reason>`, not a `BLOCKED:` stop. `BLOCKED:` applies only to work inside the checkout that cannot continue: a stall, a needed persistent password, "or a missing tool without which no part of the change can be made and proved". The quick-path stall is three fixes on three different theories that leave one check failing; a missing tool alone is not a stall. The final line is `BLOCKED: <what in this checkout cannot go on>` and names only that cause. While the named blocker is unchanged, nothing else changes, the goal stays incomplete and a goal prompt receives the same line. Goal completion requires every check that can run, or every runnable Q3 check for `quick`. `lifecycle-loop` proceeds to delivery when runnable checks print their expected results and calls the goal tool only after runnable checks pass. `lifecycle-loop`, `lifecycle-delivery` and `OutsideCheckoutSkillsCase` carry the checkout-boundary rules.
- Step verification: The shared block `Rules for every step` in `contract.src` holds six verification bullets, each exactly once in each of the three texts. (1) To claim a failure predates the change, run the same command in a clean base-commit worktree created with `git worktree add`; compare failing test names, never counts, and avoid `git stash`, which can leave untracked files in place. (2) After changing a file, search the whole repository for its name, exports and definitions, including users in scripts, build files and test fixtures, and run those users' tests. (3) After correcting a comment, doc or message, search for the exact phrase and the same claim in other words, and fix every copy. (4) In an established repository, add no top-level folder or root index row unless the request names it for this repository; put evidence, architecture notes or tracker items for another repository in NOT DONE lines. (5) Make each new test fail with the requested symptom and copy its failing line; a missing file or import error means the test is broken. (6) Start runs over about five minutes in the background with output under `/tmp`, do independent work, read the output when needed and wait once with `timeout 3000 tail --pid=<pid> -f /dev/null`; short-sleep polling triggers the no-progress brake. Focused tests stay in the foreground. Q3 reads output when the run ends.

## Work Guidance

- After any pack edit: change the contract in `contract.src` and run `python3 lifecycle/contract.py --write` (it writes `pack/AGENTS.md` and the three client assets; never edit those by hand), then `python3 lifecycle/lock.py --version X.Y.Z --write` (it also adds the old hashes to `pack.history.json`), and
  update the architecture document. A merge conflict in `pack.lock.json` is settled by running `--write` again, and one in `pack.history.json` by running `--backfill-history`, never by hand.
- The run log has one line form: `RUN | <command> | exit <code> | pass <n or unknown> fail <n or unknown> | <summary line>` or `NOT RUN | <what> | <reason>`; `<command>` is the exact command as it runs from the repository root, because the clean-checkout test report runs that column again, and a note goes after it in parentheses, such as `(at BASE)`; a tool that prints
  no count is logged as unknown, never as an invented number, and a command that prints nothing is logged with "(no output)" (the checks also accept an empty or indented note).
- A seeded text names nothing outside the run's project. The deferral table of that test (`KNOWN_DEFERRED`) is empty; an entry needs the maintainers' decision.
- Keep the text short and checkable. A rule an agent can follow without a tool goes in the contract; the reason and the how go in the skill.
- Whether the model follows a step is measured by the scorer, not assumed. Tighten the text first, then move a step from a
  skill into the contract, then make the self-check a required last step.

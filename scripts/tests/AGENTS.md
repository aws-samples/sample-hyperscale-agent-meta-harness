# scripts/tests

## Purpose

Tests for the repository scripts in `scripts/` and the lock files those scripts read.

## Ownership

Owned by `scripts/AGENTS.md`. The first file holds the library and the probe: the chunker, corpus filter and baseline tokenizer against values produced by the first run's own code; the frozen question files, the corpus pins and the first-run reference by SHA-256; the Titan token limiter and request shape; an S3 Vectors stand-in that refuses more than 500 vectors per put and a wrong dimension; the four tags on every index and its deletion whatever happens; the account guard before the first call; throttle counting, the probe's own retries and the one rerun of a latency phase above 2 percent throttled first attempts; and the judge's PASS, FAIL, INVALID and INCOMPLETE outcomes for PR-0 to PR-6 with a mutation per rule. The second file holds the VM half: EC2, IAM, S3, S3 Vectors, SSM and tagging stand-ins that keep the service rules (no location constraint in us-east-1, a role in a profile or with a policy cannot be deleted, a security group with a network interface cannot be deleted, a just-made instance profile is refused by RunInstances), tags and IAM path on every resource, the launch settings (no inbound rule, IMDSv2, terminate on shutdown, volume deleted with the instance, dead-man switch first), the write-ahead manifest, dependency-ordered deletes, the inventory (every kind of leftover, terminated instances ignored, a failed enumeration is UNKNOWN), the refusals before the first create, the instance-side runner (pinned ripgrep, steps in sequence, a status always written) and the bge-small probe. The two test files read their account and profile needles from `accounts.json`, so they add nothing to the internal-names baseline.

`environ()` gives these settings to a subprocess through `env=`; `block_hosts()` gives them to the test process through `os.environ` until the test module ends. One case runs `publish --push` without its own base and sees a local `PUBLISH-FAIL push`; a spy answers any address that is not a `file://` path with a failure and does not run git. No test pushes to a real remote.

`test_operator_identity.py` covers the optional `operator` of an `accounts.json` entry: the shared table `infra/test/fixtures/operator-identity.json` (accepted and refused words, which caller ARNs the deploy engine's caller check accepts, and for which caller ARN the generator of `setup.sh` writes which operator or refuses) run through `scripts/lib/aws_target.py` and `scripts/lib/deploy.py` `check_account`; the same table runs through the TypeScript rules in `infra/test/operator.test.ts`, and the generator cases are in `test_setup_full_units.py`.

It contains accepted and refused `HAMH_OWNER` values. It includes the default `hamh-user`. The precedence order is nonempty `HAMH_OWNER`, explicit owner, operator name, default. `scripts/lib/aws_target.py` applies this order. `deploy.py` bootstrap and project tags take the owner as an argument. The stand-in AWS CLI scenario key `stage_owner` puts the `owner` tag on the stand-in stage's stacks. The shared table `infra/test/fixtures/repo-names.json` holds the repository-name rule of a stage: accepted and refused `repoNames` entries, accepted and refused `HAMH_REPO_NAMES` values, cover rows (names a rule allows and refuses) and the exact refusal texts. `test_repo_names.py` runs it through `scripts/lib/aws_target.py`, `infra/test/repo-names.test.ts` through `infra/lib/repo-names.ts`,
`crates/control-api/tests/repo_names.rs` and `crates/delivery/tests/repo_names.rs` through the Rust matchers, and `test_setup_repo_names.py` runs the cover rows through the shell matcher of `setup.sh`. `test_setup_repo_names.py` also covers `setup.sh --repo-name`: the generated account file, the refusals, `--default-repo` and the update that keeps the stage's rule (scenario: the output `RepoNames` of the stand-in control stack).

- `setup_waits.py` holds every wait limit of the setup tests. A limit is a ceiling: a wait ends when its event comes, so a larger scale costs nothing on a pass and a hang fails later, never as a pass. `wait_for(predicate, seconds, what)`, `GroupProcess.wait_ready` and `GroupProcess.interrupt` take the limit of a free host and
  scale it themselves; `limit(...)` is for the other calls. The shared `run_setup` of `test_setup_script.py` limits one run of `setup.sh` against the stand-in to `RUN_BASE` (180 s on a free host), four times the CPU time of the slowest run measured (a teardown, 42 s); lower it only after measuring again. The ticker cases of
  `test_setup_teardown_live.py` count the lines a program prints in windows of a second or two; they multiply their intervals, polling and waits by the scale rounded up to a whole number (`Q`), so the proportions they rely on stay and the delay a window absorbs grows with the scale. `wait_for` polls an event and reads the
  predicate once more at the limit. `GroupProcess` runs a program in a session of its own, reads its output with a thread, and at the end of the test, whatever the outcome, sends SIGKILL to its process group and to the processes that left the group but stayed in its session (a process that called `setsid` is out of reach);
  cleanup fails the test when something is still running afterwards. The leader is collected only after that, so its group number cannot be reused first. `interrupt` fails when the program had already ended (a signal would reach nothing and the end would be its own). A wait that runs out names its stage (`ready`, `signal`,
  `exit` or `eof`: the program did not get there, had ended, did not end, or ended while a process it started still holds the pipe or the reader failed) and prints the output, the processes of the group with state and wait channel, the load, and the pressure and CPU-throttling figures of the host. Importing `setup_waits` makes a
  test process that was started with Ctrl-C ignored (a background CI job) handle it, so the programs it starts get the default and can trap it. `FullBase.popen` and `FullBase.follow_started` (`setup_full_support.py`) start `setup.sh` this way and wait for its first look at the stand-in build, the point from which its Ctrl-C
  handler exists. A passing run that took more than 2 s to end after a signal says so on stderr. A new wait in these files takes its limit from `limit(...)`.

# scripts

## Purpose

Repository tooling: checks, engine builds, deploy, teardown, and verification entry points.

## Ownership

Owned by the root contract. Each script documents its inputs, outputs, and exit codes in its header.

## Local Contracts

- Account target: every script, library and probe that calls AWS targets one entry of the repository root `accounts.json`, chosen by `HAMH_AWS_PROFILE` (the entry's profile; unset or empty: the active entry) through `lib/aws_target.py`. Wrappers source `lib/aws-target.sh` after `lib/python.sh`, which exports `HAMH_ACCOUNT`, `HAMH_REGION`, `HAMH_PROFILE` and `AWS_PROFILE`; libraries take `ACCOUNT`, `REGION` and `PROFILE` from `aws_target.module_target()`. An inherited `AWS_PROFILE` never selects; an unknown profile exits 2 before any AWS call. `HAMH_AWS_PROFILE=ham-acct-b02` is the interim switch back. New records name the selected entry; records already written keep theirs. The account-file override: `HAMH_ACCOUNTS_FILE`, an absolute path, makes every consumer read that file in place of the
  committed `accounts.json` (`setup.sh` generates one for the account it deploys into, so the committed file is never edited). Unset or empty, every consumer behaves as before; a relative path, a missing file and a directory are refusals and never fall back to the committed file. It is read by `lib/aws_target.py` (so by `lib/aws-target.sh`, `lib/build_selection.py` and every wrapper), `infra/lib/config.ts`, `crates/harness-protocol/build.rs`, `node.sh` (mounts the file read-only into the CDK container, after `lib/path-canon.sh` has resolved its path), `codebuild-run.sh` (carries it into the child builds) and `lib/deploy.py` (records its digest). The optional `operator` of an entry is parsed by `lib/aws_target.py` (`parse_operator`, `Target.operator`, `get operator` prints `role/<name>` or
  `user/<name>`, empty when the entry names none); an entry without it behaves as before, and the committed file names none. `tests/test_operator_identity.py` runs the shared table `infra/test/fixtures/operator-identity.json` through it. `lib/aws_target.py` parses the optional entry `owner` through `parse_owner` and `Target.owner`, resolves it through `owner_of` with nonempty `HAMH_OWNER` first, and prints it through `get owner`. `lib/aws_target.py` also provides `owner_is_named`, which is true for a nonempty `HAMH_OWNER` or an entry's `owner`. In `lib/deploy.py`, `settle_owner` reads the stage's `owner` tag from the network stack, else the control stack (`OWNER_STACKS`), keeps it when no owner is named, ends with `DEPLOY-FAIL owner` when a named owner differs or the tag is not a valid owner
  value, and exports the result as `HAMH_OWNER` to every `cdk` call. `lib/aws_target.py` also parses the optional entry `repoNames` (1 to 8 entries: a repository name, a prefix ending in `*`, or `*`) through `parse_repo_names` and `Target.repo_names`, resolves the rule through `repo_names_of` with nonempty `HAMH_REPO_NAMES` first (default `hamh-e2e-*`), matches names with `repo_name_allowed` and prints the list comma-joined through `get repoNames`. `tests/test_repo_names.py` and `infra/test/repo-names.test.ts` run the shared table `infra/test/fixtures/repo-names.json`; the Rust copies of the matcher in `crates/control-api` and `crates/delivery` run it too. Tests that were written against ham-acct-b02 select it explicitly, and each script has a case for the active default.

- `build-cline-fork.sh`: verifies and builds the Cline fork pinned in `engine/cline/lock.toml`.
  - Checks, in order: lock syntax and formats; every file in `engine/cline/patches/` and
    `engine/cline/patches/tdd/` listed; each patch SHA-256 and each test-only header; the tag clone's HEAD equals the locked
    commit; `git am` applies the series one patch at a time, applying each test-only patch on a
    side branch just before its series patch and requiring its recorded tree; the resulting tree
    equals the locked tree. `--verify-only` stops here and needs no bun or docker.
  - A build fetches the pinned bun zip into `<work>/tools` (`curl --retry 5 --retry-all-errors`) and
    checks its SHA-256. Unless
    `--no-gate`, it then runs the gate in the pinned build image as the host uid with a passwd
    entry, on the unpatched tag and on the patched tree: `bun install --frozen-lockfile`,
    `bun run build:sdk`, the five package suites and `bun run types`, every step green (exit 10
    otherwise). The `@cline/core` suite runs with vitest file parallelism off (`--no-file-parallelism`)
    on both trees, because upstream's `bash.test.ts` detached-log test races the `LocalRuntimeHost`
    start-up of another test file over the shared `TMPDIR`; every test and pass criterion stays and the
    other four suites keep vitest's scheduling. Then `bun script/build.ts` with
    `CLINE_BUILD_TELEMETRY=off`. A target matching the host uses `--single`; a cross target uses `--install-native-variants` and keeps only that
    target's binary.
  - Scratch comes from `--work-dir` or `CLINE_FORK_WORK_DIR` (required). The script refuses /tmp,
    system temp, `$HOME`, dot dirs under `$HOME`, and the repo. Child processes get HOME, TMPDIR,
    and an empty git and docker config from the run dir.
  - Outputs to `--out` (default `<work>/out/<mode>-<run id>`): `build-metadata.json` always;
    builds add `cline`, `cline.sha256`, `build.log` and `gate/<tree>-<step>.log`. Last stdout
    line `VERIFY PASS`, `BUILD PASS` (`--no-gate`), or
    `FORK-BUILD PASS series=<n> tree=<sha12> bin=<sha12> telemetry=off leaks=0`.
  - A gated build also writes the record
    `<out>/<date>-cline-fork-build-<x64|arm64>-<run id>.json` (kind `cline-fork-build`; measurements
    `arch`, `baseline` {llms, core, shared, agents, cli, types: `ran`}, `suites` {baseline, patched:
    `green`}, `passed` counts, `gateSchedule` {core: `file-parallelism-off`}, `telemetry` `off`,
    `leaks` 0, `binarySha256`), copies it to
    `--record-dir` (gated builds only; exit 2 otherwise) and prints `FORK-BUILD RECORD <path>` before
    the last line. `--image-digest <64 hex>` (the stage's SSM `/hamh/direct/image-digest`) stamps
    `imageDigest`, the record's freshness key; without it the value is null.
  - Exit codes: 0 pass, 2 usage or unsafe environment, 3 invalid lock or patch set, 4 patch
    SHA-256 mismatch, 5 commit mismatch, 6 clone or `git am` failure, 7 tree mismatch (series or
    test-only), 8 toolchain mismatch, 9 build failure, 10 gate failure.

- `cargo-slot.sh <cmd...>`: runs the command holding one of `CARGO_SLOTS` (default 2) flock slots
  in `CARGO_SLOT_DIR`,
  so at most two cargo builds run at once across
  worktrees; the command runs without the lock fd. Every builder runs heavy cargo commands through it.
  COMPAT-CAH: when `HAMH_TOOLS` is unset and `CAH_TOOLS` is set, the default lock folder is the `locks` folder of the tools folder `CAH_TOOLS` names; `HAMH_TOOLS` wins when both are set.
  `CARGO_SLOT_PRIORITY=high` (set by `deploy.py` for its builds) registers `<dir>/priority/<pid>` while
  waiting; normal jobs take no slot while a live registration exists. Never raise `CARGO_SLOTS` to
  go faster (a third build OOM-killed the linker on the 30 GB host); use the priority. A machine without `flock` (a stock macOS) or with a bash older than
  4.1 (its bash is 3.2) runs the command at once after one line on standard error that says so; a `flock` that fails with a message, or with an exit code of 126
  or more, ends the run with exit 2 and what it said. Only the silent exit 1 of `flock -n` and `flock -w` is a busy slot that is waited for.

- `research-key-put.py --stage direct [--check | --clear | --rotate | --rotate-enterprise --ttl-hours N --key-limit N]` — the one command that stores the Tavily API key in the stage's Secrets Manager secret `hamh-direct-research-tavily-api-key`. Account, Region and profile come from `lib/aws_target.py` (`HAMH_AWS_PROFILE` selects). It asks for the key twice at a hidden getpass prompt on a real terminal (a stdin that is not a terminal is refused; there is no option, variable or file that can carry the key; 20 to 256 printable ASCII characters) and runs the AWS CLI (`HAMH_AWS_BIN`, else `aws`) with an argument list: a read-only `describe-secret` pre-flight, then `put-secret-value --secret-string file:///dev/stdin` (the key reaches the CLI on stdin only, never in argv, the child's environment, a file or the output; error text is printed with the key replaced by `<redacted>`) and `tag-resource research-key-stored-at=<UTC date>`. It prints the ARN, the version id, the number of characters and the next step, nothing derived from the key. It never creates the secret and never calls `get-secret-value`. `--check` only reports whether an AWSCURRENT version exists and, from `LastChangedDate` of the same `describe-secret` answer (ISO 8601 with an offset as CLI v2 prints it, or a Unix time as CLI v1 does; an unreadable or missing date prints `age: unknown` and does not fail), how many days ago the secret was last changed, the `research-key-stored-at` tag beside it and the limit; `--max-age-days N` (a whole number from 1 to 3650, default 30, refused without `--check`) sets the limit and exit code 5 means the key is older. `--check` also prints which provider a stage in auto mode uses: the value is never read, so a current version is told from the `research-key-stored-at` tag, a date meaning a key (`auto: Tavily is used (a key is stored)`) and `cleared-<date>` a blank one (`auto: AgentCore Web Search is used (no key; cleared on <date>)`, no age line and no exit 5, since a blank has no key to rotate), and any other tag state prints `auto: cannot tell ...` and keeps the age check; no current version prints `auto: AgentCore Web Search is used (no key)`; a missing secret prints no provider line. `--clear` stores a blank version so an `auto` stage searches with AgentCore Web Search again: Secrets Manager refuses an empty `SecretString` (minimum length 1, the PutSecretValue reference), so the blank is one space, which the research Lambda trims to no key; it makes the same three calls (`describe-secret`, `put-secret-value` with the space on stdin, `tag-resource research-key-stored-at=cleared-<UTC date>`), asks for nothing, needs no terminal, prints the ARN, the version id, `cleared:` and the next step, and is refused with `--check` or `--max-age-days`; the previous key keeps the label AWSPREVIOUS until the next store, and the output says to delete it in the Tavily dashboard to revoke it. Exit codes: 0 stored, cleared or present (and not older than the limit); 1 an AWS step failed; 2 refused (not a terminal, entries differ, bad key, bad target or arguments, `--clear` with `--check` or `--max-age-days`); 3 no AWS CLI or no secret (deploy the stage first); 4 `--check` found no AWSCURRENT version; 5 `--check` found the key older than `--max-age-days`; 6 (`--rotate`, `--rotate-enterprise`) Tavily could not be asked or answered something unreadable, nothing stored; 7 the key IS stored but the research route did not confirm it within 6 minutes, cannot report, or cannot be invoked; 8 (`--rotate-enterprise`) stored and confirmed but a previous generation is not deactivated; 9 `--check` found the generation that made the current key past its expiry; 130 interrupted after the prompt. `--rotate` asks for the key like the plain store, then (1) probes it with `GET https://api.tavily.com/usage` from the operator's machine (`http.client`, which follows no redirect, so the bearer token goes to one host; a 200 must carry `key.usage` and `key.limit` (null is no limit, a missing member is a malformed answer) and prints those two numbers and nothing else; 401 or 403 refuses, exit 2; usage at or above the limit refuses, exit 2; 429, a timeout, a server error or an unreadable body is exit 6 with the minutes to retry from `retry-after`, whole seconds or an HTTP date, else the endpoint's window of 10), (2) stores only an accepted key with the plain store's calls and tag, (3) waits up to 6 minutes (`ROUTE_WAIT_S`, counted on the monotonic clock from the moment the put returned, polls every 15 s, an answer after the deadline is not accepted) for the research route to report that it holds the stored version: `aws lambda invoke` of `hamh-direct-research-api` (`FUNCTION_NAME`, pinned to `infra/lib/stacks/research.ts`) with the event of `fixtures/research/key-state-event.json` (`key_state_event`; the test pins both to the same JSON), whose answer is the provider word and the Secrets Manager version id of the key the function holds (`crates/research-api/AGENTS.md`, KEYSTATE), confirmed when the provider is `tavily` and the id equals the one the store returned; an answer of not found (a stage deployed before the question existed) or an AWS error such as AccessDenied ends the wait at once with exit 7, and (4) prints `delete the old key in the Tavily dashboard after HH:MM`, the store time plus 6 minutes in the operator's zone. A put that failed or answered something unusable is followed by `list-secret-version-ids` compared with the versions the pre-flight `describe-secret` showed: a new version means stored (the run goes on), a list that succeeded with no new version means not stored, anything else is unknown (exit 1, run `--check`). `--rotate-enterprise` reads an admin key at the same hidden prompt, generates a user-level key (`POST /generate-keys`, count 1, no scope; `--ttl-hours` and `--key-limit` are required, `--key-type` defaults to development, `--key-name` to `hamh-<stage>-<UTC date>`), probes and stores it like `--rotate`, and records the generation in the tags: `research-key-generations` is the ledger of every generation that may still be active (comma separated, oldest first, no duplicates, each `request_id@version_id` with the secret version that holds its key; it is written with the tags in one JSON array because a shorthand value cannot hold a comma; 256 characters hold three entries and a run refuses to start with an unreadable or full ledger) and `research-key-expires-at` is the expiry of the newest. After the tags were written, the route confirmed and 330 s (`DEACTIVATE_AFTER_S`, counted from the store on the monotonic clock) have passed, each previous generation is deactivated with `POST /deactivate-keys` and the admin key unless `list-secret-version-ids` shows that its version is the current one (skipped, exit 8); a version check that cannot be made deactivates nothing (exit 8); every generation that is not deactivated stays in the ledger, which is rewritten to the active ones. A key made by the run is deactivated again only when it is certain that it was not stored (the probe failed, or the secret was read back and holds no new version); an unknown outcome deactivates nothing and prints the request id, the expiry and the steps to do it by hand. A plain store, `--rotate` and `--clear` leave the Enterprise tags as they are and print the request ids that are still active and when the newest expires. `--check` prints the generation that made the current key and its expiry (recorded for the newest entry only), lists the other active generations and exits 9 when the one that made the current key is past its expiry. After the first key is typed the script prints fixed messages, status codes and the AWS error codes of `ALLOWED_AWS_CODES`, never a response body or an error text; `redact_all` replaces the longest key first; `Cli.holding(keys)` binds the typed and made keys to every later call, and every call has a 60 s limit (`AWS_CALL_TIMEOUT_S`, a call that hangs is exit code 124 inside the script and is handled like a failure). Every mode that takes a key asks the CLI itself whether its history is on (`aws configure get cli_history` with the selected profile and Region: `enabled` in any case refuses, exit 1 with no output is not set, any other failure refuses; the CLI records `SecretString` in `~/.aws/cli/history/history.db` when `cli_history = enabled`). Ctrl-C after the prompt prints a summary of what was done and that nothing was undone, exit 130. Run one operator at a time: no lock is built. The new calls are `list-secret-version-ids`, `untag-resource` (`ROTATE_SUBCOMMANDS`), `lambda invoke` (`LAMBDA_SUBCOMMANDS`) and `configure get cli_history` (`CONFIGURE_SUBCOMMANDS`); `get-secret-value` stays out and `Cli.run` raises for anything else. No `nosec` or `nosemgrep` comment was added.

- `gomod-store.sh fill --stage live|drill|direct --modules <list file> [--approved FILE] [--tools FILE] [--out DIR] [--jobs N] [--dry-run] [--go PATH] [--bucket NAME] [--no-assume-role] [--build-check] [--reuse-current]` and `gomod-store.sh check --stage ... [--manifest FILE] [--jobs N] [--quick]`: the operator step that fills and audits the Go module store, the approved, create-only GOPROXY tree in the bucket `hamh-<stage>-gomod-<account>` (packages stack) that workers read for Go modules. `fill` refuses, exit 2 before any download or AWS call, a line that is not `path@vX.Y.Z`, a module not on the approved list (default `engine/rules/deps/go-approved-modules.txt`), an upstream other than `direct` or one https URL and a checksum database other than sum.golang.org. It resolves each root and then all roots in a synthetic consumer module with real Go: `go get`, every public package as a blank import, `go mod tidy`, `go mod download`, `go mod graph`. Tidy also loads the test imports of a dependency's packages, so the store holds those modules too (amqp091-go's goleak). It harvests `cache/download`, checks each stored version against the checksum database's lookup record (the `h1:` of its zip and go.mod), stages the tree with per-module `@v/list` (tagged versions that have a zip) and `@latest`, and
  proves it offline: fresh module cache, `GOPROXY=file://<stage>`, `GOSUMDB=off` and the lock step's environment, every consumer from a minimal go.mod must pass `go mod tidy` and `go mod download` (`--build-check` adds a warning-only `go build ./...`). Only then does it upload, as the role `hamh-<stage>-gomod-filler` (`--no-assume-role` writes with the profile, for a test bucket): content objects first, each one put `If-None-Match: *` with a SHA-256 checksum (same bytes under the key = `exists`, other bytes = `CONFLICT`, never an overwrite), then the index files by compare-and-swap (`If-Match` with the ETag just read; the new content is the union), then the manifest `_manifests/<UTC>-<nonce>-<sha12>.json` (the sha256 of every object, the hashes the checksum database confirmed, upstream, Go version). Any failure before the upload leaves the bucket untouched. `--dry-run` runs everything but the AWS calls (`PLAN put` lines). `--reuse-current` (the setup runner passes it) first reads the newest manifest of the store and compares its stage, bucket, roots, tool roots, Go version, upstream and checksum database with this fill's (`manifest_covers`): when they are equal and its offline check passed, nothing is resolved, staged or uploaded, no manifest is written and the last line is `GOMOD-FILL CURRENT
  stage=<s> roots=<n> modules=<n> objects=<n> bucket=<b> manifest=<key>`; otherwise a `REUSE no <what differs>` line says why and the fill goes on (an empty store, a manifest that cannot be read and `--dry-run` always fill). Without the flag a fill always resolves everything. Last line `GOMOD-FILL PASS|CURRENT|DRY-RUN|FAIL ...`. `check` reads the bucket (`--jobs` calls at once; about 2 minutes for 785 objects): every manifest object present with its SHA-256 (an `.info` by presence: its Origin may differ between upstreams), every `list` naming only versions that have `.info`, `.mod` and `.zip` and no pseudo-version, `@latest` one of them; `GOMOD-CHECK PASS|FAIL`. A bucket with no manifest fails with the fill command in the line. `check --quick` reads one object of the bucket and nothing else: `GOMOD-CHECK PASS stage=<s> quick=nonempty bucket=<b>`, or `GOMOD-CHECK FAIL empty stage=<s> bucket=<b>: ...` with the fill command (exit 1) when it holds none; a failure that is not an empty store (wrong account, no such bucket, no permission) never says "empty". Test hooks: `GOMOD_STORE_AWS_BIN`, `GOMOD_STORE_GO`, `GOMOD_STORE_UPSTREAM` (a `file://` upstream; the manifest then says `test-upstream`), `GOMOD_STORE_SUMDB=off` and `GOMOD_STORE_TEST_DROP` (both need the upstream hook). `gomod-store.sh` accepts
  `--stage direct` beside `live` and `drill`; the packages stack uses bucket `hamh-direct-gomod-<account>` and filler role `hamh-direct-gomod-filler`, built from the stage prefix by `infra/lib/config.ts`. The flag `fill --tools FILE` lists tool roots, modules with runnable main packages: agents use `go run <module>@<version>`; blank imports cannot name main packages, so consumers use Go 1.24 `tool` directives through `go get -tool`, then `go mod tidy` downloads build needs. Each tool root gets its own consumer; `all`, the library-only consumer, excludes tools because two tool versions cannot share a `go.mod`; modules in both lists cause exit 2, and the manifest gains `toolRoots`.

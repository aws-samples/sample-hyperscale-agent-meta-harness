# crates/agentd

## Purpose

The supervisor runs inside a microVM for one AgentCore session. It serves the runtime contract on port 8080: `GET /ping`, `POST /invocations`. Its direct driver sends ONE prompt to the engine over ACP. The driver delivers what the engine left. The supervisor provides `credential_process`, a credentials helper. It also provides a loopback package proxy. It posts events to the private internal API.

## Ownership

`crates/AGENTS.md` owns this contract. Wire types come only from `harness-protocol`: `runtime`, `direct`, `api::internal`, `envelope`. Engine launch comes only from `harness-core::engine_profile`. The package proxy is the `pkgproxy` crate.

## Local Contracts

- Never log, echo or return request bodies, credentials or the refresh nonce (S3 canary check).
- The completion key: `direct::run_with` derives it from the invocation's nonce (`CredsBinding::completion_key`), gives it to `HttpEventSink::with_completion_key` and adds it to the run's `SecretSet`. The sink sends it in the header `x-hamh-completion-key` on `/internal/events` and `/internal/turn-complete` only; worker-api refuses those two routes without it. `tests/b593_completion_key.rs`.
- Credentials live only in `agentd` memory. They reach the engine through `agentd creds --socket`. agentd serves a 0600 Unix socket, `creds_socket`. Each connection gets one line of `ProcessCredentials` JSON. On failure, it gets `{"error": ...}` and exit 1. This fails closed. The invocation's session credentials are re-minted through `/internal/creds`. This uses the rotating nonce. Refresh starts when fewer than `REFRESH_WINDOW_S` (600 s) remain. A failed refresh fails closed. Every secret the store installs or a refresh mints (the secret key, the session token, the nonce) is added at that moment to the run's `SecretSet` (`secrets::SecretSet`, `CredStore::watch_secrets`; the driver watches it before the store's first use of the run), which the collector, the recorder, the digest sources and the end sequence redact with; nothing is removed from it, so a value the engine printed before a rotation stays redacted after it (report 7.3; `tests/creds.rs`, `direct_invocation.rs` with the scenario `leaky_error`).
- An engine starts only from `engine/profiles/<name>.toml`.
- Entry points are `agentd serve [--listen <addr>]`, `agentd creds --socket <path>`, `agentd sandbox-exec --policy-json <json> -- <program> [args]` and `agentd --version`. Settings come from the environment through `config::Config`. Defaults match the worker image layout. Settings include `AGENTD_LISTEN`, `AGENTD_PROFILES_DIR`, `AGENTD_FIXTURES_ROOT` and `AGENTD_TEMPLATES_ROOT`. They include `AGENTD_WORKSPACE_ROOT`, with default `/mnt/workspace`. They include `AGENTD_DATA_ROOT`, with default `/var/lib/agentd`. They include `AGENTD_RUNTIME_DIR`, `AGENTD_ENGINE_PATH` and `AGENTD_EXE`. `AGENTD_ENGINE_PATH` gains the Rust toolchain's bin directory of the worker image, `AGENTD_RUST_BIN` (default `/opt/harness/gate-tools/lang/rust/bin`; an empty value switches it off), once, before the first of `/usr/local/bin`, `/usr/bin` and `/bin`, or at the end when the list has none. `AGENTD_DIRECT_CARGO_JOBS` is the `CARGO_BUILD_JOBS` of the engine's session (default 2, a session's vCPU count; a whole number from 1, and above 64 it is 64; anything that is not a whole number from 1 is the default). `AGENTD_CARGO_TARGET_DIR` is where the engine's cargo keeps `target/`. `AGENTD_DISK_LOW_MB` (default 512) and `AGENTD_WORKSPACE_LIMIT_MB` (default 960, the checkout mount's 1024 MiB less a 64 MiB margin) are whole numbers of MiB for the session-disk check: the root volume is short of room below the first, the checkout mount is full at the second; 0 switches a check off, both at 0 switch the measurement off, anything that is not a whole number is the default and a huge number is 16 TiB. `AGENTD_DISK_CHECK_S` (default 60, 0 to 3600), `AGENTD_DISK_PRUNE_MB` (default 1536, MiB) and `AGENTD_CARGO_KEEP_MIN` (default 20, 0 to 1440) set the pruning of stale cargo output while a prompt runs: how often the free space of the root volume is read, the free space below which the cargo target folder is pruned, and how long a unit compiled lately is kept; 0 in any of the three switches the pruning off. `AGENTD_STALL_BUSY_PCT` (default 50, 0 to 1000) is the share of one CPU, in percent, that the session must have used outside agentd and the engine for the brake inside a round to count a stretch as progress; 0 switches the signal off. `AGENTD_ENGINE_USER` defaults to `agent`; an empty value disables the uid split. When agentd runs as root and the named user cannot be resolved (no such user, a failed lookup, an unreadable own uid or a user of uid 0) the run ends before anything is fetched or placed: `stopped_setup_failed`, the label "Cline did not start", and an error text and a log line that name the user. The engine never starts as root by accident. A non-root agentd and an empty setting start the engine as before. `engine::resolve_engine_identity` decides it over the seam `engine::EngineUsers` (`direct::Deps.engine_users`; the real one is `SystemUsers`: `geteuid` and the `id` command); `tests/b633_engine_user.rs`. `AGENTD_ENGINE_SANDBOX` is `uid` or `landlock` and is required: the deployment says how the engine is kept out of agentd's secrets, and unset or any other value ends the run before anything is fetched; `landlock` needs an empty `AGENTD_ENGINE_USER`. This code alone is not deployable: a worker image of this tree on a runtime that does not set the word ends every run in `stopped_setup_failed`. `AGENTD_ENGINE_IDENTITY` is read in the `landlock` mode only: unset, blank or `nobody` runs the engine as the user nobody (65534) in user and IPC namespaces of its own, through the helper `/opt/harness/bin/ham-nobody-exec`; `agentd` runs it as agentd's own user as before; any other word ends the run before anything is fetched. `AGENTD_NOBODY_EXEC` names the helper (default `/opt/harness/bin/ham-nobody-exec`). Module `sandbox::identity`, contract in `src/sandbox/AGENTS.md`; turning the route off changes the runtime's environment and needs no image build. `AGENTD_S3_ENDPOINT` and `AGENTD_INTERNAL_API_ENDPOINT` are for tests only. Settings also include `AGENTD_PACKAGES_*` and `AGENTD_GOPROXY`.
- Open-files limit (module `nofile`, whose header holds the reasoning): `agentd serve` lowers its own soft open-files limit once, right after the hardening and before the settings are read, a socket is bound or any process is started, so the engine, the tool server, the package proxy, the commands of the report step and every program they run inherit it. A very large limit (some container runtimes start a session near a billion) makes every program that closes each descriptor number up to the limit before it starts another program take minutes per start. `AGENTD_OPEN_FILES_CAP` (default 65536; a number from 256 to 4194304; `0`, `off`, `false` or `no` leave the session's limit as it is; anything else is a config error line and the default applies; read by `config::open_files_cap`) is the cap. The soft limit is only lowered, to the cap or to the hard limit when that is lower, and never to 0; the hard limit is never touched, so a program that needs more descriptors raises its own soft limit again. One runtime log line says what happened (`open files limit lowered: soft <from> to <to>, hard <hard>, cap <cap>`, `open files limit left alone: ...` or `open files limit not lowered: ...`), a limit that reads back differently than it was set is the last of these, and a failing `setrlimit` is that line and never a failed start. Both compute types start agentd the same way, so nothing is per compute. Tests: `tests/nofile.rs` (the pure function, the variable, `apply` over a stand-in limit), `tests/nofile_process.rs` (the real limit: a process of the engine launcher and a command of the report step see the cap and the unchanged hard limit), `tests/nofile_serve.rs` (the `agentd serve` binary with the fake engine and a report step; the scenario `report_prints_nofile`).
- The core is engine-neutral. Engine-specific code lives only in `src/engine/`. Outside that directory, no line of `crates/agentd/src` matches either engine name. The check uses case-insensitive word-boundary matches for `cline` or `opencode`. `tests/engine_neutral.rs` counts those matches. Comments and strings outside that directory therefore say "an engine". Generic modules keep their public functions. They ask `src/engine/` for every answer that depends on an engine's name. `src/engine/mod.rs` handles process launch and the uid split. `src/engine/config.rs` handles built-in config files, environment settings and `acp_model_value`. `emit` uses it. `src/engine/direct_words.rs` holds the plain words of the user correction path that name the engine (the title and explanation of each reason to ask, the opening line of the fresh-session prompt, the digest title of the engine's last message). `src/engine/direct.rs` handles the rules listing command and parser. It also handles the direct launch argument and locked settings file. It handles the protected configuration directory too. `src/engine/faults.rs` provides the text of an engine's own timeout. `acp` uses it. `src/engine/exit.rs` and `src/engine/stderr.rs` handle how the process ended and its rotated stderr log. An engine with a profile but no arm there gets generic behavior. That means no built-in config and no rules listing.
- Before launch, each profile's `hiddenPaths` entry is checked. Each entry must be a relative path or `<dir>/**`. The latter covers a whole directory. Any other glob is refused. Each entry that exists in the repo is moved aside. `workspace::hide_paths` does this. The run logs `direct turn quarantined: <paths>`. The end sequence drops whatever the engine wrote at those paths. The original files then return.
- `/invocations` is asynchronous. AgentCore cuts synchronous requests at 15 minutes. The endpoint takes a `kind: "direct"` body and validates it. It then claims the one turn slot. Otherwise, it returns 409 `a turn is already running in this session`. It sets `/ping` to `HealthyBusy`. It removes a stale `result.json`. It answers `InvocationAccepted` and runs the direct driver in the background. At the end, it posts `/internal/turn-complete`. The outcome is telemetry; it gives no verdict. A failed post is logged and is never fatal. A completed turn's `summary` is the agent's text. `turn::summary_of` removes control characters and keeps the last `MAX_TURN_SUMMARY_CHARS`. Next, it writes the `InvocationResponse` by rename to `<AGENTD_DATA_ROOT>/<run>/direct/turns/1/result.json`. It then frees the slot and `/ping`.
- The package proxy needs `AGENTD_PACKAGES_DOMAIN` and `AGENTD_PACKAGES_OWNER` set. The runtimes stack sets both and `AGENTD_PACKAGES_REPOSITORY`. The repository default is `packages`. `AGENTD_GOPROXY` names the Go module source. The invocation must carry `packagesToken`, the CodeArtifact token. `run-session` mints that token outside the VM with its own role. agentd asks CodeArtifact for nothing. `packages::mint_token` is the CodeArtifact call. The worker session's credentials carry no CodeArtifact grant. With these settings and token, agentd starts the loopback `pkgproxy`. `direct::PkgProxyLauncher` uses `127.0.0.1:3128`, or any free port otherwise. The token stays in agentd's memory, in root-only memory, in three places that each wipe their buffer on drop: the parsed invocation (`PackagesToken`, the wire type, whose text is read only through `expose`), `ProxyStart.token` (the same type, cloned for the proxy start) and the proxy's `Secret`s (one per credentialed upstream, `codeartifact_upstreams` makes four). The one copy that is not wiped is the run's `SecretSet` (`secret_values`), which holds every secret of the invocation as plain text so the collector and the end sequence can redact with it until the process ends (report 7.4; `tests/direct_invocation.rs` pins the type of `ProxyStart.token`). The token is never in the engine's environment, in a file or in `summary.json`. The engine gets the proxy's environment, a Maven settings file and a cargo config file. It never gets the token or an index file. Without a token or an index, the log says `direct turn package proxy not started: no token or no index`. A failed start logs `direct turn packages not available: <reason>`. The run then goes on without packages. The proxy's counters go into `summary.json` under `packages`. The proxy stops after the tree is delivered.
- `InvocationResponse.usage` contains what the engine reported in the `session/prompt` result. Usage comes from `_meta.usage` or ACP `usage`. Cache tokens use the Converse names or ACP `cachedReadTokens` and `cachedWriteTokens`. Input excludes those cache tokens. Usage is `null` when the engine reported none. A nudge prompt's usage is added through `turn::prompt_usage`. Invocation logs are the token record.
- Event ids (`time::new_ulid`, `time::ulid_from`): agentd names its own events with a monotonic ULID, the ULID specification's monotonic mode: every id is greater than every id this process made before, whatever the clock or the random source does. A newer millisecond takes a fresh random part; the same or an earlier millisecond (a clock that stepped back) keeps the newest millisecond and adds one to the 80-bit random part; a full random part moves to the next millisecond (no panic). `ulid_from(now_ms, &mut UlidState, rng)` is the pure form that tests drive with a frozen clock and a descending random source. `EventRecorder` makes the id, `seq` and the append inside one lock (`record`, and `record_urgent_minted` for a question whose event id IS its request id: the id goes to the payload builder inside the lock), so the order of the buffer, of `seq` and of the ids is one order, and a debug assertion fails an id that does not sort after the newest one the recorder made. Why: a random tail sorted `input-received` and the `input-closed` of the same finish in either order within one millisecond, and every reader that orders by `eventId` (the shard read, `ham`, `fold_input`) saw the close first (`ham finish` exited 1 for a finish that took effect). Not covered: a restart after a clock step back (the new process does not know the old tail), ordering across writers, and the cursor skipping an event written late below it. `tests/time_ulid.rs`.
- Controls arrive in `/internal/events` responses. The flusher, `events::spawn_flusher_with`, posts every 2 s. It sends an empty poll when idle. It sends a heartbeat every 60 s. The final flush sends `takeControls: false`. A control meant for a later turn therefore waits. `TurnControls` acts only on `Cancel`, sent by `ham stop`. It raises the cancel signal. `session/cancel` is written once. The engine gets `CANCEL_GRACE` (10 s) to answer `cancelled`. An `Instruct` control goes to a bounded channel (16) that the driver takes once with `TurnControls::take_instructions`; a `Cancel` in the same batch is raised first and marks that batch's instructions `cancelled_in_batch` (the driver acknowledges them `input-ignored`); a full channel or a gone receiver drops an instruction and the flusher logs it. Each pending control is parsed alone (`lenient_pending`), so a control this build cannot read never costs the batch or the Cancel beside it. `EventRecorder::record_urgent_with_id` records an urgent event with a given ULID (the id of a `needs-input` event is the id of its question). Other controls are ignored. A failed post is logged and never fails the run. At most 2,000 events are kept while the internal API is unreachable. The oldest events drop first.
- The engine runs with `PYTHONDONTWRITEBYTECODE=1`, set after the profile environment. Before engine startup, run setup lists `workspace::GENERATED` in the worktree's `<repo>/.git/info/exclude`. The generated entries are `__pycache__` and `*.py[cod]`, and the build folder `target/` (`workspace::BUILD_OUTPUT`, cargo's and the Maven and Gradle folder of the name; a file the repository already tracks stays tracked). `workspace::exclude_generated` adds one line for each entry; `exclude_generated_with(wt, false)` leaves `target/` out when the user turned that default off. A test run then never rewrites a tracked cache. Neither the engine's `git add -A` nor the end sequence's commit tracks bytecode.
- agentd's own git calls (`workspace::git_command`) use `core.hooksPath=/dev/null`, `core.fsmonitor=false`, `core.fileMode=true`, `core.attributesFile=/dev/null`, `commit.gpgSign=false`, `tag.gpgSign=false` and `protocol.ext.allow=never`, and a cleaned environment: `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_SYSTEM=/dev/null`, `GIT_CONFIG_GLOBAL=/dev/null`, no prompt, and of agentd's own environment only `PATH`, `LANG`, `LANGUAGE`, `LC_*`, `TZ` and `TMPDIR` (`passes_to_git`). So no `AWS_*`, `AGENTD_*` or `GIT_*` value of the process configures git or can be read by a program a repository setting starts. Before agentd commits, `<repo>/.git/config` and `<repo>/.git/info/attributes` regain their start-of-run content. `workspace::GitState` handles this restoration without following a link: an entry in the place of either file is removed (a link goes, not what it names) and a new file is made with `O_EXCL|O_NOFOLLOW`, `<repo>/.git/info` must be a plain directory, and the files are read back and compared with the snapshot (`GitState::verify`). Git reads its configuration from wherever `.git` points, so `workspace::check_git_dir` runs before every agentd git call on the engine's repository (the helpers that take a `Worktree`, and the restore of an earlier invocation's checkout): `.git` must be the repository's own plain directory, no link, no file naming another directory (`gitdir: <path>`), and no `commondir` or `gitdir` file inside it. Any of those is `WsError::Untrusted`, never repaired. `commit_turn_verified` compares the files again right before `git add -A` (the call that runs clean filters) and before `git commit`. A restore or a commit that fails with `Untrusted` ends the commit and the bundle of the run (no git call, no `bundle`, no upload): a run that would have read "reported done" ends `stopped_other` through `classify::repository_not_trusted` ("Cline stopped: the harness ended the run (agentd did not commit or bundle the checkout: <reason>)"; any other end keeps its label and carries the reason in its error text), and the work is in the checkout and in the last snapshot. No hook, fsmonitor or clean filter written by the engine runs in agentd's commit. No `core.fileMode false` hides a mode change from the commit. Not done: running these git calls inside the engine's Landlock domain. The bundle is written under agentd's own folder, which the domain does not grant, and the snapshot, goal and review modules keep private repositories there; the checks above and the reaper (`src/direct/messages/AGENTS.md`) are what stands between a surviving engine process and a setting written after the restore. Tests: `tests/workspace_redirect.rs`, `tests/workspace_verify.rs`, `tests/direct_invocation.rs` (`a_repository_the_engine_redirected_gets_no_commit_and_no_bundle_from_agentd`), `tests/direct_classify.rs`.
- `workspace::commit_turn_as` commits changes. It runs `git add -A`, then commits `harness: turn N`. The author is `ham agent <agent@harness.invalid>`. After a blank line, the message has `Ham-Role`, `Ham-Agent` and `Ham-Turn` trailers. `workspace::turn_message` builds that message (`tests/turn_commit_identity.rs`). A value outside `[A-Za-z0-9._:/@+-]{1,128}` is left out. It is never rewritten. Trailers are metadata, not proof. A commit is made only when something changed. No commit is made if the engine already committed its work. A run that changed nothing also makes no commit. A path is committed executable if its disk file is executable. An executable stage-0 index entry also makes the path executable. `workspace::apply_staged_exec` runs first to align those modes. The engine's editor writes files 0644. An agent therefore marks a file executable in the index. It uses `git update-index --chmod=+x` or its own commit. `git add -A` alone put the disk mode back. The alignment only adds the executable bit and clears set-ID bits. It skips symlinks, gitlinks and missing files. It skips paths through a symlinked directory or `.git`. It skips files with more than one link. A second name shares the inode, and agentd is root. It also skips hidden paths moved aside by `workspace::hide_paths` this run. Those paths stay in agentd's memory, which the engine cannot write. Engine-user processes can outlive a clean engine exit. Every check therefore uses the handle that is changed. Each directory is opened from the previous directory with `O_NOFOLLOW`. The file is then opened. `fstat` and `fchmod` work on that handle. A name renamed or replaced during the walk leaves its entry alone. `tests/turn_commit_modes.rs` tests the symlinked-directory and hard-link skips. Under the uid split, only files owned by the engine user change. `workspace::set_engine_uid` records that user in agentd's memory. `tests/turn_commit_owner.rs` tests this. A 0755 file stays executable when the index marks it 100644. An agent cannot clear an exec bit on disk.

- Module seam: the pieces that watch or steer a direct run (transcript,
  messages, goal loop, research and context, attachments, skills, continue-from) are modules in their own directories that implement `DirectHook`; the driver calls
  their hooks at fixed points and does nothing else for them. With no module registered every hook call is a no-op that awaits nothing and installs no
  wire tap, and a run is byte for byte what it was before the seam (`tests/direct_golden.rs`). A module cannot fail or hang a run by accident: a panic
  or a time-out switches that module off; only `on_startup` (and `on_restore`) may end a run as "did not start", a `TurnVote::Stop` may end it by
  choice, and the report module may signal the one hard create-only upload conflict after recording it and writing its own report over the foreign object.
  A module can cancel the prompt that is open (`DriverCtl::interrupt`, `acp::Interrupt`): one `session/cancel` per prompt, the answer or the grace running
  out reaches the module's `on_turn_end` with `interrupted` set, and the user's cancel stays final and wins when both are up.
  `on_summary` lets a module add its own members to `summary.json` (`skills`; `research`, the counters of the research lane) after the driver built it and before it is checked and uploaded; it has the
  panic and time-out rules of `on_finalize`, and a module that adds nothing leaves the file as it was (`tests/direct_hooks.rs`, the golden streams).

  placed skill once, at its own file, reading as the file reads (`SKILL.md` is read by the one reader the request is checked with, `harness_protocol::direct::skill_document`); the engine's HOME holds no skills folder and the session starts in the git top level; `summary.json` lists the skills. A request that carries `continueFrom` has the restored `HEAD` checked against the stored head before the engine starts (a second invocation of the same run may also start from a `HEAD` that has the stored head in its history; it runs the engine, and its end sequence then finds the first attempt's bundle and `summary.json` in the bucket and ends as a conflict, see the end sequence below).
- Transcript module: every message of the engine connection is redacted and stored as numbered, write-once gzip objects under `runs/<run>/agents/direct/turns/1/transcript/` (a store that fails never fails the run: the next object opens with a `gap` record), `turn-complete` carries the completeness summary (`transcript`), and one `session.capabilities` agent event is posted per engine session. `AGENTD_TRANSCRIPT=off` switches it off; the other settings are `AGENTD_TRANSCRIPT_*`. - Goal loop: the engine's own goal plugin runs by default. agentd places the pinned plugin and the

The goal plugin itself is not in the repository (it is fetched and bundled at image build, `engine/plugins/AGENTS.md`), so the tests of this module run on a plugin folder made by `tests/common/mod.rs` (`plugin_folder`: stand-in goal files, the tracked observer plugin, a lock computed from both, and a check of the observer's hashes against the tracked `engine/plugins/lock.json`); the plugin's own state machine is checked by `engine/plugins/build/plugin-unit.mjs` in the image build.
- Research module: a loopback HTTP API on `127.0.0.1` (port 3129 or a free one) that the engine reaches through `HAMH_RESEARCH_URL`; every call goes to the stage account's research route with the run's session credentials, and what the route stored (pages, filtered repository archives) is read back, checked against the route's manifest and placed read-only in `<AGENTD_DATA_ROOT>/<run>/direct/context/research/`, outside the work tree. The Tavily key is never in the VM. Settings `AGENTD_RESEARCH_*`. The module never fails a run and logs counts only.
- Provider-fault evidence: `AcpError::Rpc` keeps the JSON-RPC
  `error.data` (the display text `engine error <code>: <message>` is unchanged), and
  `AcpError::fault_hint` maps a failure on the engine transport to `FaultHint`: an RPC `-32603`
  (`transport` `rpc-32603`), an I/O error on the pipes (`io`) or the output closing (`closed`). The
  data supplies `httpStatus` (`statusCode`, `status`, 100 to 599), `retryAfterS` and a name (`errorName`,
  `awsErrorType`, ...: at most 64 characters of `[A-Za-z0-9_.-]`, the part after `#` and before `:`)
  that is `code` and, when it ends in `Exception`, `awsErrorType`; the hint copies only those short facts and none of the engine's
  message text. The error string is another matter: an RPC error's text still reaches the result and the wire as `engine error <code>:
  <message>`, and for a failure on the engine's pipes agentd adds the engine's exit and one scrubbed line of its stderr (the next
  bullet). Other RPC codes (auth -32000, invalid params -32602), a model that was

- The provider retry: when the one `session/prompt` ends in a JSON-RPC internal error (-32603) the engine is still alive, so agentd sends one fixed sentence (`RESUME_PROMPT`: "A previous attempt on this work tree was interrupted by a provider failure.   more try is worth its small cost) gets 1; `never` (the provider's content filter blocked the answer, the output or context limit was hit, a closed pipe, auth, any error that is not -32603) gets none and ends the run.   run at the first such stop; it is 0 whenever `AGENTD_DIRECT_PROVIDER_RETRIES` is 0) on the same route and model, with the sentence `RESUME_PROMPT_INTERRUPTED` ("A previous attempt on this work tree was interrupted.   `session/prompt`) and `engine_stop` names the shape: `loop-guard` (5 or more identical calls in a row), `mistake-limit` (6 or more failed calls in a row) or `unexplained`. (5 identical tool calls in a row); the model was not changed") and the log line; it changes nothing else, except for one case: an unexplained stop of an attempt that completed no tool call and ended less than 120 s after the prompt could be a provider fault that showed no output, so a
  run with failover routes and a probe asks the route once (`BedrockProbe`); only a route that does not answer (`Down`) makes it a `transient` provider failure (resumes, then the ladder), and an answer or a refusal leaves it an engine stop (a run with one route has no probe). `engine_stop::StopReport`

The grammar is the self-check script's too: `fixtures/lifecycle/records-locator.json` holds the cases `tests/direct_records.rs` and `scripts/tests/test_lifecycle_check.py` both read. The module writes nothing and logs nothing. `src/direct/records.rs` chooses the records folder once per run during repository restoration at `mod.rs` step 4a, after work-tree preparation. `records::choose` selects `.cah` when only `.cah` holds state. It selects `.ham` otherwise. State is a regular file
  named `records` or `test-command` directly in the folder, or a regular file at any depth under `lifecycle/`, `research/` or `context/` (the definition of `baseCases` in `fixtures/lifecycle/records-locator.json`, which `tests/direct_records.rs` and the self-check script of the lifecycle pack both answer). The search inspects at most 5,000 entries and 16 levels. Links and empty folders do not count as state. An empty `.ham` does not hide a populated `.cah`. State in both folders produces `Records::Conflict` with text naming both folders. The run ends as “did not start” before any model call. A `.cah` run uses `.cah/records` as its locator. Without a locator, its records reside in `.cah/lifecycle`, `.cah/research`, and `.cah/context`. `records::prompt_line` prefixes its first prompt with `Records folder of this run: .cah (this repository keeps its lifecycle records there; where the rules, skills and tools say .ham, use .cah).`. A blank line separates that line from the user's text as typed. A `.ham` run or a run with neither folder receives the user's text as typed. The report plan reads `.ham/test-command` with fallback `.cah/test-command` through `records::TEST_COMMAND_FILES`. Review facts treat `.cah` like `.ham`. The default goal text names the chosen folder through `goal::settings::goal_text_in`; a goal text the user wrote stays as written. `observe::last_log_observation_for` uses the folder chosen at run start for the final observation and reads its locator again, because the engine may write the locator during the run. `COMPAT-CAH-DATA` ends at VERSION 6.00. Tests are in `tests/direct_records.rs`, `direct_records_run.rs`, `direct_observe.rs`, `direct_goal_tree.rs`, `direct_goal_settings.rs`, `direct_report_plan.rs`, and `direct_review.rs`.
- The snapshot (`snapshot`): every `snapshotEveryS` seconds (default 600; 0 is off) while the prompt runs and the tree changed, a
  bare repository of agentd's own (`<agent data>/snapshot.git`, root, 0700, the engine's object store as an alternate) takes
  `git add -A` (its index seeded with the base tree, so a file tracked at the base that an ignore rule now matches is not a deletion),
  `write-tree`, `commit-tree` on the repository's HEAD, the `snapshot` branch ref and a bundle, uploaded to
  `snapshot.bundle` then `snapshot.json` under `runs/<run>/agents/direct/turns/1/`. It never writes the engine's index, HEAD, refs or objects. A failed snapshot is
  counted (`snapshots.failures`) and never ends the turn. The engine-controlled exclude file of the repository is read only as a regular file of at most 1 MiB,
  opened without following a link and without blocking (a FIFO or a link there is ignored). The nudge's change test uses the same kind
  of private repository (`ScratchRepo`, `probe.git`): it hashes the work tree's content, because `git status` does not change when a
  modified file is edited again.
- The user correction path, pure part: no I/O and no clock of its own. `reason_of` and
  `assess` turn the stop one stage ended with (`Classified`, plus `AssessFacts`, which the driver builds from `engine_stop::StageFacts`, the collector and the tree) into
  `Finish`, `Auto` (the one automatic fresh session, for `replay_rejected`, `context_full` and a dead engine; never for `engine_stop`) or `Ask` (one of 13 blocking reasons, its
  options, the routes `try_model` may name, `canContinue` and the window `min(wait, time left - 900 s)`; no question opens when less than 300 s are left after that margin, and a user's wait of 1 to 299 s is honoured as it is). `InputPolicy` carries the limits (3 questions, 1
  automatic and 3 requested fresh sessions; a wait of zero never asks, the server default). `Window` is the open question: `offer` checks id, answered, expiry (monotonic, closed at
  the instant), the cancel of the same batch, the action offered, the model among the routes, the text (some text of at most 262,144 bytes) and the session cap, and the first
  acceptable answer wins. `digest` builds the notes of a stop from harness facts only, in nine sections with their own caps, whole sections dropped from the end to fit 200,000 bytes (the user's task is whole in section 1 and outside that budget);
  `new_session_prompt` writes the text a fresh session starts from (the user's words verbatim, the inline summary a prefix of the notes in a fence longer than any backtick run in it,
  the slot for an analyzer's paragraph empty). `needs_input_payload` and `outage_notice_payload` build the event bodies through the protocol's size bound. Reasons are facts about
  how a stop looked and never say whether the work is good. The words that name the engine live in `src/engine/direct_words.rs`, so `input.rs` names no engine.
- The stage loop of the direct driver.
  `run_direct_prompt` keeps its signature and calls the loop with `input: None` and a host
  that cannot restart the engine (`NoRespawn`): one stage, no remedy, no question. A served run (`mod.rs` `input_wiring`) always has the loop; with no wait asked for (`inputWaitS`
  0, the server default) its policy waits zero, so it never asks, but the automatic remedies run (one fresh session for a refused history or a dead engine, one resume of a silence).
  The first stage is setup (`initialize`,
  `session/new`, the model pin) and the user's prompt byte for byte. A later stage is `Stage::Prompt` (the user's continue text, attempt kind `instruction`),
  `Stage::TryModel` (`set_model`, a `DirectSwitch` of class `user`, then the text or the fixed resume sentence), `Stage::FreshSession` (attempt kind `fresh_session`) or
  `Stage::Resume` (the one resume of a silence: the driver has written `session/cancel` at the stall, `settle_after_cancel` reads the pipe until it is quiet, the fixed
  sentence goes to the same session as an attempt of kind `resume`; the stalled try is listed with retry class `silence`; the count is run-wide, `SILENCE_RESUMES`, so the
  second silence asks `silence`);
  each begins with `Activity::reset_for_stage` and `FailoverRecord::begin_stage`. One absolute deadline covers the whole run: every stage is watched for what is left of
  `plan.timeout`, a person's wait is inside it, and the silence clock is held during a wait (`Activity::hold`); the longest silence of any stage is `max_silent_gap_s`.
  When a stage ends, the end is classified and refined as the end sequence does (the delivered tree through `TreeSource`, the engine's own stop through
  `refine_engine_stop`), then `input::assess` decides: finish, an automatic fresh session, or a question. `Machine::stage_facts` is the one place that maps the stage's facts
  (`FailoverRecord.stage`, the collector's counts, the tree) into `AssessFacts`; an error answer to the prompt counts as an answered prompt, so the person may continue
  after `replay_rejected`, `context_full`, `provider_error` and `cap_hit`. The automatic paths (class 4, a dead engine) and these triggers are pinned in
  `tests/direct_input_triggers.rs`. A question is a `needs-input` event whose id is the request id
  (`EventRecorder::record_urgent_with_id`), then `waiting::wait_for_answer`: one `select!` over the instruction channel, the user's cancel, the engine's pipe
  (`AcpClient::pump_idle`) and the window's expiry, with the cancel looked at first so it wins against an answer of the same batch. `Window::offer` decides what an
  answer is worth; the driver writes `input-received` or `input-ignored` and `input-closed` (finish, expired, cancelled, deadline, superseded). An engine that dies
  during the wait supersedes the question and the stop is assessed again as `engine_died`. Nobody answering or a chosen finish ends the run with the held stop and a
  lead sentence (`DriverEnd.input_note`); the user's cancel ends it as `stopped_by_user`. A fresh session (`fresh::start`) is a `session/new` in the live process with
  no second `initialize`; the engine process is stopped and started again (`Respawn`, implemented by `EngineHost` in `mod.rs` over the same `LaunchSpec`) only when the
  pipe is closed, the engine stalled, or `FRESH_SESSION_RESTARTS_PROCESS` says so. It never uses `session/set_config_option` and never excludes a
  route; it names the session to the client (`AcpClient::set_session`) so events of an abandoned session are dropped, and the context files and the digest are written
  before its first prompt. A fresh session that cannot start ends the stage as a dead engine; the next assessment may ask again or finish with `A fresh session could
  not start.` `DriverEnd` gains `interventions`, `fresh_sessions`, `input_note` and `engine_stop`; `usage` is the sum over all sessions (`UsageTally`: what each
  answered prompt reported, and a figure streamed by the session before is not credited to the new one). `mod.rs` builds the wiring (`input_wiring`) only when a wait is
  asked for (the request's `inputWaitS`, else `AGENTD_DIRECT_INPUT_WAIT_S`) and the instruction channel is free. The digest of EVERY stop, with or without a window, is the recorder's
  `collector.stop_digest(n, ctx)` (at most 256 KiB, redacted at write time), uploaded as `stop-digest-<n>.json` under `runs/<run>/agents/direct/turns/1/` through the host's
  `AuditSink` (`Respawn::audit`, `S3Audit`; a failed or slow upload is logged and never stops the run, 30 s at most); `direct::audit_key` is the protocol's key. The work tree
  is measured through `VisibleTree` (A3b's `GitSource` less the paths agentd moved aside at launch, which are put back before the end commit and are no change of the work). A
  second delivery of an answer, or an answer for a closed question, is acknowledged `input-ignored` (`already-answered`, `unknown-request`). Event texts that name the engine
  take the name from `engine::direct::engine_label`.
- The git facts of a stop: `ScratchRepo::facts` opens `<agent data>/facts.git` (root, 0700, the engine's objects as an alternate,
  its index seeded with the base tree, its own repository so the nudge's `probe.git` fingerprint never moves) and `git_facts(base, head)` returns the
  changed paths with their total, the diff stat, the commits since the base and the head of `PROGRESS.md` (a regular file at the top of the work tree,
  read like the exclude file). `changed_paths`, `log_since`, `diff_stat` and `tree_of` take object ids only (7 to 64 hexadecimal digits, never a ref
  or an option), run from agentd's own directory with `GIT_DIR` set, never in the engine's repository, and return bounded, scrubbed text; one caller at a time.
  `GitSource` is the real `direct::input::TreeSource` over it (unknown, never zero, when the tree cannot be measured) and the git half of the digest sources
  (`facts()` reads the engine's `HEAD` with the one `git rev-parse HEAD` agentd already runs for the snapshot and the nudge; `GitFacts::fill` writes only the
  git members of `DigestSources`); it serializes its callers.
- The context directory: `<agent data>/context/`, made by agentd (root, 0755), outside the work tree so outside the end commit, the
  snapshots, the zip and the pull request. `task.md` (the original prompt, byte for byte) and `fresh-session-<n>.md` (the digest, at most 200,000
  bytes besides the task) are written atomically with mode 0644: the engine reads them and cannot change them. A link or a file where the directory belongs is refused.
  The audit copy goes to `runs/<run>/agents/direct/turns/1/fresh-session-<n>.md` (`upload_audit_copy`, three retries) and is not delivered.
- `summary`: `UsageSum` adds the final usage of each ended Cline session to the running one (`None` only when no session reported any), and
  `input_sentence` words the lead sentences of a run that waited for the user (`You chose to finish.`, `Nobody answered in <n> min, so the run
  finished with what exists.`, `A fresh session could not start.`).
- `summary`: `UsageSum::add_prompt(prompt, usage)` sums the usage of every prompt that answered, over all stages and sessions (the engine reports
  usage per prompt; a prompt number is counted once, so a late response is not added twice; `None` only when no prompt reported any). `build_summary_with`
  adds `SummaryExtras` to `summary.json`: the last eight `interventions` and `freshSessions` (the user's text is never in them) and the lead sentences of a run
  that waited (`input_sentence`: `You chose to finish.`, `Nobody answered in <n> min, so the run finished with what exists.`, `A fresh session could not start.`),
  placed after `Ran on ...` and `Every route was down ...` and before the classifier's cause. `build_summary` is unchanged for a run that never waited.
- Settings (`config::DirectConfig`): `AGENTD_DISABLED_TOOLS`, `AGENTD_DIRECT_PROVIDER_RETRIES` and `AGENTD_DIRECT_RETRY_PAUSE_MS` (the provider retry

  `AGENTD_DIRECT_SNAPSHOT_EVERY_MS`. The input settings (all optional; a bad value is the default, above a maximum is the maximum): `AGENTD_DIRECT_INPUT_WAIT_S` (default 0 = never wait, at most 14400; the request's `inputWaitS` replaces it), `AGENTD_DIRECT_INPUT_MAX_REQUESTS` (3, at most 8, 0 never asks), `AGENTD_DIRECT_INPUT_MARGIN_S` (900, at most 3600), `AGENTD_DIRECT_INPUT_MIN_WINDOW_S` (300, 1 to 3600), `AGENTD_DIRECT_AUTO_SESSIONS_MAX` (1, at most 3), `AGENTD_DIRECT_USER_SESSIONS_MAX` (3, at most 8) and `AGENTD_DIRECT_OUTAGE_NOTICE_S` (1800, 1 to 86400). Engine-specific parts of the direct

# crates/agentd/src/direct

## Purpose

The source of the direct driver, and the seam through which independent modules watch or steer a run without editing the driver. The driver's own contracts are in
`crates/agentd/AGENTS.md` (startup, the prompt, the stop table, the retry and failover ladder, the answer window, the end sequence).

## Ownership

Owned by `crates/agentd/AGENTS.md`. Two kinds of files:

- Driver files: `mod.rs`, `driver.rs`, `collector.rs`, `fresh.rs`, `retry.rs`, `classify.rs`, `request.rs`, `hooks.rs`, `review.rs` here, and `acp.rs` and
  `events.rs` one level up. A module branch edits none of them. A module that needs a driver change writes it in its report with the exact proposal.
- `flow.rs`: `of_run` reads the flow the run declared (`DirectFlow`: `quick`, `full`, or `none`) at the end of the run, before the harness makes its own commit: the `Flow:` trailer of the message of the commit the engine left last (`workspace::commit_message`; the commit the run started from is not one), else the first line of the engine's last message. `mod.rs` sets `summary.flow` from it when the checkout can be trusted, and leaves it out otherwise. It is a fact beside the label; nothing in agentd reads it (`crates/agentd/tests/direct_flow.rs`, with a real repository and the in-process driver whose engine wrapper commits with `WRAP_COMMIT_MESSAGE`).
- `dox.rs`: the DOX starter written and committed before the first prompt, and the base of the run's work (`starter`, `bans`, `is_off`, `settle`, `Request`, `Settled`, `Why`, `SEED_SUBJECT`); `mod.rs` calls `settle` once in step 4 of `start_and_prompt`, between the check of the restored head and the read of the base, and logs its note (`crates/agentd/AGENTS.md`, "DOX starter"). The module reads only the request's `skills` and `prompt`; it adds no hook, no event and no summary member.
- `cargo.rs`: the engine's cargo settings (`home_dir`, `place_config`, `build_env` and `build_env_with` (the request's `build` member turns off the debug-information and incremental defaults), `DEFAULT_JOBS`, `MAX_JOBS`, and the target folder on the root volume: `TargetSetting`, `target_dir`, `place_target_dir`); `mod.rs` calls it in the package-proxy step of the startup and where the engine's
  environment is assembled (`crates/agentd/AGENTS.md`, "Cargo in a direct run").
- `disk.rs`: the session's two disks and a test write (`Reading` with `writable`, `DiskProbe` with `diagnose`, `HostDisk` with `with_write_dirs`, `test_write`, `Limits` with `engine_fault`, `DiskFull`, `Signal` with `signal_of` and `signal_of_error` for the engine's error text, `DiskCheck`, `DiskWatch`); `retry.rs` measures with it (`RetryPolicy::with_disk`, `disk_boundary`), `classify.rs` maps its cause (`with_disk`), `input.rs` words the question (`reason_word`, `needs_input_payload_for`), and `mod.rs` builds the real check
  (`crates/agentd/AGENTS.md`, "Session disks").
- `local_fault.rs`: telling a fault of the machine from a fault of the provider (`bare_internal_error`, `Tally`): one walk over the routes in which every route answered its small test request and then refused the switch with the engine's bare `-32603 Internal error` ends the run (`crates/agentd/AGENTS.md`, "Session disks" (g)).
- `prune.rs`: the look that prunes stale cargo output while a prompt runs (`PruneSettings`, `FreeProbe`, `StatvfsFree`, `prune_target`, `tick`, `notice`, `start`, `PruneTask`); `mod.rs` starts it in `start_prune` and stops it with the stage loop (`crates/agentd/AGENTS.md`, "Session disks", item (f)).
- Module directories, one owner each: `transcript/`, `messages/`, `goal/`, `research/` (with `research/context.rs`), `attachments/`, `engine_config/`, `skills/`, `continue_from/`, `tools/`. A module branch edits its directory, its tests (`crates/agentd/tests/direct_<module>*.rs`), its section of the table below, and the crates its issue names (`harness-protocol` with its
  version bump and frozen line, `worker-api`, `control-api`, `ham-core`, `infra`). Two named exceptions: `skills` adds its member to `request.rs` (parse and validate), and `research` extends `context.rs` (the existing context directory of the fresh session) without changing a signature or a test of it. The `report` module is a seventh directory under the same rule; it adds one
  `pub mod report;` line to `mod.rs` and one line to `Hooks::standard` (after `continue_from`, before `messages`), and nothing else of a driver file. The `engine_config` module is the ninth directory. The `tools` module is the tenth.

## Local Contracts

### The seam (`hooks.rs`)

- A module implements `DirectHook` (every method has a no-op default) and returns itself from `pub fn hook(env: &HookEnv) ->
  Option<Arc<dyn DirectHook>>` in its `mod.rs`; the stub returns `None`. `Hooks::standard(&HookEnv)` calls the constructors in the order
  `transcript, goal, research, tools, attachments, engine_config, skills, continue_from, report, messages` and is not edited by module branches.
  `Hooks::standard_with(&HookEnv, GoalSettings)` is the same list with the goal settings given (the goal module is the one that needs a folder of the host); `standard_with_tools(&HookEnv, GoalSettings, tools::settings::Settings)` also takes the tool server's settings as a value, because the kill switch `AGENTD_TOOLS_MODE` is an environment variable that a test cannot set (`unsafe_code` is forbidden); `standard` is `standard_with` over the environment, so there is one list.
  `crates/agentd/tests/direct_hooks_standard.rs` pins the order of all ten modules, the order of the nine when the goal loop is off, that `tools` follows `research` and precedes `engine_config`, and that `messages` is last. `Deps.hooks: Option<Hooks>` replaces the
  set in tests (`Hooks::new(vec![..])`). `Hooks::none()` is the empty set: every call returns at once, awaits nothing, and no wire tap is
  installed, so a run with no module is the driver as it was (`crates/agentd/tests/direct_golden.rs` pins 13 scenarios byte for byte).
- Hook points, in the order of a run (the table of `hooks.rs` has the same rows):

  | method | when | arguments (borrowed) | may change |
  |---|---|---|---|
  | `on_restore` (async) | after `request.json` is parsed, before the bundle is fetched | `RestoreCtx { env, request, repo_uri: &mut String }` | the bundle URI |
  | `on_startup` (async) | rules placed, configuration directory root-owned, credential socket up, before the rules preflight | `StartupCtx { env, request, repo, config_dir, data_dir, home, tmp, engine_uid, sandbox (the run's Landlock `Option<Sandbox>`, `None` in the `uid` mode), engine_env: &mut, session_cwd: &mut Option<String>, mcp() (the profile's `[mcp]` table), launch_spec(argv, stderr_name), clean_launch(), clean_spec(argv, stderr_name), engine_argv() }` | engine environment, session directory; an `Err` ends the run before any model call |
  | `on_wire` (sync) | every JSON-RPC message of the engine connection after it was written (agentd to engine) or read and parsed (engine to agentd), before agentd acts on it | `Wire { seq, dir, msg: &Value, stale }` | nothing |
  | `on_event` (sync) | see the next list | `Event` | nothing |
  | `on_controls` (sync) | `TurnControls::deliver`, every batch from the internal API, all kinds | `&[PendingControl]` | nothing |
  | `on_turn_end` (async) | a prompt with its retries ended; the prompt was answered (or a module's interrupt was, or ran out of grace), nothing failed before it, the user's cancel is not up, time is left | `TurnEnd { n, session_id, session, raw, classified, files_changed, interrupted, time_left, tool_calls }` | `TurnVote` (also `Wait`: the hold) |
  | `on_seal` (async) | after the answer window and the automatic remedies also finish the run; same conditions | `TurnEnd` | `TurnVote` |
  | `on_shutdown` (async) | start of the end sequence: the engine is gone, nothing is committed or uploaded yet; EVERY ending | `Shutdown { env, classified }` | nothing |
  | `on_summary` (async) | `summary.json` is built, after `on_shutdown`, before the summary is checked and uploaded; EVERY ending | `SummaryCtx { env, classified, summary: &mut DirectSummary }` | the summary (a module adds its own members: `skills`; `build_summary` sets `engine_config` to `None`, only a module's `on_summary` sets it, and a run without engine settings has none) |
  | `on_report` (async) | the delivered head is committed, bundled and uploaded and `summary.json` is in the bucket; the package proxy, the container runtime and the flusher (the heartbeat) still run; only when a head was delivered and the run did not end by the user's cancel or its deadline. A module that needs more than `Limits::report` says so through `DirectHook::report_time`; the driver grants it up to the run's deadline (`hooks::report_ceiling`) | `Report { env, classified, head_sha, bundle, bundle_uri, time_left }` | the report artifact; a refused create-only upload signals the driver after the module records its conflict event |
  | `on_finalize` (async) | just before `turn-complete` is posted; EVERY ending | `Finalize { env, classified, complete: &mut TurnCompleteRequest }` | the `turn-complete` request |

- **The sandbox is part of the context.** In the `landlock` mode the engine runs in a Landlock domain (`crates/agentd/src/sandbox/AGENTS.md`), and `StartupCtx.sandbox` carries it. Every `LaunchSpec` of the engine family (the engine, the rules listing, a tool's child, a report step) is built from `ctx.launch_spec`, `ctx.clean_launch()` or `ctx.clean_spec`, or by the driver and the report from the same `Sandbox`, so it inherits the sandbox: a module never writes `sandbox: None` for such a process. A launch with a sandbox and a `run_as` together is refused. `crates/agentd/tests/sandbox_seam.rs` scans the sources for `sandbox: None` (three places, each with its reason), for a `CleanLaunch` built outside the context and for a `LaunchSpec` literal that names no sandbox.

- Events (`Event`): `SessionStarted { session_id, number, response (the `session/new` result), cwd, trigger }` after the engine took the pinned
  model (first session and each fresh session); `SessionEnded { session_id, number, why: Replaced | RunEnded }`; `PromptSent { no, session_id, text }`
  and `PromptReplied { no, session_id, stop_reason, usage, error }` around every `session/prompt` (the user's prompt, retries, resumes, nudges and
  voted prompts); `Ladder(..)` from the functions that record the recovery ladder (`ProviderRetry`, `Switch`, `EngineStop`, `Wait`, `Outage`,
  `OutageNotice`, `OutageRecovered`, `Notify`, `SilenceResume`); `Cancel { session_id }` after a `session/cancel` agentd wrote was seen on the wire;
  `EngineStopped(Reaped | Restarted)` after the engine's process group was killed (tool processes the engine started in their own session
  survive it: that is the moment to reap them); `RunEnded` after `result.json` is written.
- Votes (`TurnVote`): `Done` (no opinion, today's behaviour), `Prompt(text)` (send as the next prompt in the same session, attempt kind
  `instruction`, then ask again), `Stop { detail }`,
  `Wait { until }`
  (the engine is still working by itself, so the run must not end: see "The hold" below).
  Modules are asked in registration order. A `Stop` ends the poll at once and later modules are not asked. A `Prompt` is kept and a later `Prompt`
  replaces it, so the LAST module has priority among prompts; that is why `messages` is registered last: a pending user message wins over
  another module's continuation, and a brake (`Stop`) of an earlier module is final before `messages` claims anything. `on_seal` follows the same rule
  and runs only when `on_turn_end` voted `Done` and the rest of the driver finished the run; a `Prompt` there continues the run, which is how a
  message that arrived at the last moment is delivered. A vote that returns after the user's cancel or the deadline is dropped.
- Failure rules (enforced by `Hooks`): a panic in any hook switches that module off for the rest of the run with one log line
  (`direct module <name> disabled: ...`); an asynchronous hook that does not answer within `Limits` (startup 60 s, restore 60 s, decision 120 s,
  shutdown 15 s, summary and finalize 15 s (one limit for both), report 480 s) is cut off and switched off and its vote counts as `Done`; `on_startup` and `on_restore` are the exceptions: an
  `Err`, a panic or a timeout there ends the run as `stopped_setup_failed` (the "did not start" row) before any model call, with the module's own words
  or `module <name> panicked in on_startup`. A module whose startup is optional returns `Ok` after logging. `on_wire` and `on_event` run on
  the read path: copy and queue, never wait. Nothing a module does may print a secret: the wire is raw, a module redacts before it stores. `HookEnv.secrets` is the run's `SecretSet`: the goal loop passes the text and the fields of its events through it, and the transcript writer follows it (`Writer::follow_secrets`), so a value that a refresh minted a moment ago, or one the writer's own keeper never reads (the refresh nonce, the package token), is hidden from the next message on. `classify::redact_known` replaces the longest value first. `DigestSources` prints the count of its secrets and never a value with `Debug`. Tests: `crates/agentd/tests/b592_secret_reach.rs`, `crates/agentd/tests/b592_transcript_secrets.rs`.
- The wire sequence `Wire.seq` counts every message of the run from 1 across sessions, restarts and stale lines, without a gap; `Wire.stale` marks
  a message of an abandoned session. A stdout line that is not JSON-RPC is not a message and is not seen. A write that failed is not seen.
- Every module reads its settings from `AGENTD_<MODULE>_*` environment variables (`config.rs` is not edited) and takes everything else from
  `HookEnv` (run id, region, bucket, internal API URL, data directory, `Config`, the credentials store, the event recorder, the log, the controls).
  A module that calls S3 or the internal API uses the run's own session credentials (`env.creds`); a module that writes under `config_dir` writes as
  root, files 0444 and directories 0555.
- No engine product name appears in `crates/agentd/src` outside `crates/agentd/src/engine/` (`crates/agentd/tests/engine_neutral.rs` scans every file under `src`, this one
  included): a module says "the engine" and gets anything engine-specific from `crates/agentd/src/engine/`.
- Every file here is an input of the worker image key (agentd, `harness-protocol`, `pkgproxy`).

### The engine_config module

The optional `engineConfig` member of the stored start request (`EngineConfig {engine, schema, settings}`) holds the user's settings for the engine as typed values; `ham` reads them from `~/.config/ham/engines/<engine>.toml`. A run with no member is the run it was: the 13 golden streams of `direct_golden.rs` are unchanged by this module, and no argument, variable, provider-file key, event, summary member or log line is added.

- Check: `request::engine_settings(start, engine)` calls `harness_protocol::direct::check_engine_config` (the one check that `ham` and control-api also call) right after the rules check, before anything is placed, and returns `engine::user_settings::UserSettings`. A refusal ends the run `stopped_setup_failed` ("did not start") before any model call, with the key and the rule and never the value. A member for another engine than the run's is refused too ("the settings are for another engine"): settings that are set and never applied are not allowed.
- Typed values: `crates/agentd/src/engine/user_settings.rs` holds the engine's words. `UserSettings` is `Effort`, `CommandSeconds` (1 to 1,800; only `CommandSeconds::new` makes one), `CompactionMode`, `Trigger` (finite, 0.10 to 0.99; only `Trigger::new` makes one) and a list of `UserTool` (a closed set; `name()` is a static text). No user string is kept or written: every value is an enum member or a number.
- Placement, in the order of the startup: `EmitContext.compaction` (a `CompactionBlock`) makes `engine::config::emit_cline` write `settings.compaction` of `providers.json` through `serde_json::json!` over typed values (`enabled` true for `agentic` and `basic`, false for `off`; `strategy` `agentic` or `basic`; `thresholdRatio` a number), only the keys the user set, and the required `updatedAt` datetime stays; with none the file is byte for byte as before. `engine::direct::direct_launch_argv(engine, argv, effort)` appends `--thinking <level>` at the end unless the level is `default`, and replaces a level the profile already names, so the flag is named once. `engine::direct::launch_env` adds `CLINE_RUN_COMMANDS_TIMEOUT_MS` (seconds times 1,000, checked; the engine's own range is 1,000 to 1,800,000 ms). `UserSettings::disabled_tools(stage)` is the stage's `AGENTD_DISABLED_TOOLS` list as it is, then the user's tools it does not name, in the key table's order; `lock_global_settings` receives that union and its body is unchanged, so `telemetryOptOut` true, `autoUpdateEnabled` false and the tool list are written last and a user cannot remove a stage entry. `emit::render` (raw text into a template) is never used for these values.
- `on_startup` (after the configuration directory became root's): with no member, or a member that sets no key, it does nothing. Otherwise it checks the member again and calls `engine::user_settings::read_back`, which reads the `--thinking` argument, the command time limit variable (only what the user set; a stage may set its own default), `providers.json` (`updatedAt` present and `settings.compaction` equal to what was meant, or absent) and the locked `global-settings.json` that `CLINE_GLOBAL_SETTINGS_PATH` names (the two locked keys and the union of the tools). A mismatch ends the run `stopped_setup_failed` before the first model call and names the part ("the provider file", "the locked global settings", "the engine's environment", "the engine's launch"), never a value. Read-back proves agentd wrote what it meant; that the engine accepted it is proven by the probe records of the key table's admission rule.
- Event and summary, only after the read-back compared equal: one `turn.progress` event of kind `engine-config` with `turn`, `kind`, `engine`, `sha256` (`EngineConfig::canonical_sha256`, the settings hash), `keys` (the count), `settings` (a list of `{key, value}` in the key table's order, at most 24, each value a text of at most 64 characters, lists joined by commas; entries are dropped from the end to keep the payload within 4,096 bytes) and `readBack: "ok"`, and one log line `direct engine settings placed: N key(s), read back ok`. `on_summary` sets `DirectSummary.engineConfig` (`EngineConfig::to_ref`: engine, schema, `sha256`, `keys`; never a value). "Placed" is the word: agentd wrote the value where the engine reads it.
- Tests: `crates/agentd/tests/direct_engine_config.rs` (whole runs), `direct_engine_config_hook.rs` (a module in front of this one edits the files between the write and the read-back) and `engine_user_settings.rs` (the typed settings, the argument, the variable, the compaction block, the union, an enumerated property over 1,080 accepted documents, `request::engine_settings`, `read_back`); `direct_hooks_standard.rs`, `direct_launch.rs` and `emit.rs` follow the new module, argument and field.
- Every file of this module is an input of the worker image key; the package does not run `scripts/image-key-guard.sh --update`.

### The review round

After the engine ends a turn with a message and the harness counted a changed file, the stage loop sends ONE more prompt in the same session: the user's review prompt (`review.md`), which asks the engine to review its own delivery as the maintainer who must merge it. It is a driver feature and not a module of the seam, because the loop must put the outcome of the turn before the round back when the round fails.

- Plan: `InputWiring.review` (`ReviewPlan {mode, text, guard, base, repo}`), made in `mod.rs` from the request's `review` member (`ReviewOptions`; `review::check_member` checks it again with `check_review` before anything is placed) laid over the stage settings `AGENTD_DIRECT_REVIEW_ROUND` (default on; `0`, `off`, `false` and `no` switch the round off for every run: a request cannot switch on what the stage switched off) and `AGENTD_DIRECT_REVIEW_GUARD_S` (default 1200, 60 to 28,800; the request's `guardS` replaces it). A request with no member means the built-in prompt (`DEFAULT_REVIEW_PROMPT` of the protocol) and `auto`. A run with no stage loop has no plan and records nothing.
- Rule (`review::skip_reason`, pure): the first that applies is the reason, in this order: `off`; `forced_stop` (a module voted `Stop`, the goal loop's brake); `not_done` (the last turn is not "reported done": no message, a stop for length or refusal, a failure); `blocked` (a line of the message starts with `BLOCKED:`); `question` (the last line that holds text ends with `?`, a heuristic on the shape of the message); `files_unknown` (the harness could not count the changed files) or `no_changed_file`; `no_time` (less of the run's deadline is left than the guard). These are the `reason` words of `DirectReview`.
- Where: in `run_direct_stages`, after the seal consult found nothing to send. The prompt goes out as `Stage::Prompt` through the ordinary `send_and_nudge`, so retries, failover and the nudge apply to it. The round's stage is judged when it ends (`end_round`), before the modules and the answer window are asked; neither is asked about it, so a failed round never becomes a question for the user; the seal consult then runs again (a late user message is still delivered); the round never repeats (`round_ran`). A skipped round is recorded after the loop from how the run ended.
- Outcome: a round whose turn ends with a message is the run's last turn, and its message is the run's last message. Any other end (provider error, engine death or stall, the deadline, no message, length, refusal) puts back the turn before the round (a `RawEnd` rebuilt from its `PromptDone` and message), so the run ends with the outcome it would have had without the round. The user's cancel is the exception: the run ends as the user's stop (`result` `cancelled`). The label "reported done" still needs a message and a changed file at the end.
- Prompt: the template with `{{base}}` (the commit the run started from) and `{{facts}}` (`review::facts_text`: the changed files, the new top-level folders, the files under `.ham` and the untracked files, one dashed line each; paths are cleaned to one line and lists are cut with "and N more"), filled in one pass (`review::render`), so text that was put in is never read for a token again. The git reads (`GitRepo`) are `rev-parse HEAD`, `ls-tree --name-only -z <base>` and `ls-files --others --exclude-standard -z`; none of them hashes file content, so no filter the engine wrote can run.
- Evidence: `DirectSummary.review` (`DirectReview`: `status` `ran` or `skipped`, `reason`, `commitBefore`, `commitAfter`, `changedFiles` (the work-tree fingerprint differs), `seconds`, `inputTokens` and `outputTokens` (only when the engine reported a change in usage) and `result` `completed`, `failed` or `cancelled`), set by `mod.rs` once the summary is built; EVIDENCE.md prints `DirectReview::sentence()` under "Review round". Two `turn.progress` events of kind `review-round` (phase `start` and `end`) tell the card.
- Tests: `crates/agentd/tests/direct_review.rs` (scripted engine, paused clock, the pure rules). Every file of the round is an input of the worker image key.

### skills and continue_from

Both read their member of the stored start request (`harness_protocol::direct::StartDirectRunRequest.skills` and `.continue_from`), act in `on_startup`
and end the run `stopped_setup_failed` ("did not start") before any model call when a check fails. A request that carries neither does nothing in either module,
except that the skills module also runs steps 1 below in every run. Neither writes to the prompt: the engine receives the user's text as typed (invariant 1).

- `skills` (`skills/mod.rs`; switch `AGENTD_SKILLS_ENABLED=0`, which refuses a request that carries skills instead of ignoring them; bound `AGENTD_SKILLS_LISTING_TIMEOUT_S`, 20 s,
  at most 25 s, because two listings run inside the 60 s startup limit). In order:
  1. `home::clear_home_skills`: `$HOME/.agents/skills` is removed (the engine reads it; a link is unlinked and never followed; nothing else in HOME is touched), and
     `cwd::top_level` sets the session directory to `git rev-parse --show-toplevel` (below it the engine's skills still load but AGENTS.md and rule files vanish).
  2. With no skills the module stops here.
  3. The shared validator `harness_protocol::direct::check_skills` (the one `ham` and control-api call) through `request::check_skills_member`, then `place::skill_document` for each
     SKILL.md, which is `harness_protocol::direct::skill_document`, the one reader of the request and of this module (frontmatter name equal to the folder, a description of at most
     1,024 characters, a non-empty body, the documented subset of YAML; the pinned engine lists only a file named exactly `SKILL.md`, not one with an empty body, and under the
     frontmatter name). A text the validator accepted at the request is accepted here.
  4. `place::retire_placed` removes the skill folders an earlier attempt of this run placed (a real directory that holds the marker file `.agentd-placed`; a link is never followed), so a second
     invocation of the same run on the same VM starts from what the first one found. Then the engine's own listing (`config skills --json --config DIR` of the engine's binary,
     `engine::direct::skills_listing_argv`) before anything is placed: a repository skill, or one of another module in the skills directory (the research module places its context there), with the name of a
     requested one stops the run (refuse, so one input fails the same way every time; the configuration directory would win silently), and so does a skill loaded from
     outside the repository that is not inside the skills directory (a link out of the repository counts as outside): `preflight::check_repo_skills_in`.
  5. `place::place_skills` writes `<config dir>/skills/<name>/...` as root, files 0444 in directories 0555, the exact bytes the client sent (the request's hash and size are
     checked again), and in each folder the marker file `.agentd-placed` (written first, 0444, naming the digest): agentd owns the folders that hold it and nothing else under the skills directory. A folder of
     a requested name that agentd did not place is refused ("already there") before the first file is written and is never deleted; other content keeps its files and modes, and a skills

### The clean-checkout test report

- Go counts and the rows of the log: gotestsum prints no `--- PASS:` line in its default format, only `DONE 80 tests, 2 skipped, 1 failure in 1.065s` (`testjson.PrintSummary`: `DONE`, ` N runs,` after `--rerun-fails`, the tests that ran with the subtests in them, `, N skipped`, `, N failure(s)`, `, N error(s)`, the time or `unknown`). The reader takes a line that has exactly that form at the start of the line (counts of 0 are never printed, 1 is singular, the parts come in that order, anything else after it is another line) and names its runner `gotestsum` in `countsFrom`. `passed` is the tests that ran minus the skipped and the failures, `failed` is the failures and `skipped` the skipped; errors are lines of standard error and no tests, so they are not failures. The summaries of one output are added, as the lines of several cargo test binaries are (a script may run gotestsum for two package lists). A summary with errors and no failure, which a clean run does not print, a summary with ` N runs,`, whose total counts the retried tests again, and a summary without `DONE` (the form of a run that did not finish) make the whole gotestsum result unreadable: the step says `counts not read`, and the verbose `go test` lines of the same output do not bring a count back. When a summary is readable it wins over those lines, which leave out the subtests, unless a top-level `--- FAIL:` line is there that the failures of the summaries do not cover (a script that runs `go test -v` for one package list and gotestsum for another): then nothing is read. A script that runs gotestsum twice and ends 0 although the second run never printed its summary cannot be told from the text; the claim still needs every step to exit 0. A package that failed without a failed test (a build failure, a `TestMain` or timeout failure) is a failure with no test behind it, so `passed` can be one too low; the failure is never lost. A command that names gotestsum (`gotestsum`, a path ending in it, `go run <module>/gotestsum@<version>`, `go tool gotestsum`) reads only its own summary; a wrapper script is read when exactly one runner printed one. `plan::is_test_command` accepts the same commands from the log, except `--version`, `--help`, `help`, `tool slowest` and the other `tool` subcommands, and `go tool -n`. The `logged` member of a step is the log's row for the last run of the command. A leading `timeout [options] N` of the model is cut from the command column of the log after the notes (`strip_timeout`: the program `timeout`, `/bin/timeout`, `/usr/bin/timeout` or `/usr/local/bin/timeout`; the options `-k` and `-s` with the operand `timeout` takes (a duration, a signal name or number), `--kill-after=`, `--signal=`, `--foreground`, `--preserve-status`, `-v`, `--verbose`, `--`; assignments in front stay; a form it does not read exactly, such as an operand `timeout` would refuse, a `NAME=value` word after the duration or a quoted assignment in front, is left as it is, because the shell would not have run that command as it stands), because the report gives every step its own limit and a run typed with `timeout 240` is a run of the command. The step and its row are therefore the model's last word on the script, green or red, and the report still re-runs it in the clean checkout. Tests: `crates/agentd/tests/b767_go_counts.rs` (the six real outputs of the events steps and the delivered events report in `crates/agentd/tests/b767_fixtures/`), `crates/agentd/tests/b767_log_rows.rs` (the rows of the events and web logs and the report an events run states).
- What it does: after the engine has ended and the delivered head is bundled, it clones `<agent data>/turns/1/bundle` into a fresh directory of the same microVM,
  checks out the delivered head, plans the repository's own test commands (`plan.rs`), runs them one after the other as the test user (`run.rs`), reads the
  counts from the runner's own output (`parse.rs`) and uploads `runs/<run>/agents/direct/turns/1/test-report.json` (`harness_protocol::direct::TestReport`,
 ) create-only (`If-None-Match: *` and a signed `x-amz-checksum-sha256`, three tries, `S3Objects::put_file_new_retrying`). A put whose answer was lost and whose retry
  meets a 412 is checked against the checksum agentd sent and counts as stored when the object is its own. A key that holds another writer's object is logged, recorded as exactly
  one `upload-conflict` `turn.progress` event (`classify::upload_conflict_payload`) and then written over with agentd's own report (`S3Objects::put_file_retrying`, three tries;
  the log says `direct report replaced` or `direct report not replaced`); the module signals the driver (`crates/agentd/tests/direct_report.rs`). The driver makes this one conflict the
  existing `stopped_other`/`Failed` final result in `turn.ended`, `turn-complete`, `InvocationResponse` and `result.json`, while retaining the head; it introduces no new outcome
  variant or label. `summary.json` was stored before the report step and is not rewritten. run-session `plan-delivery` reads the objects under the summary and report keys, so the
  pre-report summary label and agentd's own report sentence can reach the evidence, pull request comment and run completion.
  The create-only write detects an object present when agentd writes and agentd replaces it after recording it; it does not stop a process holding the engine's session identity from
  writing first or from overwriting agentd's object later (`crates/agentd/AGENTS.md`, the end sequence). Every ordinary report result or failure changes no label, outcome, head or
  `turn-complete` request; a report failure says `not_run` or stores no report, and a run that ended by the user's stop, its deadline or before it started makes none.
- Reading the command: a command is read before it runs and is never handed to `sh -c` as free text. `command::classify` gives `Plain` for words, quotes (`'...'`, `"..."`, a
  backslash; a backslash at the very end is a character of the word, as in the shell), `NAME=value` prefixes and a comment at the end of the line. The step starts a `Plain` command as an argument vector with no
  shell (the prefixes join its environment) when its first word names an executable file that the test user may run (`find_program_as`: the owner, group or other bits as the kernel judges them for the user with no
  other groups) and that the kernel can start itself (`runs_directly`: a binary or a script with a `#!` line; an executable text file with neither is a shell script, so the shell runs it). The file found is the file
  started, by its absolute path (a relative path is the checkout's). Everything else goes to `sh -c`, once `sh -n` has read it to the end: unquoted shell syntax (`&&`, `||`, `;`, `|`, `&`, a redirect, a subshell,
  a line break, `$`, a backquote, `*`, `?`, `[`, `{`, a `~` at the start of a word or after `=` or `:`), an assignment of `PATH`, a first word the shell owns (a builtin such as `echo`, `printf`, `test`, `exit`, `cd`; a
  keyword such as `if`, `!` or `time`: a file of that name on the search path is another program), a script with no interpreter line, and a program the session lacks, so that the shell's own "not found" and exit
  127 reach the reading of a missing program below. A command that cannot be read (empty or only a comment, a quote that is never closed, a control character anywhere, a carriage return included) and a shell line that
  `sh -n` rejects (exit 1 or 2 with the shell's message on standard error; the check runs as the harness's own user, because parsing runs nothing) are not run: the step is `NOT RUN` with the reason `could not read the command`,
  the cause on the second line of `outputTail`, no exit code, no counts, no time and the command text kept; the summary sentence reads ``NOT RUN: `<command>` (could not read the command).`` and `all_exit_zero` stays false,
  so the card never says that a suite exited with a code it did not run for. A setup step that cannot be read ends the run of steps like a failed setup (`run::setup_stops_the_run`): the tests after an install that did not happen would fail for want of it. A setup not run for want of a service or a program does not end it. A shell that cannot be started, or a syntax check that takes over 10 s, says nothing about the command: the step runs. A review found the builtin, interpreter-line, tilde, carriage-return and user checks; two limits stay and show as "could not read the command", never as a wrong run: two notes in a row
  cannot be cut when an earlier one holds an apostrophe, and a script that needs an alias or a shell option set on an earlier line fails `sh -n`. Tests: `crates/agentd/tests/direct_report_command.rs` (the planner and the
  step runner, with a stand-in `python3` and `echo` and a search path that holds no shell) and `direct_report_command_parse.rs` (the reader).
- The step: the command, read as above, runs through `setpriv` as the test user (the engine's uid) or, in the `landlock` mode, through `agentd sandbox-exec` in a sandbox of its own folder (`RunEnv.sandbox`, `Sandbox::rebased`: the same system grants, the report folder writable, and the shared scratch directories), its own process group, no input, a clean environment,
  and nothing of the engine's AWS or engine
  variables: the step gets the same package settings and the same container runtime as the engine's own session, and no credential (the package-registry token stays inside `pkgproxy`; the settings
  mirror to the loopback proxy and hold none; the runtime's socket is the engine user's own). The proxy and the runtime run until the report step is over (`on_report` placement below). Both streams go to one bounded
  reader (`parse::OutputScan`: lines of at most 8 KiB, a ring of the last 4 KiB). The counts come only from that stream, never from a file the step wrote. When the step ends,
  by itself or at its limit, its process group is stopped and the pipes are read for 0.5 s more, so a background process cannot hold the report open. A process that starts
  its own session leaves the group; the microVM that ends the run is the last boundary for it.
- A full disk: the report's checkout sits on the session's root volume, and a whole-workspace debug build of a big repository can fill it. A step that ends with an exit code other than 0 (not at its limit), whose output holds the system's words `No space left on device` in any letter case (read from the whole stream, not only the 4 KiB tail; the bare code name `ENOSPC` does not count, Node uses it for the file-watcher limit), and whose runner reported no failed tests, is marked NOT RUN with the reason `ran out of disk: <that line>`: the line is cut after the phrase and its `(os error 28)`, loses a leading `error: ` and has at most 100 characters. The exit code stays, the counts go (an incomplete run measures nothing), the step is no red result and keeps the claim away. The steps after it are listed as not run with the reason `skipped: the session ran out of disk in an earlier command`, because the volume is still full (`run_steps` in `mod.rs`). The sentence reads `NOT RUN: `cargo test` (ran out of disk: couldn't create a temp dir: No space left on device (os error 28)), and 1 more.` A repository can print the words itself; the line is shown with the step, and the container-runtime and missing-program marks have the same property. The disk's free space is not measured here. Tests: `direct_report_parse.rs`, `direct_report_run.rs`, `direct_report.rs` (scenario `report_disk_full`).
- How a command was chosen: when plan source 4 detects `cargo test` and the root `Cargo.toml` makes a bare `cargo test` run more than one member, `run_steps` writes the line `PLAN NOTE: cargo workspace, 14 members` at the head of that step's output (after the `NOT RUN:` line when the step has one, so the reason stays the first line, and after the runtime block of a step not run for the runtime; the output gives way from the front within the 4 KiB cap) and removes any line the repository printed in that place. The count is what cargo selects: all `members` of a virtual manifest, its `default-members` when it names some, only the root package when the manifest has a `[package]` (then no note), minus `exclude`, a member counting when its folder is inside the tree and holds a `Cargo.toml`. The reader is a small one without a new dependency (comments, quotes, multi-line arrays, dotted top-level keys, `dir/*`); a pattern or layout it does not know gives no note. The command stays `cargo test`. `TestStep::plan_note_members` reads the line only for a Test step with source `Detected` and the command `cargo test`; `TestReport::summary` writes the note as the second line of the summary's `reason` (the first line is the report's reason or the NOT RUN reason, so neither is hidden) and `TestReportSummary::plan_note` returns it. Tests: `direct_report_plan.rs`, `direct_report_run.rs`, `direct_report.rs` (scenario `report_cargo_workspace`).
- EVIDENCE.md notes: after the sentence the packager prints `TestReportSummary::plan_note` (the command was chosen from the manifest and runs the whole workspace, so a narrower `.ham/test-command` can replace it) and `TestReportSummary::limit_note` (a command stopped at its limit: the command, the limit it was given in seconds and the two settings that change it, the client setting `run.report_command_minutes` and the stage variable `AGENTD_REPORT_STEP_S`). `sentence()` is unchanged because `ham` appends its own advice to it. The machine line `PLAN NOTE: ...` never appears in EVIDENCE.md.
- Wording: the one allowed sentence is "repository tests pass in a clean checkout: N of N" (`TestReportSummary::claim`); N is the number of tests that passed, skipped tests
  are counted apart; it needs every setup and test step to exit 0 inside its limit, counts read by the runner's parser for every test step, no failure and one pass at least.
  Any other result is a plain sentence of what happened (`TestReportSummary::sentence`). The report does not say the tests are meaningful.
- Settings: `AGENTD_REPORT_TESTS` (`0`, `off`, `false`, `no`: the module is off for the stage), `AGENTD_REPORT_BUDGET_S` (480; 1 to 27,900; the time all steps share), `AGENTD_REPORT_TAIL_KIB` (256; 4 to 4096; the end of each step's output that the report keeps),
  `AGENTD_REPORT_STEP_S` (300; 1 to 27,900). The request's `reportTests: false` (the user's `report_tests = off`) switches it off for one run. The request's `reportStepS`
  replaces the step limit for one run: `Settings::with_step_s` lengthens the whole budget by
  the time the new limit adds to the stage's (budget = max(stage budget, limit + (stage budget - stage limit)); 780 s for a 600 s limit with the defaults) and keeps it when the limit is shorter, and a request with the member makes
  the module ask the driver for that budget plus `CEILING_GRACE` (30 s) through `DirectHook::report_time`, which the driver grants up to what is left of the run's deadline (`hooks::report_ceiling`; the driver's own
  480 s is the floor). Without the member nothing changes, whatever `AGENTD_REPORT_BUDGET_S` says, so a stage that set it above 480 sees no new behaviour.
- Progress: the module writes `turn.progress` events of kind `report` with `harness_protocol::direct::ReportProgress`, flushed at once (`record_urgent`): `checkout` when the report begins, `running` at the start of each command (`step` of `of`, the redacted command cut to 120 characters, `limitS`, and a `text` such as "Running the repository's tests: command 2 of 2 (up to 5 min).") and `ended` with the status when the commands are over, before the upload. They change no status and no outcome, say nothing about how the tests went, and are written only when the report runs (not when it is switched off, skipped for lack of time or not applicable). The client shows the phase `running the repository's tests` from them and the text as the live row. Tests: `crates/agentd/tests/direct_report_card.rs`.

### The goal module

The engine's own goal plugin runs the goal loop by default; agentd places it, watches it and ends it with brakes that are stalls (no cap on rounds or tokens).

- On when `AGENTD_GOAL` is not `off`, the engine has a spec in `crates/agentd/src/engine/goal.rs` (the engine's profile) and `AGENTD_GOAL_PLUGIN_DIR` (default `/opt/harness/engine/plugins`) holds
  `lock.json`; otherwise `Hooks::standard` gets `None` and a run is what it was. `files.rs` checks every file of the two plugin folders against the lock, then copies them
  read-only to `<configuration directory>/plugins/`; one mismatch places nothing, the run goes on without the loop and the log says `direct turn goal loop off: ...`.
  `engine::goal` fixes the plugin mode (`in_process`, never left to whether a bootstrap file exists).
- `on_wire` sees the model's call of the completion tool (`tool_call` titled with the tool, then a `tool_call_update` `completed` whose `rawOutput.completed` is exactly `true`):
  the only done claim the module believes. The rounds log and the state file are written by the engine user, so they steer and measure; they never say done.
- `on_turn_end` reads the rounds log (`rounds.rs`), the fingerprint and the state file and feeds the pure rules of `machine.rs`; the answer is `Wait` (the driver holds the run),
  `Done`, `Prompt(KICK_PROMPT)` or `Stop`. The first look decides whether the engine claimed the goal (state file active, or the engine already went on by itself); an engine that did not
  runs as a plain run after `AGENTD_GOAL_CLAIM_WAIT_MS` (3 s). A done claim counts when the round that made it ended `completed` with a message and 3 s passed; a round that ended aborted
  or with no message is a brake. `BLOCKED:` twice (the same last line, ignoring case and edge spaces), 3 text-only rounds with an unchanged tree and 5 rounds with an unchanged tree end the run;
  a loop that stopped gets one continue (2 s after a round that ended aborted or failed, 15 s after a completed round with no new round) and the run ends when two continues changed nothing.
  A tree change gives the continues back. Rounds read together are counted together, so a brake's count can pass its limit.
- A brake clears the state file (the plugin's follow-up rounds ignore `session/cancel`), lets the round in flight finish for `AGENTD_GOAL_DRAIN_S` (120 s) and votes
  `Stop` with a detail that begins "The harness ended the run:" (`stopped_other`; the label says the harness ended the run and gives the rule as the reason, from `DirectOutcome::label_for`, and the summary
  puts that sentence first in its detail). The user's cancel clears the state file at once (`Event::Cancel` when the latch is up); a stall or the deadline
  does not: the ladder's one resume follows a silence, and the deadline ends the run itself. The continue goes through the driver's one sender, so it never overlaps a user's message.
- The brake inside one round: the rules above see a round only when it ends, and a loop that polls inside one long round (many varied
  tool calls over a long time, no file changed, no new text) never ends one. `on_wire` counts the model's tool calls (`tool_call`, not the completion tool) and its non-blank
  `agent_message_chunk` text; a task started in `arm()` reads the tree fingerprint every `AGENTD_GOAL_LOOK_EVERY_MS` (5 s) while calls come. The pure `Watch` (`WatchLimits`) ends the
  run after `AGENTD_GOAL_ROUND_CALLS` (30) tool calls in a row with an unchanged tree and no new text, or when `AGENTD_GOAL_ROUND_WINDOW_S` (1200 s, 20 minutes) have passed with an
  unchanged tree and at least `AGENTD_GOAL_ROUND_MIN_CALLS` (10) calls (one long build or test run is one or two calls, not a poll). A changed tree and an unreadable fingerprint start both counts
  again (an unreadable tree never ends a run), new text starts the call count only, and a round boundary starts everything again. The brake has the rule `round-no-progress` and a detail that
  begins "The harness ended the run:" and says `<engine> made no progress in N tool calls in a row: no file changed and no new text appeared` or `<engine> made no progress in 20 minutes: no file changed and M of N tool calls counted as no progress`;
  the label is `<engine> stopped: the harness ended the run (<that reason>)` from `label_for`. The task stores the brake and, while a prompt is open, calls `DriverCtl::interrupt` (one
  `session/cancel` of the open prompt); `on_turn_end` takes the stored brake first, clears the state file, emits `brake` and votes `Stop` when the turn was interrupted (the driver holds no run after an
  interrupt, so a `Wait` would be ignored), otherwise it enters the drain like any brake. Both limits are settings below. Tests: `crates/agentd/tests/direct_goal_watch.rs` (the pure watch) and `crates/agentd/tests/direct_goal.rs` (three whole-agent cases).
- The session's CPU as a second signal of progress: a long build on two vCPUs can only be waited for with short calls, and a run can be ended while it waits. `busy::ProcBusy` reads a counter of clock ticks that only goes up: `user + nice + system` of the first line of `/proc/stat` less agentd's own `utime + stime` and `cutime + cstime` (the git it starts for the snapshots and the fingerprint of the tree) and the engine process's `utime + stime` (`/proc/<pid>/stat`; the engine's pid is `DriverCtl::engine_pid_cell`, set when the engine is started and again at each respawn), so what remains is what commands, builds and tests used; the first reading is 0, a counter that goes back never moves the reading back, an unreadable table gives none. The monitor reads it every `AGENTD_GOAL_LOOK_EVERY_MS` whether or not a call waits and tells `Watch::cpu`. At a brake point `Watch::look` judges the stretch (the time since the tree last changed, a window at most, for the 30 calls; the window for the 20 minutes) from the newest reading and the newest one at least that much older: at least the share is progress (`forgive`: both counts and the clock of the window start again, the time of a held-back command is dropped, one `goal-loop` event `hold` with `busyPct` and `spanS`, `HoldNote::Busy`), less is a stop whose first sentence says `(the session CPU was idle)` (below 5 percent) or `(the session CPU was busy at N percent)`, and fewer than `BUSY_MIN_SPAN` (30 s, a quarter of a short window) of readings judge nothing. With no reading, or the signal off, the words are the old ones. The grace of a running command counts from the last real change of the tree (`anchor`), so a busy session is still ended after two hours (`a command was running, but no file changed`, with the CPU words); that stop is not excused. The signal is off when `run.command_grace_minutes` is 0 (the request's `commandGraceS`), when `AGENTD_GOAL_COMMAND` is off, and when the engine has no user of its own (`GoalHook::new` and `for_engine`; the constructors that name a command probe read no CPU). A loop that runs the same failing suite again and again burns CPU and now counts as progress until the grace. Tests: `direct_goal_busy.rs` (the watch with a clock the tests move, the reading over a `/proc` the tests write, the settings, three whole runs).
- Calls that bring something new are not a stall (`watch.rs`, `mod.rs`, `settings.rs`; `AGENTD_GOAL_NEW_CALLS`, default 100, 1 to 1000, `0` or `off` counts every call): a model that is still reading the code to plan a feature that touches several modules can make dozens of calls that each have an input and an answer that no earlier call of the run had, none failed and none repeated, and without a credit the brake `round-no-progress` would end such a run. `on_wire` reads the id, kind, title and `rawInput` of a `tool_call` and the status and `rawOutput` of its `tool_call_update` (`watch::input_key`: a hash of the kind, the tool name before the first colon of the title and the input; `watch::output_key`: the distinct non-blank lines of every string of the answer as hashes, without the engine's echo of the call, the object member `query` at any depth, and whether the call succeeded). `Watch::tool_call_keyed` counts the call as always and remembers it when its input is new to the run; `Watch::tool_done` takes it out of both counts when the call succeeded (status `completed`, no `success: false`, `isError: true` or non-empty `error` in the answer), its answer has at least `MIN_NEW_LINES` (3) lines that no earlier answer of the run had, and the allowance (`Watch::with_new_calls`, between two changes of the tree) is not used up. The lines of every answer are remembered, credited or not (`SEEN_LINES_MAX`, 200,000 hashes, then no line is new), so the same answer again, a poll that words its check differently each time and gets one answer, and a poll that prints the time or a counter (one new line each) bring nothing. The credit is taken back by the same rules as a wait for a command: an answer to a call that began before a change of the tree or a round boundary earns nothing, a call a running command took back is not credited again, a text since the call keeps `run_calls` as the text left it, and a call that is no longer pending is left out of the calls a sample may take back. A repeated input, an answer with fewer than three new lines, a failed call, a call with no `rawOutput` on the wire (the engine does not send it, it came in the `tool_call` update itself, or the fake engine's bare calls) and every call beyond the allowance are counted, so a loop of identical calls, a poll of an idle session and a run that keeps failing end as before, and the old words of the stop stay when nothing was credited. A stop after credits says `(N calls that brought something new were not counted)`. A change of the tree gives the allowance back (`boundary`); the seen inputs are kept for the run (`SEEN_MAX`, 20,000, then nothing is new). Known limit: an engine that echoes a call's words under another name than `query` still counts those words as lines, which is one line for a short command, so it takes a poll with three other new lines in every answer to earn credit; the allowance bounds that case at 100 calls, and no clock bounds it. The run's `goal.newCalls` (the user's `run.stall_new_calls`) replaces the stage value (`GoalSettings::with_request`). Tests: `crates/agentd/tests/direct_goal_explore.rs` (the pure watch, the two readers, six whole runs against the fake engine's scenarios `goal_explore_*`) and `direct_goal_settings.rs`.
- A command that is running: a model that starts the repository's full test run in the background can only wait for it with `sleep` and `tail` calls (the shell tool gives up after ten minutes), and the brake `round-no-progress` can end the run after a few such polls. The watch is told what the engine's user's processes did (`watch::Command`: `Active { age }`, `Idle`, `Unknown`). A call is taken back, and the time left out of the window, only when `age` is at least the call's age plus `START_MARGIN` (5 s): the sessions that used the CPU are older than the call, so the model started that command with an earlier call and the call waits for it. A command a call starts and waits for is as old as the call or younger, so its call stays counted and a loop that runs the failing test suite again and again is still ended at 30 calls or 20 minutes. A later call qualifies whenever an earlier one does. The watch keeps the arrival of the calls waiting for a sample (`UNFOLDED_MAX`, 1024; a call beyond it stays counted) and of the newest call across boundaries, so a long poll keeps earning the time. The time is paused, not forgiven, so the history before it stays. `Unknown` protects nothing, and one sample credits at most 60 s. Once a command has been seen running, the tree may stay unchanged for the grace (`AGENTD_GOAL_COMMAND_GRACE_S`, 7200, never below the window, counted from the last change of the tree) and the run then ends with the same rule and the detail “The harness ended the run: <engine> made no progress in 2 hours: a command was running, but no file changed.”; the monitor looks at the tree for this even when no call comes. The evidence is `ProcProbe` (`command.rs`): the processes of the engine's user (`StartupCtx.engine_uid`; in the `landlock` mode, where the engine has no user of its own, the processes below the engine's process, `ProcProbe::for_engine_family` and `evidence_choice`; a process left to init by a parent that ended is not seen there) outside the baseline taken when each session begins (`Event::SessionStarted`; the baseline keeps the sessions of its processes too, so what runs in the engine's own session is no command), tracked by pid and start time, with CPU ticks `utime + stime` and, the ticks of the children they waited for (`cutime + cstime`: a test run that starts a short-lived process per test keeps almost none of its CPU in itself, and the children are gone before a sample sees them; a child that lives across a sample is counted in its own ticks and again in its parent's, so a deep process tree counts a tick up to once more for each level). The engine starts each command of the model in a session of its own. A session is as old as its oldest process still there; the sessions are sorted oldest first and their CPU is added until it reaches `AGENTD_GOAL_COMMAND_CPU_PCT` percent (5) of one CPU over the time since the previous sample, rounded up; the age of the session where it does is the answer. Since a sample is also Active when the sessions that have a process in the scan used that rate over a trailing window (`AGENTD_GOAL_COMMAND_WINDOW_S`, by default the longer of the run's stall window and 30 minutes, 5 to 14,400 s, 0 is off; a young window is judged by the time it has. It is a stage setting only: no client key and no request member names it, so a user lengthens it with `run.stall_window_minutes` above 30 and turns the whole look off with `run.command_grace_minutes` 0, and a key that shortens it needs a protocol bump): the ticks each session used in the samples of the window are kept per session and added oldest session first against the rate over the window, and the age is the older of the interval answer and the window answer. A session that two scans in a row found no process of loses its history (a command the model ran itself and that has ended lends nothing to the next call; one scan that missed it does not wipe a job), and a new baseline forgets everything. A job that worked and then does nothing reads Idle once its work leaves the window or its rate over the window falls below the threshold, so a job that hangs does not hold the run for ever. The ages come from `/proc/uptime`, read before the listing; without it the sample is `Unknown`. A process first seen that was born before the previous sample counts nothing. The monitor samples on a blocking thread every `AGENTD_GOAL_LOOK_EVERY_MS` (5 s) while a call is pending or a command was seen running, and tells the watch at the instant it asked. The hold is told to the run's events: `Watch::take_note` gives `Held { age }` when a sample first takes calls back or credits time and `Released { held }` when none did for six sample intervals (30 s), and the monitor writes the `goal-loop` events `hold` (field `ageS`, the age of the command; the text says the command has used the CPU lately, because the rate over the window grants a hold too, and never that it is using it now) and `release` (field `heldS`, the time credited in that hold); the in-round `brake` event carries `heldS`, the time of its window that was held back. One event for each change; the label and the detail of the brake do not change. With no engine user of its own and no sandbox (a developer machine, a test), `AGENTD_GOAL_COMMAND=off` or a grace of 0 there is no evidence and every call counts, as before. What it does not see: a command that waits on the network or the disk and uses almost no CPU for longer than the window (a test run that uses the CPU for a few minutes and then waits for network timeouts one after another; a job with little work before a long silence is not told from a hung one); CPU in processes of another user; workers a program starts with a session of their own; a job that was in the baseline. A CPU-bound job started earlier protects a later call that has nothing to do with it, until the grace. The ages come from the machine's clock and the calls from the supervisor's, so a machine that was suspended between a call and the next sample can lend one interval to a foreground command. `ProbeSource` says where the evidence comes from: the engine user of the run and the real `/proc` (the product), a probe a test names (`GoalHook::for_engine_with_probe`), or an engine user and a `/proc` tree a test names (`GoalHook::for_engine_over_proc`; a real engine user needs a root agentd). Tests: `direct_goal_command.rs` (over a `/proc` the test builds, with an uptime, sessions and start times), `direct_goal_command_window.rs` (the window, the sessions that are still there, the window setting), `direct_goal_command_replay.rs` (a replay of the recorded process table of a long test step, `fixtures/replays/scripts-suite-serial/`, through the real probe), `direct_goal_hold.rs` (the hold notes), `direct_goal_watch.rs`, `direct_goal_command_run.rs` (whole runs with a probe the test names, and with the engine user and a fake `/proc`) and the scenarios `goal_command_polling`, `goal_command_polling_late`, `goal_command_polling_brake`, `goal_command_polling_long` (40 polls over 24 s, for the events of a hold that ends) and `goal_command_polling_final_hangs`. `direct_goal_command_run.rs` also runs a job with bursts, a job whose CPU is in children that exit and a loop of short foreground commands (which must still end the run) over a fake `/proc`.
- The last turn: when a brake of the rule `round-no-progress` fires, `final_message` is on (request member `finalMessage`, stage `AGENTD_GOAL_FINAL`, on) and 30 s of the deadline are left, the module votes one `Prompt(FINAL_PROMPT)` instead of `Stop` once the engine is idle: the open prompt was cancelled and answered, or the follow-up round in flight finished in the drain. The driver's one sender puts the prompt in the same session. The phase is `Final`, one `goal-loop` event of phase `final` says so, a timer interrupts that prompt once after `AGENTD_GOAL_FINAL_S` (120, cut to the deadline less 15 s), and the turn end that follows, however it ended (answered, cut short, the engine ignoring the cancel), votes `Stop` with the brake's own detail. The engine's answer to that prompt is the run's final message; the label and the rule are the brake's. The run ends at once, as before, when the engine ignored the cancel, when the drain ran out with a round still in flight (a prompt would queue behind it), when the user cancelled, and for every other brake (their rounds ended with a message of their own). A last turn that fails ends the run with that failure's own label; the brake event stays. Tests: `direct_goal_command_run.rs`.
- The request's `goal` member (`newCalls`: 0 counts every call): `roundCalls`, `roundWindowS`, `roundMinCalls`, `commandGraceS` (0 looks for no command), `finalMessage` and `newCalls` replace the stage's settings for one run (`GoalSettings::with_request`, `crates/agentd/tests/direct_goal_settings.rs`). `on_startup` checks the member again with `harness_protocol::direct::check_goal`; a refusal ends the run `stopped_setup_failed` before any model call and names the member and its range, never the value.
- A missing or damaged rounds log switches the module to the stream, the silence limit and the deadline (a `fallback` event; a done claim then needs a quiet engine and a goal that
  left the state file). A fresh session writes the goal again (`rearm`).
- Events: `turn.progress` of kind `goal-loop` with `phase` (`on`, `round`, `kick`, `hold`, `release`, `brake`, `final`, `done`, `off`, `fallback`, `rearm`) and plain `text`; a `round` carries `rounds` and `status`, a `brake` carries `rule`

### The hold

The engine's goal plugin queues its follow-up prompts itself, so after the first `session/prompt` answers `end_turn` the engine goes on with no request open. A module
that sees this (the `goal` module) votes `Wait { until }` at `on_turn_end` instead of `Done`. The driver (`driver::hold`) then keeps the run open for `until`:

- It reads the engine's pipe (`AcpClient::pump_idle`), so the engine never blocks on a full pipe and what it says reaches the collector and every module's `on_wire`.
- It ends the hold as it would end a prompt: the deadline (`stopped_timeout`) and the silence limit (`stopped_silence`, not while a tool runs) write `session/cancel` once
  first; the user's cancel writes `session/cancel` once, marks it sent (`stopped_by_user`) and ends the hold at once, because no prompt is open to answer it (a module hears
  `Event::Cancel` and can stop the engine's own loop); a closed pipe is a dead engine.
- When `until` has passed it asks the modules again. The last message of the run is the one the engine said last (`DirectCollector::final_message`), and the tree is measured
  again. A `Prompt` of any module replaces a `Wait` whichever module votes first (a user's message goes out while the engine works), a `Stop` beats it, of two `Wait`s the shorter
  is kept (at least `hooks::MIN_WAIT`, 10 ms), and `on_seal` may not wait (a `Wait` there is read as `Done`).
- A module that waits keeps its own bound: the hold has no cap of its own beyond the deadline and the silence limit. Tests: `crates/agentd/tests/direct_hold.rs`, `crates/agentd/tests/direct_hooks_unit.rs`.

### The research module

The engine researches with Tavily and downloads public repositories for context while the VM firewall stays as it is. The Tavily key is in the stage account; the VM holds none. The module is a loopback HTTP API in agentd plus the read-only context storage behind it:

- `settings.rs`: every setting is an `AGENTD_RESEARCH_*` variable (`MODE` off|false|0|no switches the module off; `PORT` 3129, never the package proxy's 3128, and any free port when taken; caps: page 512 KiB, kept archive 64 MiB, unpacked 200 MiB, 20,000 files, 1 MiB a file, 300 MiB a run, 256 MiB of free disk kept; `WAIT_S`/`WAIT_MS` 90 s; `RETRIES` 3; `MAX_INFLIGHT` 8). A value that does not parse, or a cap of zero, keeps its default.
- `route.rs`, `client.rs`: `Route` is the seam; `HttpRoute` posts the JSON body of `harness_protocol::research` to `<internal API>/internal/research/{search,fetch,repo,job,limits}` with SigV4 (service `execute-api`, the run's session credentials). `FailureKind::Absent` is the gateway's own 403, 404 or 405 (no such route for this run), `Transient` a throttle, a 5xx or a connection that failed (asked again with the same idempotency key, pauses 500 ms doubling to 8 s, the route's `retryAfterS` up to 10 s, 3 more tries), `Final` everything else. A search or fetch without a key gets a ULID; a repository request must have one (`api.rs` makes it from the arguments).
- `store.rs`, `place.rs`, `extract.rs`, `context.rs`, `index.rs`: `Placer::place_ref` reads the item's manifest and body from the harness bucket (`runs/<run>/agents/direct/research/items/<id>/`, which the worker role can read and not write) with `S3Store`, applies `ItemManifest::validate` and this run, this item and a plain body key, checks the route's answer (`ItemRef`) against the manifest, applies the size caps to what the manifest says before the body is read, reserves the run's byte total, checks the body's length and SHA-256, unpacks a repository with `extract_targz` (only files and directories; plain relative UTF-8 paths; every member listed with the manifest's size and hash; caps on the decoded stream, one file and the member count of any kind, twice the file cap plus 16; the decoded stream is read to its end, so bytes after the tar's end marker count against the cap; every sum is checked, so a cap as large as a number can be does not wrap; free disk checked first; files 0444, directories 0555; a failed unpack leaves nothing; the unpack happens in `repos/.stage-<item>-<n>`), and publishes it with a no-replace rename (`renameat2` `RENAME_NOREPLACE`) to the first free name of `<owner>__<repo>__<commit12>`, then that name with `-<item>`, then with `-<item>-<n>`: a directory that already holds a name is never replaced or removed, and a failed placement removes only its own unpack, and writes `context/research/{pages,repos,manifests}/`, `INDEX.json` and `INDEX.md` (columns Origin, Date read, sha256, Licence, Why it matters; the sha256 is `ItemManifest::sha256`, the hash of the canonical bytes). Placing an item twice reads nothing; concurrent placements of one item read its body once. The index is written from one snapshot, one writer at a time; a placement stands when the index files cannot be written (`Placer::index_dirty()` is set, and the next call that reaches the placer writes them again). `verify` compares the disk with the route's manifests; `check_tree` runs `harness_protocol::research_copy` over a directory of the work tree (links are not followed, `.git` is skipped).
- `api.rs`: the loopback server (`127.0.0.1` only, peers checked, 8 calls at once, request bodies at most 64 KiB, JSON errors `{"error":{code,message,exit,...}}` with the route's HTTP status and the `ham-research` exit code; agentd's own words are `integrity` 502/7, `limit_context` 429/4, `no_space` 500/5, `unavailable` 502/5). A call that places an item (`fetch`, `repo`, `wait`) does the placement in a task of its own, so a caller that hangs up does not stop an unpack half way. A listener that is not on a loopback address is closed and nothing is served. An error about a body that is not the request says where it went wrong (line and column), never what the body held. Search answers are marked `untrusted`. A log line holds counts and codes, never a query, an address or fetched text. `Server::stop` ends it with the run.
- `mod.rs` (`ResearchHook`): `on_startup` returns `Ok` whatever happens (the module never ends a run). It does nothing when `AGENTD_RESEARCH_MODE` is off or the request's `research` switch (`ResearchOptions`) is `{"enabled": false}`; the user's switch posts one `turn.progress` event of kind `research`, phase `off` ("Research off: you switched it off for this run."), which the run screen draws as a plain line (`ham_core::notice`), and a stage without the route stays silent. It asks the route's `limits` once (8 s budget): an answer starts the module and gives the request rules their limits; `Disabled` (the run's policy row) logs "direct research off"; a gateway that has no such route (older stage) is silent, so a stage without the route changes no log, event or golden stream; a route that does not answer starts the module anyway. The request's `thirdParty` member is read here too: the check answer carries `"thirdParty": "allow"` or `"block"`, and `ham-research check` ends a list of copies with the sentence that is true for the run (a copy ends the run without a zip under `block`; under `allow` the delivery reports it as a finding and still delivers). The engine then gets `HAMH_RESEARCH_URL`, `HAMH_RESEARCH_WAIT_S` and `HAMH_CONTEXT_DIR`. `on_shutdown` stops the server, keeps a snapshot of the counters (`Stats` and the bytes placed, as `DirectResearchCounts`), and, when the run made any call, logs one line and records one `turn.progress` event of kind `research` with the same counts; it then reads the route's `limits` once more (3 s budget, after the server has stopped) for the route's own count of the run, and last (8 s budget, inside the hook's 15 s) writes `<agent data>/context-listing.json` from `Placer::listing()` and uploads it to `runs/<run>/agents/direct/context-listing.json` (`harness_protocol::direct::s3::context_listing_key`; three tries as the clean-checkout report; a failure or a late finish is a log line and changes nothing). The listing is what only agentd can make: `{schema "hamh-research-placed/1", run, items {<id>: {files {<path>: <sha256>}}}}` with the SHA-256 of each regular file as it is on the disk (a repository: every file under its directory, keyed by the path relative to it; a page: its file, keyed by the name of the manifest's body key, `body.txt`; links and unreadable files are left out). It is written whenever the lane started, also with `items {}` when nothing was placed, and never when research was off or the stage has no route. Tests: `direct_research_place.rs` (the content, the disk and not the manifest, links, the judge's keys), `direct_research_hook.rs` (key, file and object, absence, a failed upload). `on_summary` copies the note into `summary.json` as `DirectSummary.research` (`DirectResearchNote`): the member is there when research was decided for the run. `enabled: true` with `provider` (from the route's answers), `usage` (the route's count at the end; left out when that read failed or did not answer in time, because a zero would claim the route counted nothing) and `counts` (agentd's own: `searches`, `fetches`, `repos`, `waits`, `placed`, `refused`, `errors`, `placedBytes`) when the lane started, also when the engine never called it; `enabled: false` with nothing else when the user switched research off, the route said `disabled` or another final word (`no_key`), or the lane could not start; no member on a stage without the route. The numbers are this process's own and need not equal the route's (one `fetch` can name several addresses). Telemetry only: the label, the outcome and the delivery never depend on it. The bytes of a typical note are in `fixtures/research/summary-research.json`, the one set the writer (`direct_research_hook.rs`) and the readers (`harness-protocol`, `run-session`, `ham-core`) are tested against.
- The engine side is `images/worker-python/ham-research` (Python 3.12, engine-neutral: any engine that can run a command or send HTTP). The run counters are in `summary.json` through the `on_summary` hook.
- No key, token or password exists anywhere in this module or its tests; the module spawns no process and opens no connection but the two signed clients (`crates/agentd/tests/direct_research_sources.rs`).

### The tools module

A stateless MCP server on `127.0.0.1` that offers the engine typed tools (`code_search` first), so that an engine with an HTTP tool client uses them without a command in its shell, and the hook that starts it for a run (`ToolsHook`, registered by `Hooks::standard` right after `research`). The tool names, descriptions and input types are the table of `harness_protocol::tools`; no word of an engine is in this directory (`crates/agentd/tests/engine_neutral.rs`). Is the library (the first block of bullets) the hook (the second).

- `tools/server.rs`: `POST /mcp`, JSON answers only. `GET`, `DELETE` and any other method are 405 with `Allow: POST`, any other path 404. The peer must be on the loopback, `Host` must be one loopback name and `Origin`, when present, a loopback origin; anything else is 403 and repeats nothing. Both are read strictly (only letters, digits and `.:-[]`; `localhost.example.com`, a user part, a path or a port above 65535 never pass). A body is at most 64 KiB (413; one that does not arrive in 10 s is 408). One JSON-RPC object per request: a batch, text that is not JSON, a null or non-integer id or a missing `"jsonrpc": "2.0"` is a 400 with an error that has no id; a notification of any name and a response of the client are a 202 with no body; an error that belongs to an identified request is a 200 with its id (`-32601` unknown method, `-32602` bad parameters or an unknown tool, `-32800` a cancelled request). `initialize` answers the highest of 2025-11-25, 2025-06-18 and 2025-03-26 that the client asked for (the highest for any other value) and no answer ever carries `Mcp-Session-Id`: a server that issues one breaks after a restart on the same port because the engine never initializes again. `Mcp-Protocol-Version` is counted and never a gate: the specification asks for a 400 to a value the server does not know, but the engine connects once per session and a 400 at `tools/list` would lose the tools for the whole session in silence.
- A call (`tools/call`): the input is validated against the table (`error: usage: ...`, the text names members and rules and never a value), a slot is taken (eight at once, the ninth gets `error: busy`), and the backend runs in a task of its own. It ends with the backend's answer, a cancel, the backstop (130 s, `error: timeout`) or a client that hung up. `notifications/cancelled` is matched on the `User-Agent` and the request id, so two client programs that both count from 0 do not cancel each other (two copies of one program still would; the server keeps no session to tell them apart), and a cancel for a call that is not in flight is forgotten so that it cannot cancel a later call with the same number. On a cancel the backend's `CancelToken` fires and the backend has 500 ms to end its children; then the task is aborted, and every child a backend starts must also die when its future is dropped (`GroupGuard`, `kill_on_drop`). The cancelled request is answered `-32800`. A panic of a backend is `error: unavailable: internal fault; do not retry`. The failure words are the six of `harness_protocol::tools::RESULT_FAILURE_WORDS` (`FailureWord`); `usage`, `busy`, `refused` and `disabled` mean the call did not run (the summary's `refused`), `timeout` and `unavailable` that it ran and failed (`failed`).
- `tools/result.rs`: a result is `content` text only (one text block and `isError`, never `structuredContent`), and its serialized form is at most the profile's `maxResultChars` (7,500; a smaller value is raised to 256), counted in UTF-16 code units because the engine's client cuts the JSON text of the result in the middle at 8,000 JavaScript characters. The cut is made on the text and charges each character what it costs once escaped, keeps the head, ends at the last line end when that keeps four fifths of what fits, and appends `[shortened: showing N of M characters]`, counted inside the cap. A failure is `error: <word>[: detail]` with the word first, the detail one short plain line of at most 120 characters; a backend's detail is a template and never a value the caller sent, a path or the text of another process.
- `tools/backend.rs`, `tools/backends.rs`: `ToolBackend` (`name()`, `call(ctx, input, cancel)`) is the seam. `ToolContext` carries the work tree, the context directory, the counters and a builder of launch specs for commands run as the engine's user (`launch_spec`; the hook of a run supplies one made from `StartupCtx::clean_launch`). `backends::all` is the one list of tools: a tool package adds exactly one line to it, and a conflict there is resolved by keeping every line. `AGENTD_TOOLS_DISABLE` removes single tools from the list (`retain_enabled`).
- `tools/settings.rs`: `AGENTD_TOOLS_MODE` is the image's kill switch: `off`, `false`, `0`, `no` switch the module off, `on`, `true`, `1`, `yes` and an unset variable leave it on, and any other word switches it off and says so (a typo in a kill switch must not leave the thing running; the research module reads its own switch the other way). `AGENTD_TOOLS_PORT` (3130, never 3128 or 3129; 0 takes any free port; `bind` takes any free port when the port is taken).
- The serving task is supervised. The supervisor keeps the bound socket and serves a clone of it, so when the task ends the port stays bound and connections that arrive meanwhile wait in the backlog; calls in flight are cancelled (a call is never replayed and never outlives its task) and a new task serves the same socket. At most three restarts; the fourth end leaves the server down, logs it once and `ServerHandle::state()` says why. A listener that is not on a loopback address is closed at once and nothing is served. `ServerHandle::self_check` asks a ping of the address and expects this server's answer: the hook calls it before it writes the registration file, so that the file never names a port that another process serves.
- `tools/stats.rs`: counts and times (initializes, lists, calls per tool, failed, refused, truncated, cancelled, protocol errors, unknown protocol headers, restarts, p50 and p95 in milliseconds, absent when no call ran). A log line holds a tool name, a result word, a time and a size, never a pattern, a query, a path, a header value or a result (`crates/agentd/tests/direct_tools_server.rs` plants canaries in all of them). The hook reads a `Stats` snapshot for the connect check and for `DirectSummary.tools` (`Stats::to_counts`).
- The hook (`ToolsHook`, `tools/mod.rs`). `hook(env)` is `None` when `AGENTD_TOOLS_MODE` switches the module off, so the list is then the nine modules it was; `Hooks::standard_with_tools` takes the settings as a value for a test.
  - `on_startup` never ends a run. The profile's `[mcp]` table comes from `StartupCtx::mcp()`. With no table, or `via = "none"`, the module does nothing at all: no log line, no file, no variable, no event, no summary member (the 13 golden streams run the test profile of `direct_support`, which has no table unless a test asks, `crates/agentd/tests/direct_tools_off.rs`). Otherwise, in this order: the backends (`backends::all(env, startup)` less `AGENTD_TOOLS_DISABLE`; none built is the reason `no-tools`, all switched off by name `all-disabled`, and no server starts); the registration's pieces are checked (the profile's `path` under `{dataDir}` or `{configDir}`, `register::target`); the port is bound (3130, any free port when taken); the server starts on it and answers a `ping` (`self_check`); the profile's template is read from the templates root (`AGENTD_TEMPLATES_ROOT`) and filled (`{toolsName}` is `ham`, `{toolsUrl}` the bound address; at most 64 KiB, JSON, no placeholder left); the root directory is opened once and kept; the file is written; and only then `HAMH_TOOLS_URL` joins the engine's environment (beside `HAMH_RESEARCH_URL`) and `direct tools server on 127.0.0.1:<port> (<n> tool(s))` and `registration written (<n> bytes, <n> stale file(s) removed)` are logged. A failure at any step stops the server, logs one line `direct tools not started: <word>` (`bind-failed`, `self-check-failed`, `bad-profile`, `bad-registration`, `registration-failed`, `no-tools`, `all-disabled`) and leaves a summary note with that word; the run goes on without the tools.
  - The context a tool gets: the work tree (`StartupCtx.repo`), `HAMH_CONTEXT_DIR` from the engine environment the research module set, and a launch builder over `CleanLaunch`: the engine's user, the work tree as the working directory, the engine's search path and an environment that keeps only `HOME`, `TMPDIR`, `USER`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TERM` and `TZ` of the engine's own (no `AWS_*`, no model pin, no proxy or harness variable). The environment is a scrub, not isolation: a child runs as the engine's user, or, in the `landlock` mode, in the engine's Landlock domain (`CleanLaunch` carries the sandbox through `with_sandbox`).
  - The registration file (`tools/register.rs`). The engine reads its tool servers from the file at the first prompt of each session, rewrites it after every connect and goes on without the tools when it is missing or unreadable, so the file is in a directory the engine owns, and the module keeps it right. It is written, and written again, without ever following a link the engine planted (agentd is root, the engine has a shell as the file's owner): the root directory (the engine's data or configuration directory, which agentd made under a directory only root can change) is opened once before the engine runs and the handle is kept; the directories below it are walked with `openat` and `O_NOFOLLOW | O_DIRECTORY`; the new text is written to `<file>.agentd-new` created with `O_EXCL | O_NOFOLLOW`, handed to the engine's uid and gid (`fchown`, only when it is not already theirs) and put in place with `renameat`, which replaces a file, a link or an empty directory without opening it. Stale files are removed with `unlinkat`, which unlinks a link and does not follow it. A file is "right" when it is a regular file, not a link, the rendered bytes, owned by the engine's user and group and readable and writable by its owner. It is checked at the first `PromptSent` of each session (raised just before the prompt is written, so before the engine reads), at `SessionEnded` and at `EngineStopped`; a wrong file is replaced, a right one is not touched (its modification time stays). At `EngineStopped` only (the engine's process group was killed, and the event comes before the new process starts) the `<file>.lock*` and `<file>.tmp.*` files the engine's lock left are removed too, at most 4,096 directory entries looked at: the lock of an engine that still runs belongs to it. Errors are words with no path (`registration could not be restored (<word>)`). The checks run inline in `on_event` (a few system calls on local disk). The engine can still write the file between two checks, which it owns; nothing here is a boundary against the engine.
  - The connect check (`tools/connect.rs`). The clock of a session starts at its first `PromptSent` (the engine connects at the prompt; `session/new` returns in 5 ms). After the window, 30 s, one word is recorded from what the server's counters show since the clock started: `none` (no `initialize`, no `tools/list`), `handshake-only` (an `initialize` and no `tools/list`: the failure of a read-only directory and of a 500 on `initialize` look like this) or `ok`. The summary keeps the worst word over the sessions that were judged. The counters are the one server's: sessions are strictly one after another in a run, and anything that calls the loopback, the engine's shell included, counts, so the word is what the server saw, not a proof of what the engine did. A clock that is still inside its window when its session ends or the engine's process is stopped is judged only if the tools were already listed (`ok`) and is otherwise closed without a word: an engine that went away did not get its window, and a short run is not called a failure. At the end of the run (`on_shutdown`) the same rule applies to every open clock. Each word is logged once (`direct tools connect <word>`).
  - `on_shutdown` runs for every ending, a startup refused by a later module included: it aborts the timers, stops the server, and only then reads the counters for the note, so what the server counted is final. `on_summary` copies the note into `DirectSummary.tools`: `enabled`, `reason` (a word; set also for a server that stopped for good, `restarts-used`), `port`, `connect`, `list` (bare tool names) and `counts` (`calls` per tool, `failed`, `refused`, `truncated`, `restarts`, `p50Ms`, `p95Ms`). Words and counts only.
  - Order: right after `research`, which sets `HAMH_CONTEXT_DIR` and `HAMH_RESEARCH_URL` in the engine environment before the tools are built, and before `attachments`, `engine_config` and the modules after them. None of those reads `HAMH_TOOLS_URL` or the registration file. A later module that refuses the run leaves the port bound for the time between its refusal and the shutdown, which stops the server (`crates/agentd/tests/direct_tools_mcp_run.rs`).
- `tools/rg.rs` and `tools/confine.rs`: the `code_search` backend (`CodeSearch`) and the confinement of its `paths`.
  - Process: ripgrep (`rg`, 14.1.1 in the worker image) is started through `ToolContext::launch_spec` (the engine's user, the scrubbed environment, the engine's search path), in its own process group, with `--json --no-config --no-follow --max-filesize=2M --sort=path --case-sensitive --max-count=<maxPerFile + 1>`, `--glob=!.git` first, `--glob=<g>` and `-e <pattern>` as single arguments (a value that starts with a dash is never a flag) and the resolved paths after `--`. `filesOnly` runs `--files-with-matches --null` and `count` runs `--count --null --with-filename` (they have no `--json` form; `--max-count` is left off so a count is exact). A pattern with a line end is `error: usage: pattern: must be one line` and starts nothing.
  - Failures: the standard error of ripgrep goes to `/dev/null`, because ripgrep repeats the pattern and the paths in its error text and none of that may reach a log, a counter, an answer or a file. A failure is a fixed phrase chosen from the exit status and from the `summary` message: exit 0 or 1 is an answer (`no matches` when there is nothing); exit 2 after a `summary` or with entries is the answer plus `[search incomplete: some results may be missing]`; exit 2 without either is `error: usage: pattern or glob: not accepted by ripgrep ...`; 126 or 127 is `error: unavailable: ripgrep could not be started`; a signal nobody sent (an out-of-memory kill) is `unavailable`. Limits: 10 s of wall time (the group is killed, `error: timeout`), four at once (the fifth `error: busy`; the server's own limit is eight), one `--json` message of at most 4 MiB (a longer one is skipped and counted in a note), the group killed on a cancel and when the future is dropped.
  - The answer: matches are `path:line:text` in `--sort=path` order, so the same call returns the same first matches; context lines are `path-line-text` with `--` between groups; a line over 300 characters is a window of 300 that holds the first match, with `…` at a cut end; control characters other than tab are U+FFFD; text that is not UTF-8 is shown lossily. Paths under the work tree are relative to it, paths under the context directory are absolute. The total is `maxResults` matching lines (default 50) and `maxPerFile` per file (default 10; ripgrep is asked for one more per file, so a file that has more is known and said once in a note). Context lines belong to the nearest kept match, so a match past the per-file cap takes its own context with it. The text is held to `ANSWER_BUDGET` (7,000 characters of the serialized form) and units (a match with its context) are never cut in half, so the server's cut at 7,500 never removes the note that says why an answer is short; the first unit is always shown. Notes are lines that start with `[` and name `maxResults`, `maxPerFile`, the size limit, a message too long to show, or an incomplete search. The `count` mode ends with `total: N matching lines in M files`.
  - Confinement (`confine.rs`): each `paths` entry is resolved before ripgrep sees it, against the work tree when relative and against the work tree or the context directory (`HAMH_CONTEXT_DIR`) when absolute (compared by components; an absolute path may use the root as given or canonical). The rule is the kernel's `RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS` inside ONE root: `..` may rise to the root and no further, a link is followed when its target is relative and stays beneath, an absolute link target is refused even when it points back inside, a loop (over 40 links) is refused, a link from one root into the other is refused, a file in the middle of an entry cannot be walked through and a trailing slash on a file are both a missing path. `Strategy::Openat2` asks the kernel (Linux 5.6 or later, and a filter must allow it; the resolved path is read back from `/proc/self/fd`), `Strategy::Walk` is the same rule in user space, and `Auto` (what the tool uses) tries the kernel and walks where it is not available; a test holds the two to the same answer on a generated set of entries. The entries are sorted, deduplicated and without any path inside another, and ripgrep gets the canonical paths. Refusals are `error: refused` (outside, or not openable) and `error: usage` (missing) with a fixed phrase that names no path. The confinement is the tool's contract and a second line of defence: ripgrep runs as the engine user, whose shell reads the same files, so a link swapped between the check and ripgrep's own open crosses no boundary.
- Tests: `crates/agentd/tests/direct_tools_server.rs` (the transport and the supervisor, through sockets with a client that starts no process), `direct_tools_result.rs`, `direct_tools_settings.rs` (settings, the backend seam, the counters), with `crates/agentd/tests/tools_support/`; the hook: `direct_tools_register.rs` (the file, the restore, the links), `direct_tools_connect.rs` (the words and the clocks), `direct_tools_off.rs` (the kill switch, a profile without the table, the disable list, the list), `direct_tools_summary.rs` (the note and the log), `direct_tools_mcp_run.rs` (whole runs with the fake engine's MCP client) and `direct_hooks_standard.rs` (the order), with `crates/agentd/tests/hook_support/`. `ToolsHook::start_with` takes the run's directories and the backends as values, so most tests drive the module without the driver, and `crash_server_for_tests` and `stop_for_tests` are hidden test hooks. ### Interrupt

`HookEnv.ctl: DriverCtl` is what a module may ask of the driver while a prompt is open. `ctl.interrupt()` cancels the `session/prompt` that is open
now and returns `true`; it returns `false`, and queues nothing, when no prompt is open (between prompts, during a retry wait, while a fresh session is
set up), so a message then goes by the next turn end. `ctl.prompt_open()` says whether one is. The client (`acp::Interrupt`,
`AcpClient::with_interrupt`, installed only when a module is registered) does the rest:

- It writes `session/cancel` once for the prompt, however many interrupts are asked, and waits for the prompt's own answer for the grace (10 s,
  `CANCEL_GRACE`). The user's cancel (`ham stop`) is a different thing: a latch that is never reset and ends the run. When both are up the user's cancel
  is the one written, there is one `session/cancel`, and the run ends as the user's stop; a vote that comes back after the user's cancel is dropped.
- The activity record marks the prompt `interrupted` as well as cancel-sent (so the engine's `cancelled` answer is the one asked for, it is not read as
  the engine's own brake, and no nudge follows). The next prompt and the next stage clear both.
- When the stage ends, `on_turn_end` is called with `TurnEnd.interrupted = true`, whether the engine answered (`raw.watched` is `Done(Ok)` with stop
  reason `cancelled`) or did not within the grace (`Done(Err(CancelIgnored))`; the engine may still be busy). The module decides: `Prompt(text)` sends its
  text in the same session as an instruction attempt; `Stop { detail }` ends the run. A module that returns `Done` after an interrupt gets the end the
  driver reads from the facts, which is "stopped by the user" (the cancel was agentd's), so a module that interrupts always answers.
- The module's part: claim the message with worker-api before calling `interrupt`; reap the tool processes the engine's tools
  started in their own session (a cancel leaves the engine and its tools running; `EngineStopped` covers a killed engine, not a cancel), within its
  own bound, before it votes; demote the message to a next-turn delivery when the grace runs out and quarantine the session; count its interrupts and
  serialize them; keep the `/now` text confirmation in the client. The decision's own bound is `Limits::decision` (120 s) per call.
- `slice.rs` reads the `slice` member of the invocation. A later session restores the repository from the bundle or snapshot the plan names; `Restored::check` refuses to start the engine unless the repository is at `restoreHead` and `baseSha` is an ancestor of it. `first_prompt` is the fresh-session prompt of a later session: the task, the facts of the repository and the earlier session's last message quoted as data. A session that is not the last ends at its prompt deadline as a handoff: it commits, bundles, uploads and says `handoff: true` in `turn-complete`; its label is unchanged. Changed-file counts, the no-changes label, the review round and the summary use the run's original base, which is the DOX starter commit when `dox::settle` found or made one on top of the original head. `sessionsBefore` keeps the `new-session` events counting across sessions. Tests: `crates/agentd/tests/direct_slices.rs`.

## Work Guidance

- To fill a module: write the failing test first (a fake plane and fake engine through `Deps.hooks` or `Hooks::new`, as `crates/agentd/tests/direct_hooks.rs`
  does), save the red output, then fill `hook()` and the module. Implement only the hooks the module needs. Keep a module's state inside the
  object `hook()` returns (interior mutability); the driver gives it no other place.
- A module that changes what a run says (an event, a field, a log line) re-records the golden files it touches in its own commit
  (`GOLDEN_UPDATE=1 cargo nextest run -p agentd --test direct_golden`) and gives the reason in the message. A module must not change them when it
  is switched off by its own setting.

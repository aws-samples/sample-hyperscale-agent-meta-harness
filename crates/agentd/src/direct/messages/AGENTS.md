# crates/agentd/src/direct/messages


## Purpose


- **Message control.** agentd, the message queue owner, sends each user's message separately. Each message gets its own engine prompt turn.
- **Queue owner.** agentd sends exactly ONE session/prompt at a time.
- **Engine queue.** Never use the pinned engine's internal queue.

## Ownership


- **Parent contract.** crates/agentd/src/direct/AGENTS.md owns this module's boundary.
- **Hook order.** Hooks::standard registers this module last in hooks.rs. Pending messages beat another module's continuation. An earlier module's Stop is final before any claim.
- **Edit boundary.** Edit only this directory and crates/agentd/tests/direct_messages_*.rs. The fake engine in crates/ham-e2e, src/fake_cline.rs, is also allowed.
- **Control plane.** IM2c, the control-plane helper, owns routes and DynamoDB items. It owns protocol types in crates/harness-protocol/src/messages.rs.
- **mod.rs.** Contains hook settings, state, and DirectHook implementation.
- **types.rs.** Defines Mode, Notice (hand-out without text), and Message (claimed with text). Defines the ten States, RejectReason, FailReason, Refusal, and ClaimOutcome. Also defines SealMode, SealOutcome, and StoreError.
- **store.rs.** Defines MessageStore, the store trait, and MemoryStore, the in-memory server model. Every module test uses MemoryStore, including fault injection. `MessageStore::delivered` is the read of the run's delivered messages, which also names the claims without a report of the delivery (`History::unconfirmed`); the model answers both from its own states (`delivered`; `dispatching` and `delivery-unknown`) and can lack the route (`without_history_route`), fail it (`Op::History`) or delay it.
- **http.rs.** Defines HttpMessageStore, the four signed internal API routes and the read `POST /internal/message-history`. Defines notice_of, the PendingControl::Message reader.
- **machine.rs.** Defines Queue and Budget.
- **earlier.rs.** Defines Earlier, the record of the delivered messages, and Log, which keeps it in the machine and in the run's bucket. Defines `ask_service` and `Ask`, the question to the control plane for the messages delivered in earlier sessions and its bound, and `Fallback`, why a session read the bucket's record instead. Defines `fetch_newest_again`, the look at the records of the turns before, with `Again` and `AskedAgain`: the further GETs of the first record whose read failed for a moment.
- **reap.rs.** Defines Reaper, the engine process finder and killer.

## Local Contracts


1. **One prompt at a time.**
   - Send only through TurnVote::Prompt, the prompt vote, at on_turn_end or on_seal. Never claim or send while a prompt is open.
   - If the driver already sent a nudge, log "a prompt is open". on_turn_end and on_seal vote Done. A message during that nudge waits for the next turn end.
   - Give each message one turn, in order. Send `now` messages first.
   - The helper chose separate turns over joining messages into one prompt. This keeps "delivered (turn k)" exact for each message. Each claim and withdrawal concerns one message.
2. **Claim before send.**
   - on_turn_end takes the next hand-out. Report the session first if the store lacks it. Claim by id with POST /internal/message-claim.
   - The answer carries text and an attempt number. Only then return Prompt(text). Losing a claim costs nothing.
   - Loss causes include withdrawal, a hold, queued cancel, or another session. Repeat a claim whose answer was lost. The repeat finds the same claim.
   - An unanswered claim marks doubt; the plane may have applied it. An unanswered store request never holds the run. The vote is Done.
   - Before sealing and at close, resolve doubt through MessageStore::held, the held-message lookup. This claims without a message id. With no held messages, the plane claims the next pending message.
   - The plane returns every message this incarnation holds in dispatching. It returns Held { message, redelivered, current_session } with the same attempt. This also applies after the session changed.
   - Take over an unknown held message belonging to the current session. Send it before sealing; at close, fail it with not-sent. Never end that message as delivery-unknown.
   - Release a returning claim belonging to an older session. The control plane holds it until the user confirms a copy. Never resend a returning claim already voted or sent.
   - Fix the deadline at turn end; reread remaining time before dispatch. Release the claim when less than 300 s remain. Release an unsent vote when the session changes.
   - Settings.decision_cap, the decision time limit, stops searching after 90 s. The driver cuts a module off at 120 s.
   - A never-claimed rejection carries attempt 0. A rejection after release carries its last claim's attempt. Every other outcome carries its claim's exact attempt.
   - A release rejected for the closed run returns 200 on repeats. HTTP 409 stale-attempt and bad-transition are final. Never repeat them.
3. **Acknowledge on send.**
   - PromptSent, the send event, carries the claimed text. Text and session id must match the claimed message. Record submission through POST /internal/message-outcome kind submitted.
   - Set turn = the prompt number. The message becomes "delivered (turn k)".
   - The retry ladder may resend the same text. This remains the same delivery in the same turn.
   - A claimed message never sent ends failed (not-sent). Record that result at shutdown.
   - Keep unposted submitted, failed, release, and reject outcomes as owed. Retry them at the seal and the close. A rejection waits behind the same message's release.
   - A delivered message joins the record of the run. The first prompt of a session that follows carries the record. Tell the record inside the `PromptSent` event, with the session's number; the record adds the turn. The record and its file are written before the event returns, because the engine can be replaced a moment later and the fresh session's prompt is written at once; only the bucket follows from a task of its own. A ladder resend of the same text and a prompt of another module add nothing. on_startup makes the log (`Log::for_session`); a later session asks the control plane there for the messages that were delivered in the sessions before it, before its first prompt is written. The close waits for the write in flight and the newest record behind it: 2 s to 10 s, within the 15 s a module has at the end (`earlier::flush_bound`). on_finalize waits up to 5 s more. A session that could not read the earlier sessions' record marks its own `incomplete`; a later session then looks further back. The look gives each record one GET; the first record whose read fails with an answer that may be another one a moment later (a 5xx, a throttle, no whole answer) is asked for again after the look. Keep the further GETs after the look: asked at the place of the failing GET, their pauses stand in front of the older records, and a look that runs into the limit of its read loses what it read. The harness vouches for two things: what the control plane answered and what its own process delivered. `Earlier::from_history` builds the record a session starts with from the control plane's answer (`MessageStore::delivered`: the ledger's `delivered` messages in its order, each with its id and its stored text), `Log::delivered_message` records a delivery with its id, and both carry `inherited` false. `fetch_newest` marks every message read from the bucket `inherited` whatever the stored bytes say (the engine's tools can write that prefix) and drops its ids, and `Earlier::block` gives the first kind under `BLOCK_HEAD` (the user's own words) and quotes the second as data under `RECORD_HEAD`. Never give a text read from the bucket the standing of the task.
   - The bucket's record is the fallback and nothing else. `ask_service` returns an answer at once, and so the explicit answer that the control plane has no such route (`HistoryError::NoRoute`: a 404 of worker-api with the code `not_found`, a 404 with no error body of the service, a 405 (the path belongs to something that takes no POST there, as on the four message routes), or the gateway's answer to an unknown resource, a 403 whose `message` is exactly `Missing Authentication Token`; it marks no other route unavailable; a 404 of the service for another reason and a 403 that is a refusal are failures). Any other failure (no answer within `Ask::limit`, a refusal, a failed store, an HTTP 200 that is not the answer) is asked again, `Ask::tries` times in all with pauses of `Ask::pause` and twice that: 3 questions of 5 s and pauses of 1 s and 2 s, 18 s at most (`Ask::bound`). Only then, or after `NoRoute`, is the record read (`Fallback::Unanswered`, `Fallback::NoRoute`), and the log and the first prompt say which (`NO_ROUTE_LINE` before the quoted record, `NO_ROUTE_NONE_LINE` when the record shows no message, `NO_ROUTE_ONLY_LINE` followed by the line on the unread record when the record could not be read; `UNANSWERED_LINE` also when there is no message to show). A question that failed is never an empty history. When the control plane answered, the bucket's record is neither read nor shown. `AGENTD_MESSAGES_EARLIER=record` (`Source::Record`) asks nobody and quotes the record without a word on a fallback.
   - Handed over, not confirmed. The answer also names the messages the ledger holds as handed to an earlier session with no report of their delivery (`History::unconfirmed`: `dispatching`, or `delivery-unknown` once the session after it has reported itself). `Earlier::from_history` puts them after the delivered ones with `Said::unconfirmed` set, and `Earlier::block` shows them after the delivered messages under `UNCONFIRMED_HEAD`, each with the label `(handed to an earlier session, not confirmed as delivered)`: the control plane's texts, so the user's own words, which the earlier session may or may not have read. The file of the machine keeps the mark; a record read from the bucket never has it (`Earlier::as_inherited`). The bucket's record is not read beside an answer.
   - No message twice. A message sent to this session is claimed and sent as a prompt of its own, and one that waited in an earlier session is `held` by the control plane until the user confirms it and is in neither part of the answer. A delivery takes the place of a record entry with the same id (`Earlier::push_message`). An id the answer names in both parts is taken as delivered. Ids alone decide, in the answer (`from_history`) and in the record (`push_message`): two messages with the same text and ids of their own are two messages, and each is shown in its part. Words the user sends again are delivered as a message of their own, and an unconfirmed entry that holds the same words stays in the record. A message whose `submitted` report never reached the control plane is never called delivered: the ledger holds it as `dispatching`, turns it into `delivery-unknown` at the next incarnation's session report and sends it again only when the user confirms it. One window stays open: a worker the control plane has replaced that is still alive can claim a message after the new session's question; that message is not in this session's first prompt and is in the answer a later session gets.
   - Every message of the block, of either kind, stands in a fence one backtick longer than the longest run of backticks in any text shown, so a text can neither close its fence nor write a line that reads as a label or a heading of the harness.
   - The file of the machine is this process's own: `Log::start` writes it from what the session starts with, also over a file an earlier process left (a record with no message replaces such a file and is not sent to the bucket). The file is written also when the session starts with no message and a record that could not be read or a count of cut messages (`Earlier::try_parse` keeps `incomplete` and `cut` of a record with no message), so the first prompt, which is built from the file, says so. With the module off (`messages::hook_with` with `enabled` false) no log exists, and `earlier::forget_local` writes a record with no message over a file an earlier process left, so nothing is shown. `messages::hook` reads the settings from the environment and calls `hook_with`; `messages::module` is the module on a given store, or none when the settings switch it off. The context directory is one the engine reads and cannot change (root-owned 0755 with files of 0644 where the engine has its own user; a read-only grant of the Landlock domain where it has none).
   - Named exceptions outside this directory are listed in `crates/agentd/src/direct/AGENTS.md`. Tests: `b857_a_delivered_message_joins_the_record_of_the_run_and_no_other_prompt_does` (`direct_messages_hook.rs`), `b857_earlier_messages.rs`, `b857_earlier_sessions.rs`, `b857_trusted_messages.rs` (the record from the answer, the frame, the cap, the ids, the question's bound, the fallback's words, the file of the machine, the two switches, the unconfirmed messages and their frame, a record that could not be read), `b857_history_http.rs` (what each answer of the route means, the unconfirmed part and no message twice) and `b857_trusted_sessions.rs` (whole sessions in a new machine: the answer, a plane without the route, a plane that fails or never answers, a pending message, the switches, a session lost between the hand-over of a message and its report, words the user sends again, a record that does not read).
4. **Seal.**
   - on_seal atomically checks pending messages and closes an empty run. Use POST /internal/message-seal, mode normal.
   - Pending messages return as the next prompt. No pending messages means admission closes.
   - Use limit-reached when the continuation allowance is spent. Use terminal when less than 300 s remain.
   - Before asking, wait for interrupt claims and acknowledgements in flight. Post every owed outcome first. Resolve claim doubt before asking.
   - Normal or limit-reached seals return 409 bad-transition while messages dispatch. They also refuse while agentd owes a claimed message's outcome. This includes user cancel; response text names the message ids.
   - A refused seal ends the vote with Done. The close settles the message. The terminal seal does not wait and changes dispatching messages to delivery-unknown.
   - Pending messages may return but remain unsendable twice in a row. The third seal is terminal. Those messages end rejected as run-sealed.
   - on_shutdown and on_finalize use an idempotent terminal seal. Later messages receive 409 run-sealed. They store nothing.
   - The close has a 12 s budget. Each call makes one bounded attempt. First, stop the engine's processes within 2 s.
   - Then wait up to 3 s for an interrupt claim. Allow acknowledgements in flight 2 s to reach the store.
   - Resolve doubt and fail claimed messages never sent with not-sent. Retry every owed outcome. Finally, attempt the terminal seal up to two times.
   - Once close starts, no interrupt begins. Leave returning claims for the close. After user cancel, close asks only for the terminal seal.
5. **Epoch.**
   - The epoch is the ACP session id from Event::SessionStarted. Report it through POST /internal/message-session before any claim.
   - A session report carries its number. Repeat that number unchanged on a retry.
   - Older-session messages leave the queue until the user confirms a copy. The control plane holds them. A model change creates no session and holds no messages.
6. **Continuation.**
   - Governs this allowance. It starts at the first done-looking stop, end_turn.
   - Count no message-driven turns and limit no extra execution by default. Keep 300 s before the run's deadline. That deadline already includes the 900 s delivery reserve.
   - A stage may set `AGENTD_MESSAGES_MAX_TURNS` and `AGENTD_MESSAGES_MAX_EXEC_S`. Check an execution limit before starting another turn. Once spent, start no new turn. Do not cut short the turn in flight.
   - Messages beyond a limit a stage set end rejected (continuation-limit). Deliveries before the first done-looking stop do not count.
   - Charge an unanswered message turn when its session ends. Also charge it when another prompt replaces it. allowance(), the allowance report, reports turns and time.
   - Another stop or model change does not reset the allowance. Neither does an interrupt or an answer. Tests: `a_model_change_an_answer_and_a_new_session_leave_the_allowance_where_it_was` (`direct_messages_hook.rs`: after 3 turns a model switch, an answer and a new session change nothing and the ninth message is rejected for the limit), `interrupts_count_against_the_allowance_and_the_limit_still_holds_after_them` and the turn counts of the sixth-interrupt test (`direct_messages_e2e.rs`).
7. **/now.**
   - Aim the interrupt at the prompt number open when requested. If another prompt is open when the claim returns, write no cancel. Send the message at the next turn end.
   - A stage ending on its own clears a pending interrupt. Send one session/cancel. The client waits for the prompt's own answer.
   - Measured waits were 0.19 to 0.48 s. At stage end, on_turn_end checks TurnEnd.interrupted.
   - Reap the engine's tool processes, then vote the new message prompt. Cancel kills the shell but leaves processes the shell started.
   - Serve interrupts one at a time. Allow at most 5 per run. An active interrupt or quarantined session prevents another interrupt.
   - An unsafe cancel or no open prompt also prevents it. Send that `now` message at the next turn end.
   - A `now` message that found no prompt to interrupt goes out at the next turn end, and its user is told. No prompt is open while the engine works through the goal plugin's follow-up rounds, between two prompts, during a retry wait and while a session is set up: `offer` starts no interrupt then. `next_message` writes the user notice below when it claims and votes a message that is still `now`, at the first ask of a stop as at a later one. The interrupt flow writes it for a message it claimed when the prompt it was aimed at had ended or another had begun. A message is told once (`Run.told`), whichever path writes the notice first. Tests: `b857_now_claimed_at_the_first_ask_of_a_stop_cancels_nothing_the_user_is_told_and_the_engine_is_kept` and `b857_now_claimed_at_a_later_ask_of_a_stop_cancels_nothing_the_user_is_told_and_the_engine_is_kept` (`b857_now_in_follow_up_rounds.rs`: the real message module and the real goal module in the real driver against the engine simulator, scenario `goal_message_in_round`), `b857_a_now_message_that_found_no_prompt_open_goes_out_at_the_turn_end_and_the_user_is_told_once` (`direct_messages_hook.rs`).
   - The allowance is checked before anything else. When it is spent, a `now` message is refused at once with `continuation-limit`, without a claim and without a `session/cancel`: the turn that is running keeps its work, the engine is not resumed with the "interrupted" sentence, and the user gets no promise of delivery (the row shows the refusal). Tests: `a_now_message_beyond_the_allowance_is_refused_and_the_running_turn_is_not_cancelled` (`direct_messages_e2e.rs`), `a_now_message_beyond_the_allowance_is_refused_at_once_and_interrupts_nothing` and `the_allowance_decides_before_the_other_reasons_a_now_message_cannot_interrupt` (`direct_messages_hook.rs`). The time left is not known at that moment, so a message that comes too late is still refused at the turn end.
   - Every other `now` message that cannot interrupt (the 5 interrupts are spent, the session is quarantined, the cancel is unsafe, or an interrupt is under way) writes no `session/cancel`, becomes a `next` message at the head of the queue, and gets the user notice below. The log line names the reason. Test: `a_sixth_interrupt_is_not_made_the_message_goes_out_after_the_turn_and_the_user_is_told` (`direct_messages_e2e.rs`: five cancels and no sixth, delivered as prompt 8, one notice, no needs-input question).
   - CANCEL_GRACE, the cancel grace period, is 10 s. Missing acknowledgement or surviving engine processes demotes `now`, an interrupting message, to `next`, delivery after this turn, retaining its claim. agentd writes the user notice (`turn.progress`, kind `notify`, reason `message-not-interrupted`) with detail "could not interrupt; delivered after this turn".
   - Kill covers the engine and every process of its family. New prompts remain blocked until the driver starts a fresh session. The message goes first after the restart turn, once without confirmation; no needs-input question opens, and the interrupt counter remains unchanged at 5 per run.
8. **User cancel stays final.**
   - Once the user's cancel is up, claim nothing. Close with run-cancelled. A Cancel beats messages in the same batch.
9. **Tripwire.**
   - Detect end_turn with usage 0 and no session/update since the prompt. The answer must arrive within 2 s. This indicates the engine's own queue.
   - Never call that result a done label from the engine. Mark the session cancel-unsafe.
   - Kill the engine and its family. Vote the resume sentence so the driver starts a fresh session.
   - One answer of that shape is expected and trips nothing. A message voted while `TurnEnd.engine_working` is true goes to an engine that works by itself, through the goal plugin's follow-up rounds. The engine takes the message behind the round it is working on and answers the request at once. For a message voted in that state, `end_turn` with usage 0 alone is that answer: the engine goes on writing the updates of the round in progress, and a busy engine may answer after the 2 s window, so neither is asked (`b857_a_message_taken_behind_a_round_that_streams_is_sent_again_when_the_engine_is_idle`, `b857_a_message_a_working_engine_answered_late_is_sent_again_when_the_engine_is_idle`). Keep that engine, write one log line, and leave the session's cancel as it was. A prompt of another module in that state, and a message voted to an idle engine, are judged as before. A ladder resend of the message is judged as a prompt to an idle engine too: no poll stands behind that send (`b857_a_resend_of_a_message_by_the_ladder_is_judged_as_a_prompt_to_an_idle_engine`). Tests: `b857_a_message_the_engine_queued_behind_its_own_round_is_not_a_tripwire`, `b857_the_same_answer_to_a_message_sent_to_an_idle_engine_is_still_a_tripwire` and `b857_a_prompt_of_another_module_while_the_engine_works_is_judged_as_before` (`direct_messages_hook.rs`), and the three runs of `b857_now_in_follow_up_rounds.rs`, which also show that a `next` message takes the same path.
   - A message the engine took behind a round is remembered until the engine began a run after it took the message. `Inner::runs_begun` counts the start lines of the observer's log of the engine's runs (`Wiring::rounds`: the `rounds_file` of the engine's goal table, in the engine's data directory). The engine's user writes that file, so it only steers. A count is given only when a read reached the end of the file (one call reads at most 2 MiB): a count of part of the log is no count, because the lines a later call reads would look like runs begun since (`b857_a_log_of_runs_too_long_to_read_at_once_does_not_settle_a_message`). The count is taken when the queued answer arrives. When no module says the engine works by itself (`on_turn_end` with `engine_working` false, and `on_seal`), `Inner::unread` settles each message the engine began a run after, one run for each message in front of it, and votes the first of the others again as an ordinary prompt: the round it arrived in ended the engine's loop, so the engine cannot have read it. A message nothing counts runs for is voted again too. The second send is the same delivery: no claim, no acknowledgement, no entry of the record, one message turn of the allowance, and an answer judged as a prompt to an idle engine. A new session drops the list, because its first prompt carries the record. A message that cannot go out again (the run's time, the allowance) gets the user notice `message-not-read` with detail "not read; the run ended before this message was reached". Tests: `b857_a_message_taken_behind_the_round_that_ends_the_loop_is_sent_again_to_the_idle_engine_and_read` (`b857_now_in_follow_up_rounds.rs`, scenario `goal_message_in_last_round`), and in `direct_messages_hook.rs` `b857_a_message_taken_behind_a_round_is_sent_again_when_the_engine_is_idle_and_began_no_run_since`, `b857_a_message_the_engine_began_a_run_after_is_not_sent_again`, `b857_the_runs_the_engine_began_before_it_took_the_message_do_not_count`, `b857_two_messages_behind_one_round_need_a_run_each`, `b857_a_new_session_is_told_by_the_record_and_nothing_is_sent_again` and `b857_a_message_that_cannot_go_out_again_is_named_to_the_user_as_not_read`.
10. **Kill path.**
    - Tool processes survive killing the engine's process group. A shell tool runs in its own session. A command that forks and exits leaves its child to init.
    - on_startup sets AGENTD_ENGINE_TAG=<random>, the engine process tag, in the engine's environment. Reaper finds every process carrying that tag through /proc.
    - Reaper reports unverified when /proc cannot be read. Accept an empty family only after two consecutive empty scans.
    - The container runtime is out of every scan and reap. Its front runs as the engine's user and Podman's service as the namespace's root, which is that user on the host, so the sweep would stop both when the engine ends and the test report would find a socket nobody listens on. `Reaper::protect_pid` marks a process by pid and start time; `on_startup` marks the pids in `StartupCtx::runtime_pids` (named by `ham-containers up` before the engine exists), and a scan leaves a marked process and everything below it, whatever other mark it carries. A marked process that is gone, or whose pid another process holds, protects nothing. The log line of the engine-stop reap names what it stopped; a process name is text the engine's tools choose, so the line writes every character that is not plain printable ASCII as an escape (`reap::killed_list`). Tests: `crates/agentd/tests/b765_runtime_reap.rs`, `crates/agentd/tests/b765_runtime_pids.rs`.
    - AGENTD_ENGINE_USER, the engine user setting, controls the microVM user-wide sweep. sweep_uid, the user-wide sweep, requires both users to be known. agentd's user and the engine's user must differ.
    - In the landlock mode (`StartupCtx.sandbox` is set, `Reaper::for_run`) the engine has no user of its own, and a tool that runs with an empty environment (`env -i program`) and is left to init escapes the tag. Two more marks count then. A process with more seccomp filters than agentd: the launcher installs one filter on the engine, the kernel keeps it through fork, setsid, a double fork and exec, and `Seccomp_filters` of `/proc/<pid>/status` (Linux 5.9 and later) counts it; agentd's own helpers have agentd's count. And a child of any process of the family, which finds a tool where the kernel reports no count. Both read the machine and not the run: right where one run owns the machine (the Instances machine), wrong beside another sandboxed run. So they are off for the uid mode, for a run with no sandbox and for tests that do not ask. agentd is not made a subreaper: an adopted orphan stays a zombie after the kill, because the runtime owns the waiting for agentd's children and a `waitpid` of agentd's own would take their exit status. In a session's microVM the first process of the machine collects what is handed to it; agentd works behind it and is still no subreaper.
    - Sandbox marks read the seccomp filter count and parent chain from `/proc`. Processes with more filters than agentd count as engine processes regardless of user; filtered host services of other users cannot be stopped and keep `Report::remaining` nonempty. `real_processes::a_tool_that_scrubs_its_environment_and_is_left_to_init_is_gone_after_the_reap` in `crates/agentd/tests/direct_messages_reap_sandboxed.rs` reruns itself inside `unshare --user --map-root-user --pid --fork --mount-proc` and asserts that it is process 1 and `/proc` lists only its own processes; the reap cannot see or stop host processes there. The tool's pid is in its file as soon as the shell has forked, two execs before the tool has scrubbed its environment, so the test waits for the empty environment inside the 20 s the tool has to start in. `real_processes::b836_a_tool_whose_pid_is_known_before_it_scrubs_its_environment_is_waited_for` holds the gap open until the test has seen it. Missing or refused `unshare` leaves the test on the machine's `/proc` and prints `NOT ISOLATED`. The `seccomp-children` group in `.config/nextest.toml` runs every `sandbox_*` test binary and `direct_messages_reap_sandboxed` one at a time.
    - mark_engine, the engine identity marker, records its pid and start time. Mark that identity when a session starts. Keep the engine by that identity.
    - Being agentd's child does not identify the engine. Orphaned tools reparent to agentd when agentd is the machine's init.
    - Never list zombies or agentd. Repeat scans and kills until a scan is empty. Bound the repeat.
    - Reap after an acknowledged interrupt; keep the engine. After an unacknowledged interrupt or tripwire, kill the engine too.
    - Unverified removal makes on_turn_end vote Stop ("could not be stopped"). Stop before sending another prompt beside those processes. Confirmed removal allows the resume sentence as before.
    - Reap on every EngineStopped event and at shutdown. Finish before the end commit and the bundle.
11. **Fencing.**
    - Every agentd process makes a new generation through http::new_generation(). Its ULID is later than any this process made before.
    - The plane replaces an older incarnation with an unseen generation. It refuses one more than 60 s older under GENERATION_CLOCK_SKEW_MS. A replaced incarnation receives 409 stale-generation on every route.
    - HTTP 409 stale-generation or stale-epoch makes the store unavailable(). The module makes no further calls. The server model also reports replaced worker generations as unavailable().
    - HTTP 404 on a message route means no plane message control. This also marks the store unavailable. The module stays out of the run; the run remains unharmed.
12. **Text limits.**
    - No harness text says a run is verified. Logs name ids and sizes. Never log message text.

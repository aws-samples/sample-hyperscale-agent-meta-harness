# crates/agentd/src/sandbox

## Purpose

How the engine is kept out of agentd's memory and private files. The microVM runs agentd as root and the engine as a second user (`uid` mode). The Instances container has no capabilities, so there is no
second user: the engine runs in a Landlock domain and agentd is non-dumpable (`landlock` mode). The outcome is the one of root invariant 2 (the package-registry token and any long-lived credential never reach the engine); the mechanism differs. By default the engine there runs as the user nobody in user and IPC namespaces of its own; invariant 2 is kept by the same domain and filter.

## Ownership

`crates/agentd/AGENTS.md` owns the crate contract. This directory owns the mode, the policy, the installer and the launcher. The wiring is in `crates/agentd/src/engine/mod.rs` (`LaunchSpec.sandbox`, `command_argv`), `crates/agentd/src/direct/mod.rs` (mode check, policy,
launch specs), `crates/agentd/src/direct/hooks.rs` (`StartupCtx.sandbox`, `CleanLaunch`), `crates/agentd/src/direct/report/` (the report's steps start in a sandbox of their own folder) and `crates/agentd/src/direct/goal/` (the evidence of a running command below the engine's process).

## Local Contracts

- **The mode is the deployment's** (`mode.rs`): `AGENTD_ENGINE_SANDBOX` is `uid` or `landlock`. Unset, empty, `auto` or anything else is a refusal that names the variable, and no engine starts: the run ends `stopped_setup_failed` before anything is fetched. `landlock` needs `AGENTD_ENGINE_USER` empty (a conflict is a refusal). `AGENTD_ENGINE_IDENTITY`, read in the `landlock` mode only, turns the nobody route on (unset, blank or `nobody`, the default) or off (`agentd`); any
  other word is a refusal of the same kind. The mode is no `ham config` setting: invariant 2 is locked and no setting may change it. Both runtime settings are the infrastructure change, which has to be deployed with this code.
- **agentd is non-dumpable** (`mode::set_non_dumpable`): in `landlock` mode `agentd serve` calls `prctl(PR_SET_DUMPABLE, 0)` first thing in `main`, before the settings are read or a secret is loaded, and reads the flag back; a failure ends the
  process. A same-user process outside a Landlock domain then cannot read its environment or memory. The flag resets at `exec`, so a helper agentd starts is dumpable: nothing secret goes in its argument list or environment.
- **The launcher** (`launch.rs`, `agentd sandbox-exec --policy-json <json> -- <program> [args]`) is a fresh process of the agentd binary that main dispatches before any runtime exists, so it is single-threaded and has loaded nothing. In order: parse
  and check the policy, require an absolute program, close every descriptor above 2 and look again (`/proc/self/fd`; one that stays open ends the launch), check the nobody route when the policy has one (below), install the domain, check the kernel's report, install the SysV IPC filter, then `exec` the program. Any failure prints `agentd sandbox-exec: refused: <reason>`
  and exits 125; the program never starts, and there is no unsandboxed fallback. `LaunchSpec.sandbox` and `LaunchSpec.run_as` are never both set.
- **The installer** (`enforce.rs`): the `landlock` crate (pinned `=0.4.7`, which keeps `unsafe_code = "forbid"` in this crate) at the hard-requirement level with every file right, both TCP rights and both scopes (abstract Unix sockets, signals) of
  Landlock ABI 6. A kernel below ABI 6, a rule that cannot be added, a report that is not `FullyEnforced`, a missing `no_new_privs` or an ABI below the policy's `minAbi` each end the launch. The installer sits behind the `Enforcer` trait; the tests
  inject every one of those.
- **The seccomp filter**: two lists, both answered with `EPERM` for the engine and everything it starts. The launcher installs the filter (the `seccompiler` crate, pinned
  `=0.5.0`, no default features; it sets `no_new_privs`) right after the domain. A filter the kernel refuses ends the launch like a domain that is not in force. The policy member `denySysvIpc` is true unless the policy says otherwise (a policy without it denies).
  - `DENIED`, whatever the arguments: `shmget`, `shmat`, `shmctl`, `shmdt`, `msgget`, `msgsnd`, `msgrcv`, `msgctl`, `semget`, `semop`, `semtimedop`, `semctl`, the six POSIX message-queue calls, and `io_uring_setup`, `io_uring_enter` and `io_uring_register`. Landlock does
    not cover SysV shared memory, message queues or semaphores and the IPC namespace is shared with agentd. The container allows an unprivileged process to stack a filter (measured on the Instances machine); its `unshare(CLONE_NEWIPC)` is refused, so agentd cannot move the engine into a fresh IPC namespace itself. The nobody route gets one with `clone3` in its helper, and a launch on that route allows the System V calls (below).
    A program that needs SysV IPC, such as a database server that keeps an interlock segment, fails with `EPERM` on a launch without the route. io_uring is closed because a send queued on the ring never reaches the argument rules below; libuv and Tokio fall back to their ordinary system calls when the ring is refused.
  - `DENIED_WHEN`, for one argument value (read as 32 bits; the positions are those of `man 2`, pinned by `crates/agentd/tests/sandbox_ipc.rs`): `sendto` argument 3, `sendmsg` argument 2 and `sendmmsg` argument 3 with `MSG_FASTOPEN` (0x20000000) set, `socket` argument 2 equal to `IPPROTO_MPTCP` (262) and `socket` argument 0 equal to `AF_SMC` (43).
    These are the doors around Landlock's `CONNECT_TCP`, which is the only barrier to agentd's port, the credential-vending port and port 80 and is asked only at `connect()` of a TCP socket: TCP Fast Open opens the connection inside the send (kernels before the Landlock fix, which Linux 6.18.54 has, never ask), and multipath TCP and SMC sockets are
    no TCP sockets to Landlock and fall back to plain TCP, so a connect on one reaches an ordinary listener. `crates/agentd/tests/sandbox_ipc_network.rs` runs the probe's door rows unconfined (fast open fails) and under the filter alone (all three pass); the same rows run on the Instances machine.
  - Still open on a closed port: UDP (Landlock does not cover it, and the three listeners are TCP), the three Unix sockets of the platform's process 1, and anything that reaches the port from outside the engine's family. A separate network namespace for the engine would close the last. It is a later hardening and not built: it needs `unshare` or a user namespace, and the container refuses `unshare(CLONE_NEWIPC)` (measured).
- **The nobody route**. On the Instances machine agentd is root in a container with no capability (`CapEff` 0, `CapBnd` 0, `no_new_privs`), so the engine was root too, and programs that refuse root failed there, such as PostgreSQL's `initdb` and a project's own setup script. The container refuses `unshare`, `setns` and every write of `uid_map`, and it allows `clone3` with `CLONE_NEWUSER` and `CLONE_NEWIPC` and the writes of `setgroups` and `gid_map` (measured on the test stage, kernel 6.18.54). A user namespace with no `uid_map` shows its processes as the overflow user 65534, and they hold no capability after the `exec`.
  - **Setting** (`identity.rs`, `config.rs`): `AGENTD_ENGINE_IDENTITY` is unset, blank or `nobody` for the route, which is the default, and `agentd` for the engine as agentd's own user. Any other word ends the run before anything is fetched (`stopped_setup_failed`) and the reason names the variable. The `uid` mode never reads it. `AGENTD_NOBODY_EXEC` names the helper (default `/opt/harness/bin/ham-nobody-exec`). Turning the route off is a change of the runtime's environment and needs no image build.
  - **Command line** (`Sandbox::wrap`): `ham-nobody-exec -- <agentd> sandbox-exec --policy-json <json> -- <program> [args]`. `Sandbox.identity_helper` and `Policy.nobody` are set together, and `wrap` refuses one without the other. Report steps (`Sandbox::rebased`) and the commands the tool server starts go through the same `wrap`, so each command gets user and IPC namespaces of its own. The helper is `images/worker-python/ham-nobody-exec` (`images/worker-python/AGENTS.md`).
  - **Policy member** `nobody` (`agentdIpc`, `agentdUser`): the names of agentd's own namespaces as `readlink` prints them (`ipc:[4026532731]`), read from `/proc/self/ns` when agentd builds the policy (`route_of_this_process`). `Policy::validate` refuses a name that is not `ipc:[<digits>]` or `user:[<digits>]`. The member is left out of the JSON when absent, so the isolation probe's drift test sees the same system keys as before.
  - **The launcher** (`launch::run_with`): after it closes the inherited descriptors and before it installs the domain, it runs `identity::check`. Its IPC and user namespaces must differ from agentd's and its effective user id must equal `/proc/sys/kernel/overflowuid` (65534). Otherwise it returns `SandboxError::SharedNamespace` or `NotNobody`, exits 125 and starts no program. The facts come through the `NsSource` seam; `ProcNs` is the real one.
  - **The filter** (`ipc.rs`): a launch on the route installs `SysvIpc::AllowedInPrivateNamespace`, which leaves the twelve System V calls out of the denied list. The POSIX message queue calls, the three io_uring calls and the argument rules of the TCP doors stay. A launch without the route installs `SysvIpc::Deny`, the list. `Enforcer::install_filter(sysv)` has a default for an enforcer that knows only `deny_sysv_ipc`.
  - **Preflight**: before anything is fetched or placed the driver runs the helper with `--check` (`HelperCheck` behind the `IdentityPreflight` seam, `Deps.identity`, 20 seconds). A machine that cannot make the namespaces ends the run with `engine sandbox: the nobody helper refused: ...`. The rules preflight reports a refusal line that starts with `ham-nobody-exec: refused` like one that starts with `agentd sandbox-exec: refused`.
  - **What the engine is**: the overflow user with group 1000, `CapEff`, `CapPrm` and `CapBnd` at 0, `no_new_privs`. The kernel user is unchanged, so agentd (root, outside the namespaces) reads, archives and commits what the engine writes: files the engine made show as 65534 inside and as root outside, and agentd's `tar`, `git log` and `git bundle` of them worked live. `chown` to the engine's own id fails with `EINVAL` (the id has no mapping). The engine cannot make another user namespace (its user id is unmapped) and holds no capability for `setns` or `mount`.
  - **Process accounting**: the engine's parent is the helper, which agentd spawns. A kill of the helper takes the program with it (`PR_SET_PDEATHSIG`). The reaper still finds the family by the tag in the environment, by the launcher's filter and by the parent chain, and the goal loop's probe still walks the processes below the spawned one.
  - **Limits**: each command has its own IPC namespace, so System V objects are not shared between the engine's shell and a command the tool server starts. Docker and Podman stay unavailable on Instances. The helper adds a Python start to each command.
- **File-path sockets authorise their callers**: a connect to a pathname Unix socket is outside Landlock, and a same-user caller passes the file mode. `creds_socket::Callers` is `Anyone` in `uid` mode (the 0600 mode and the engine's
  ownership of the file are the check, as before) and `Uid(agentd's own user)` in `landlock` mode: the socket reads the caller's user id from the connection (`SO_PEERCRED`) and answers any other caller, or a connection that does not say, with a refusal before the
  store is asked. What the socket serves is the run's own session credentials and nothing else; no other pathname socket is created by agentd, the package proxy, the tool server or the research API (they listen on TCP).
- **Network**: the policy handles both TCP rights and closes by exception. Every port is open for connect and bind except agentd's contract port (`AGENTD_LISTEN`), the platform's credential port (from `AWS_EC2_METADATA_SERVICE_ENDPOINT`) and, for connect, port 80
  (the EC2 metadata address). The package proxy (3128), TLS (443), the resolver's TCP fallback (53) and the tool server's and research API's ports (bound at run time) are therefore open without being listed. Names an allow list of those ports; this
  policy keeps the closed set the same and leaves the rest open, because a run's own tests start servers on ports chosen at run time and connect to them, and an allow list of fixed ports would end those tests. Landlock names ports, not addresses, and does not cover UDP.
- **The policy** (`policy.rs`) is data: read-write folders (every file right except device-node creation), read+execute trees, read-only trees, device files one by one, private paths and the TCP ports the engine may not connect to or bind (every
  other port is open, because the tool server, the research API and the package proxy bind ports chosen at run time, and the engine's own tests start servers). Grants add up in Landlock, so `validate` refuses a read-only tree inside a writable one and a
  private path that lies inside a grant or holds one. Rules, skills, plugins and settings live in the configuration folder, a sibling of the writable folders, and are granted read-only; the modes `0444`/`0555` are no protection in this mode.
  The base denies agentd's own port, the platform's credential-vending port (from `AWS_EC2_METADATA_SERVICE_ENDPOINT`) and port 80 (the EC2 metadata address).
- **Shared scratch directories**: `/tmp`, `/var/tmp` and `/dev/shm` are optional writable (and executable) folders of the engine and of the report's steps (`Sandbox::rebased` grants them again). The shipped rules and the lifecycle pack tell the engine to keep logs in `/tmp`; the JVM, glibc's `tmpfile()` and a `mktemp` without `TMPDIR` use it; Python's `multiprocessing` makes POSIX semaphores under `/dev/shm`. In the `uid` mode they work because the directories are world-writable. Here the engine has agentd's own user, so file modes protect nothing and the grant stands on a fact: agentd, the package proxy, the credential socket and the tool servers keep nothing in them. Their folders are `AGENTD_DATA_ROOT`, `AGENTD_RUNTIME_DIR` and `AGENTD_WORKSPACE_ROOT`; the proxy and the tool server make no file of their own; and `crates/agentd/tests/sandbox_shared_tmp.rs` scans the sources of agentd and of the proxy for a path in a shared directory or a temp file of their own, so a new use fails there and has to be argued. The driver declares agentd's runtime folder, the end sequence's `turns` folder and its private repositories (`snapshot.git`, `facts.git`, `probe.git`) next to `input` and `input.bundle` as private paths, and `with_shared_tmp` leaves a directory out, with a log line, when a path of agentd's or of the run is inside it or holds it: `AGENTD_RUNTIME_DIR=/tmp/agentd` loses the grant of `/tmp`; it never makes the credential socket's folder writable. One Instances session is one machine, so what the engine leaves in these directories reaches no other session; it stays until the machine ends. The probe's controls `control-tmp-literal`, `control-var-tmp` and `control-dev-shm-lock` (a `multiprocessing.Lock`) check that these folders work inside the domain.
- **Tool environment**: a Java program takes `user.home` from the password database (`/root` for the user of the Instances container) and `java.io.tmpdir` from `/tmp`, not from `HOME` and `TMPDIR`, so in the `landlock` mode the engine's environment and the environment of every report step get `JAVA_TOOL_OPTIONS` (after any value already there) with `-Duser.home=<the run's home>` and `-Djava.io.tmpdir=<the run's temp folder>`, and `GRADLE_USER_HOME=<home>/.gradle`. The report's steps get them from their own `home` and `tmp` under the report folder, because they have no agent to adapt. The `uid` mode is unchanged (its engine user owns `/home/agent`). Maven's `MAVEN_ARGS=--settings` is separate and stays. `crates/agentd/tests/sandbox_shared_tmp.rs` pins the composition and `crates/agentd/tests/sandbox_tool_env.rs` reads the result back from a whole run and from a report step through a stand-in launcher. On an Instances session, a Maven sample (`mvn -B test` with no agent present), a Python `multiprocessing.Lock` and a redirect to `/tmp` run inside the domain.
- **Layout**: the rules, skills, plugins and settings (`config_dir`) and the research and attachment files (`context`) sit beside the writable folders, never inside one, and are granted read-only; `Policy::validate` refuses a read-only
  tree inside a writable one. `/proc` is granted read-only as a whole (a rule on `/proc/self` does not reach children); the domain itself keeps other processes' `environ`, `mem`, `maps` and `exe` unreadable. The engine's `HOME` and `CARGO_HOME` are folders agentd makes
  under the run's data folder (the image's `/home/agent` belongs to a user that does not exist here). No secret is in an argument list: the launcher's argument is the policy, which holds paths and ports. The helpers agentd starts hold none (their environment is agentd's
  own, which carries none); a helper that must hold one calls `mode::set_non_dumpable` first thing, because `exec` sets the flag back.
- **Process accounting** keys on no user id in this mode: the reaper's sweep by user is off when the user is agentd's own (`direct::messages::reap::sweep_uid`, pinned by `crates/agentd/tests/direct_messages_hardening.rs`). The reaper finds the engine's family by the tag in the environment, by the launcher's seccomp filter (a process with more filters than agentd, `Seccomp_filters` in `/proc/<pid>/status`, which the kernel keeps through fork, setsid, a double fork and exec) and by the parent chain (`Reaper::with_sandbox_marks`, `crates/agentd/tests/direct_messages_reap_sandboxed.rs`), so a tool that scrubbed its environment and was left to init is stopped at the end of the run. The goal loop's evidence of a running command
  and the session's CPU use the processes below the engine's process (`direct::goal::command::ProcProbe::for_engine_family`, `direct::goal::evidence_choice`). There a process left to init by a parent that ended is not seen. agentd is no subreaper (`crates/agentd/src/direct/messages/AGENTS.md` says why).
- **The change of owner is skipped on purpose** in `landlock` mode: `engine::direct::own_by_root` does nothing when the process mode is `landlock` (`mode::note_process_mode`, set by `agentd serve`), and no code gives a file to an engine user because
  there is none (`owner` is `None`). Nothing swallows an `EPERM`; in `uid` mode a failed change of owner still fails.

### Sockets and listeners of the container (the inventory the mode relies on)

Landlock does not restrict `connect()` to a pathname Unix socket (ABI 9 adds a right for it; Linux 6.18 has ABI 7), and a same-user caller passes the file permissions, so the only protection of a socket is what it does with a caller. Measured on the Instances
machine (`fixtures/direct-probe/sandbox_probe.py` repeats the checks).

| Socket | Created by | Reachable by the engine | What a caller gets | Protection in `landlock` mode |
| --- | --- | --- | --- | --- |
| TCP `0.0.0.0:8080` (`AGENTD_LISTEN`) | `agentd serve` | Denied by the connect rule on its port | The runtime contract (`/ping`, `/invocations`) | The port rule, and the filter's doors (fast open, multipath TCP, SMC, io_uring) |
| TCP `127.0.0.1:3128` or a free port | `pkgproxy` (a task in agentd) | Yes, intended | GET-only proxy to the stage's package index; never the token | Its own rules (`proxyGetOnly` of the isolation probe); the token is in agentd's non-dumpable memory |
| Unix socket `creds.sock` in `AGENTD_RUNTIME_DIR` | `creds_socket` | Yes, intended (`agentd creds`); Landlock does not stop a connect | One line of the run's own session credentials per connection | `Callers::Uid` checks the caller's user id (`SO_PEERCRED`) before the store is asked; the file mode is the same user's |
| TCP `127.0.0.1:<port>` | the tool server (`direct::tools`) | Yes, intended (MCP) | The harness's tools, which start commands in the engine's sandbox | `CleanLaunch` carries the sandbox; the call is bounded by the tool table |
| TCP `127.0.0.1:<port>` | the research API (`direct::research`) | Yes, intended | The `ham-research` operations of the run | The operations are the contract; no credential is returned |
| TCP `100.88.0.1:<port>` | the AgentCore platform | Denied by the connect rule on its port (the port is read from `AWS_EC2_METADATA_SERVICE_ENDPOINT`) | The execution role's temporary credentials | The port rule and the filter's doors; the microVM does not have it |
| TCP `169.254.169.254:80` | EC2 | Denied by the connect rule on port 80 | The instance identity; no instance profile is attached | The port rule and the filter's doors |
| Three Unix sockets held by process 1 | the platform | Reachable (pathname sockets) | Not examined | Open item: they belong to AWS's side of the container |
| Docker front socket and supervisor wake socket | `ham-containers` | Not on Instances: `newuidmap` fails with `EPERM`, so the helper never starts | Nothing | Routes container tests to the old machine |

SysV shared memory, message queues and semaphores are outside Landlock and the IPC namespace is shared with agentd; none is in use (an empty `ipcs` on a fresh container) and the seccomp filter above closes them to the engine (on the nobody route the engine's IPC namespace is its own, so the calls are allowed and reach nothing of agentd's) (the probe's `sysv-shm` and `sysv-msg` checks attach and send to objects another process made).

## Work Guidance

- A new listener of agentd or of a module is a new row of the table above and a decision about who may connect: write the row in the same change.
- A new path the engine needs goes into `Policy::for_config` (a system tree, optional) or the driver's policy (a run folder, required); a folder a module makes later is an optional read-only grant. Never put a private path or agentd's state in a granted tree.
- Landlock calls are made only in `enforce.rs`. Tests use `Enforcer`, `FdSource` and `Execer` fakes; the kernel's own behaviour is tested on a Linux 6.12 or newer machine (the Instances machine), and the tests that need it print `NOT RUN` on an older kernel.


Runs on an Instances session are separate from these tests: a real engine, git, node, cargo, a Maven sample and the package proxy inside the domain, and the isolation probe through the launcher with its door rows and its controls for `/tmp`, `/var/tmp` and `multiprocessing`.

# crates/ham

## Purpose

`ham` is the binary covered and W2. It makes SigV4-signed `/v1` calls. It supports the argv start form. It has 21 subcommands: `runs`, `watch`, `cancel`, `models`, `pr`, `pull`, `clone`, `push`, `link`, `doctor`, `rules`, `config`, `engine`, the four that answer a run's "Cline needs you" question: `say`, `new-session`, `try-model`, `finish`, and the three of the lifecycle pack, the follow-up run and the resume of paused and stalled runs: `lifecycle`, `continue` and `resume`, and `update`, which brings the backend and the client to the newest version and runs from a shell only. Its Ratatui TUI has a Runs screen and New-run composer. It also has a run dashboard and Artifacts screen. `ham-core` supplies state, reducers, the parser and agent groups. It also supplies the download plan and renderings. This crate adds terminal, network and AWS credential code. It has no agent logic, under invariant 5. `ham "<prompt>" --repo ... --direct [--model <id|alias>]` starts a run on the Cline engine. The run uses the user's own rules through `ham rules init|edit|show`. `ham config get|set|unset|show|check|edit|docs` and a local `ham models` choose the model and show or repair the settings; `set` and `unset` change one line of the file and keep every comment. `ham engine <name> init|show|check|edit|set|unset|import` do the same for an engine's settings file. Runs use Claude Sonnet 5.5 unless the user chooses another model.

## Ownership

Owned by `crates/AGENTS.md`.

## Local Contracts

- `lib.rs` re-exports `crossterm` (`ham::crossterm`): the terminal library the TUI reads events with, for the TUI battery's probe in `ham-e2e` (`tui-probe`), which confirms the bytes the battery's
  driver sends against the reader `ham` itself uses. A second dependency edge in `ham-e2e` would change `Cargo.lock`, which the worker image key hashes.
- Transport: `http::ControlPlane` (`call`: one signed `/v1` request; `fetch`: an unsigned GET of a presigned URL, optionally one inclusive range and `If-Match`).
  `https::HttpsPlane` is hyper 1 with rustls, the ring provider and webpki roots (S11: no Apple framework). `apiEndpoint` is the stage base URL; routes are appended. Only
  `https://` is called, or `http://` to a loopback host. 30 s per call, 300 s per range. Error text names method and `scheme://host/path` only (`redact_url`): never a query,
  body or credential. Nothing is logged. A call to the stage whose host does not resolve (a DNS failure on connect) ends in `TransportError::Unresolved(host)`: its text says
  the stage address does not resolve, that the stage may have been removed or replaced, and names the two ways forward, `./setup.sh --status` (it prints the current
  endpoint) and `ham config set api_endpoint <url>`. It is retried like a network error. `https::is_dns_failure` reads the error chain for hyper-util's `dns error` link or
  the platform's `failed to lookup address information` text, each as a whole link. Every other connect failure (refused, a handshake that ends, a certificate that is not
  trusted), a timeout and a failed lookup of a presigned object URL (`fetch`; the host is the object store's) keep their words and carry no hint.
- Signing (`sigv4::Signer`): service `execute-api`; Region from `region` in config, else `AWS_REGION`, else the profile's region. `content-type` and `idempotency-key` are signed. Credentials are cached until 5 minutes before they expire. Credentials whose expiry has passed are refused before any request, whatever the source (`AWS credentials: the credentials expired at <UTC time>. ...`).
  - Which profile: the `awsProfile` profile of the config; without it, the `AWS_*` key pair when both are set, else the profile named by `AWS_PROFILE`, else the default profile.
  - Kinds (`awsprofile.rs`): read from section and key names only, in the order `credential_process`, static keys (`aws_access_key_id`), SSO (a key that starts with `sso_`), assume-role (`role_arn` or `web_identity_token_file`), unknown, missing; the first that applies wins. setup.sh's `profile_kind` holds the same definition; `fixtures/aws-profiles` and `tests/aws_profile_kinds.rs` pin both.
  - Static keys and `credential_process` profiles: the aws-config profile provider, as before. The `aws-config-client` workspace entry is aws-config without its HTTPS client, so a profile that must call STS or SSO inside aws-config fails with `NO_NETWORK`. A `credential_process` command that is the AWS CLI still works: aws-config runs it through `sh -c`; output that is not credentials JSON gets `PROCESS_OUTPUT_HINT` (run the command in a terminal), and a non-zero exit shows the process's own stderr (`tests/bridge_profile.rs`).
  - SSO and assume-role profiles: `awscli.rs` runs `aws configure export-credentials --profile NAME --format process` (the program `HAMH_AWS_CLI` names, else `aws` on the PATH; AWS CLI 2.9.0 or later) and kills it after 30 seconds. It reads the credentials JSON (`Version` 1, `AccessKeyId`, `SecretAccessKey`, optional `SessionToken` and `Expiration` in RFC 3339) and never shows what the command printed on standard output. A failed run is remembered for 5 seconds, so the four requests of `ham doctor` start the command once.
  - Messages: an SSO profile whose sign-in has ended gets `your IAM Identity Center sign-in has ended. Run: aws sso login --profile NAME`; any other failure shows the AWS CLI's own words (standard error, cut to 400 characters). A missing AWS CLI names the install page; an old one gives its version and `older than 2.9.0`; no answer within 30 seconds suggests `aws sts get-caller-identity --profile NAME`; output that is not credentials JSON says `not credentials JSON`.
  - Tests: `aws_cli_profiles.rs` (through the `ham` binary and `ham doctor`, with a stand-in `aws` script), `aws_cli_runner.rs` (time limit and kill, a flood of output, the JSON, RFC 3339, the version line), `aws_profile_kinds.rs` and `bridge_profile.rs`; none asserts that a key or process output is printed.
- `backends::Backends<P>` is the set of backends behind one `ControlPlane`; `connect(defs, default_alias, factory)` builds the planes at once (`https_factory` is the live one: a SigV4 signer from the backend's profile). With one backend a failure ends the start with the words of before and every call is forwarded unchanged (no view, no extra call). With two or more a backend that cannot be built is `Down` or `SignedOut`. `call_on(Some(alias), ..)` goes to that backend only; without an alias a call about a run follows the run map and an unknown id is asked of every backend at once (`ham_core::backends::decide`); a start goes to `default_backend` or is refused (`Local::NoBackendChosen`); a tag edit whose runs are in two backends is refused; a start that continues a run (`continueFrom.runId` in its body) goes to the backend that holds that run (the map, else every backend is asked; a run nobody holds, or a backend that could not be asked, starts nothing), and a backend named for it must be that one when the map knows (`Local::ContinueElsewhere`); a change (`changes_something`: not the two `POST .../download-url` routes) is refused for a backend below `MIN_BACKEND`, of a newer major, or whose service answers the one `GET /v1/whoami` that learns an unknown version without any version header (`Local::Untagged`); a failed or gateway-only probe tells nothing and the change goes on; a change that names no run (`Route::Other`) goes to `default_backend` or is refused. Answers teach the run map (`learns_from`) and the health (`backend_view()`; `judge_answer` reads the HTTP status and the version header, so a refusal at the gateway, a throttle and a server failure each get a banner), a lapsed login or a refusal at the gateway pauses the timer reads of that backend (`paused`), and `retry_down()` (the manual refresh) lifts the pause. `aim(&api, named, customer_content, Aim)` aims a command and refuses a customer-content start on a backend not declared safe before any call. `TransportError::Local` carries the refusals and is never retried. `Api::on(alias)` aims an Api; `start::start_direct` puts the Api's alias into the idempotency key. `api_multi.rs` reads the list of every backend at once (`multi_rows`: a deadline for each page, 5 s on the timer and 15 s on `r` and `ham runs`, at most one retry inside it, merge with the watermark, the rows of a failed backend kept and marked stale; a first page that says more follow keeps the older rows of the last read, `keep_older`, so a failed full read still shows them); `doctor::checks_many` checks every backend at once with a deadline of its own (`DOCTOR_DEADLINE`); a client with one backend never enters it.

- `api::Api` retries idempotent calls after network errors, 429 and 5xx. It makes 5 attempts, starting at 500 ms and doubling. `POST /v1/direct/runs` retries with the same `Idempotency-Key`. `POST .../download-url` carries a fresh key. Event reads get one attempt. `poll` reads all 32 shards at once. It keeps reading a shard while the server sends `FULL_PAGE` (500) events. `RawEventsPage` decodes each page event by event. It skips event types this client has no name for. These are types written by a newer harness. The cursor moves past each skipped event. It uses the server's `nextAfter`, else the largest id read. The server does the same for items it cannot parse. A new event type therefore never hides the `run.completed` behind it. A known event type that fails decoding still produces `ApiError::Decode`. A `ham` built without `RawEventsPage` stalls on the first unknown event. Deploy the new `ham` before relying on a new event type.

- Config verbs and the writer.
  Reading: `config_cmd::load_file` reads the file once, bounded: a regular file (a link is followed; a directory, a device or a pipe is refused with "not a regular file"), at most `MAX_CONFIG_BYTES` and one
  more byte, and it keeps the SHA-256 of what it read. A file with bad content is `Ok`: `Loaded::read` holds the findings, and `Loaded::refusal()` is `Some` only for a file that is not usable as TOML at all.
  `config_cmd::load` is the strict form that `ham models`, `ham runs` and a start use: a file with an error finding, or a newer file whose unknown key may steer a run, is refused with the line of each problem.
  Writing: `apply_set` and `apply_unset` plan the change as text (`ham_core::config_write`) and `commit` writes it: a temp file in the same folder, its mode set on the handle (the bits of the old file whatever the umask;
  a new file is 0600), synced; just before the rename the file is read again and its SHA-256 compared with the one loaded, and a difference stops with "config.toml changed on disk; reloaded; nothing written". That
  narrows the race and is not a lock: the last rename still wins and no lock file is made. A link at `config.toml` is followed and stays a link, and the file it points to must be a regular one. A no-op writes nothing.
  A file with a bad key is patched around, and what it still holds that is wrong is printed as `ham: warning:` lines on standard error. The write that adds the first table to a file prints on standard error after the
  write `ham: note: ham versions before v<CLIENT> refuse this file. To go back, run `ham config unset <key>` or delete the `[table]` and `configVersion` lines.`; in the message box `commands::door_preview` gives a
  `/config set <table key> <value>` that has no preview of its own the same text as a preview before the write, confirmed by Enter alone.
  Verbs: `get` and the list print the keys that could be read, with the exit codes and JSON shapes they always had (the list has the 23 names and `path`; `get` of an unset key exits 1). `show [--json]` prints each
  key with the value in force, where it came from (`env HAMH_MODEL`, `file`, `default`; `config_cmd::effective`) and when a change takes effect, then the seven locked classes with their reasons. `check [--strict]` prints
  each finding with its line and exits 0 when clean, 1 on an error (on a warning too with `--strict`; a newer file that blocks run starts is an error) and 2 for usage. `edit` opens `$VISUAL`, else `$EDITOR`, else `vi`
  on the file (the file a link points to) and then runs `check`. `docs` prints `settings::reference_markdown()`. `ham doctor` runs on a file with a bad key (`cli::doctor_config`): the keys that could be read connect,
  and a `config` check line for each finding comes first (a warning passes); a healthy file adds no line, and a file that leaves nothing to connect with is the whole report with exit 1. The composer's `d` key
  (`tui::save_default_model_with_env`) and `/config set` write through the same writer, so they keep comments.

- `HAMH_RANGE_BYTES` sets the range size. Its range is 1024 to 16 MiB. Other values cause usage exit 2. Uses small ranges to kill a download mid-way. `--artifact` selects zip by default, or partial or evidence. It picks the newest artifact of that kind. If none matches, the message names what the run has. A plain key's last segment becomes the local name. Otherwise, the name is `<runId>-<artifactId>.<zip|jsonl|bin>`. The default range size is 16 MiB. There are 4 ranges in flight. Ranges are written in order to `<file>.part`. The ETag is stored in `<file>.part.etag`. A rerun resumes while the ETag matches. Every range uses `If-Match`. A 403 gets one fresh URL. A SHA-256 mismatch deletes the `.part`. A destination that already verifies is kept and its `.part` leftovers are removed. One download at a time writes a destination's `.part` (BATR1 defect D2: two downloads appended to one `.part`, and the zip was twice its size while the first said `sha256 matched`): it holds a flock on the lock file `<file>.part.lock`, removed while still locked, and a claim of this process on the destination; the lock comes before the download link is requested. A second download of the same artifact (the dashboard's automatic one and Enter on the Artifacts screen, or two shells) waits, then keeps the file the first one verified (`ranges` empty) or resumes the `.part` of a first one that died. It ends with `PullError::Busy` (`another download of <file> holds <lock> and has written nothing for <limit>`) when the holder's `.part` has not grown for `pull::LOCK_IDLE` (5 minutes; `download_waiting` takes another limit). The `.part` is written at an explicit offset (no append), its size and SHA-256 are checked through the handle that wrote it before the rename, and the size of the file in place once more after it (a different size removes the file and is an error). A destination of the wrong size (the doubled zip) is replaced by a verified download. A directory that cannot lock files (ENOLCK, ENOSYS, EOPNOTSUPP) gets a download into its own `<file>.<nonce>.part`, no resume, other downloads' files untouched (`download_unlocked`). - Clone:
  `ham clone <runId> [dir]` downloads the run's newest `zip` artifact, else its newest `partial` one (announced on
  stderr; never a fallback from a `zip` whose download failed), by the pull flow (ranged GETs, resume, SHA-256 against the artifact; the zip stays
  in the download directory), after checking, before any download, that git runs and that the destination is free. `clone_zip` reads only
  `<top>/repo.bundle` out of the zip (never `src/`) into a private staging directory `.ham-clone-<runId>-<nonce>` beside the destination,
  then `git init` (empty template), `git bundle verify`, `git fetch` of `refs/heads/harness/<runId>` and a hard reset to it: no remote is
  ever made, and no reflog or `FETCH_HEAD` names the staging path. The proof (any miss exits 1, nothing published): every `<top>/src/` entry
  is hashed as a git blob in Rust (`blob_id`, streamed) and must equal `git ls-tree -r -z HEAD` by raw path, blob id and mode
  (`git_mode`; gitlinks are skipped), HEAD is attached to `harness/<runId>` at the commit the bundle advertises, `git status` is clean
  (`check_clean`), and the checkout on disk holds every path of the zip once with its kind and mode and nothing else (`check_worktree`
  walks the disk: git calls a checkout clean when a case-insensitive file system folds `A` and `a` into one file). The zip's `src/` is the
  verbatim head: the packager neutralizes every in-tree conversion attribute and keeps a symbolic link a link entry (`crates/delivery`, tested
  through the real `Packager::package` in `tests/clone_packager.rs`), so `src/` equals the committed blobs, links and modes included, and any
  difference from the bundle's tree is a refusal. A repository file name that is not valid UTF-8 is shown with its bytes escaped (`caf\xe9.txt`) and named as the cause, without the earlier-release hint: a zip entry name is text, and the packager's raw copy rewrites such a name through the zip crate, so the trees cannot match. A checkout under the repository's own `.gitattributes` (line endings, `ident`, an encoding)
  writes other bytes on disk than the zip holds; that is a warning in `Cloned.warnings`, not a failure, because git reproduces the conversion
  from the proven blob. A zip delivered before the packager rule existed, of a repository with a link or such an attribute, still fails the
  tree check (its `src/` is not the head): `unzip` reads it as it is. The run id must be one plain path component (letters, digits, `_`, `-`, at most
  64), paths are made absolute before git runs, a destination written with a trailing `/.` is the directory itself, and a zip whose top directory is not UTF-8 is
  refused. Publication is one `rename` of the staging directory onto the destination;
  before it succeeds the destination is untouched, and a failed removal of the staging directory afterwards is a warning in `Cloned.warnings`.
  The staging directory is removed on every error and panic (`Drop`); only a killed process leaves a `.ham-clone-*` directory, which is safe to delete.
  Every git command runs with the machine's configuration shut out: all `GIT_*` variables removed (not `GIT_EXEC_PATH`), `HOME` and
  `XDG_CONFIG_HOME` in the staging directory, no system or global configuration, an empty template, `core.autocrlf=false`,
  `core.fsmonitor=false`. Missing or unusable git (macOS without the command line tools: `/usr/bin/git` exits non-zero) says so with
  `xcode-select --install` and exits 1. Output: `cloned run <id> into <dir>` then branch and commit, the tree line, the kept zip and how to
  add a remote; `--json` one object (`runId`, `dir`, `branch`, `head`, `commits`, `files`, `partial`, `treeEqualsZip`, `zip`
  `{path, sha256, artifactId, resumedFrom}`, `warnings`). `ham clone` runs none of the delivered code. `extract_bundle` writes at most the
  entry's declared size plus one byte, then refuses a longer entry (zip 9 already fails a read past the declared size; `copy_declared` keeps its own `take(size + 1)` bound and message, pinned by unit cases that feed it a reader which ignores the size). Dependencies: `zip` and
  `sha1` (both already in `Cargo.lock`); `delivery` is a dev-dependency (the clone tests run the real packager).

- A fault a test installs in `tests/support` (`Faults`: 503s, slow answers) is installed by an event of the code under test, never by a timer task

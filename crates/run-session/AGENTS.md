# crates/run-session

## Purpose

The `run-session` Lambda of a direct run. One run is one Cline session in one
AgentCore microVM; the Step Functions machine `hamh-direct-run` (`statemachines/direct.asl.json`) sequences the work and this Lambda decides every
step: `prepare`, `start-session`, `plan-delivery`, `finalize`, `mark-blocked` and the EventBridge shape `run-ended`. One more op, `name-run`, writes the display
name and the topic and tech tags of a run and changes nothing the run does. It delivers what Cline left and says how Cline stopped; it never judges the work.

## Ownership

Owned by `crates/AGENTS.md`. The wire types it uses live in `harness-protocol::direct` (`DirectInvocationRequest`, `DirectOutcome` with its
frozen labels, `DirectSummary`, `DirectEvidence`, the `direct::s3` keys); the delivery payloads are those of the Lambdas in `crates/delivery`.

## Local Contracts

- Ops (`ops::Op`, `{"op": "<kebab-case>", ...camelCase}`): errors are `RunSessionConflict` and `RunSessionUnavailable` (the machine retries) and
  `RunSessionInvalid` (it does not). `prepare` refuses a run that is not active, a model outside `models.json`, a `request.json` whose SHA-256
  differs from `run.created`, a prompt or target the Run item does not hold; it builds the repo-gateway `stage` (and `new-repo`) payloads. `prepare` reads stored requests using the same strict type as `control-api`. The `engineConfig` member passes, and `prepare` answers the same as without it. Unknown members fail as `RunSessionInvalid`, with a message naming the member; the deploy order control, runtimes, orchestration produces this named failure; tests are in `tests/engine_config_request.rs`.   repository (`Repo`, never `--new-repo`) with no `baseRef` or with `harness/<source run>` (also `refs/heads/harness/<source run>`, passed on to the gateway as it was stored),

- Flow: the flow agentd recorded (`summary.flow`: `quick`, `full` or `none`; absent when it could not read the commits) reaches the delivery two ways, both from the summary. The summary is written whole into `evidence/direct.json`, so the client reads `summary.flow` out of the delivered zip (`ham_core::head::flow_in_evidence`), and `DirectSummary::to_evidence` copies it into the evidence the packager renders (the Flow row of EVIDENCE.md). A run with no summary has no flow. `plan-delivery` reads nothing else for it and the flow changes no outcome, label or delivery (`tests/deliver_flow.rs`).
- Chat index: after the session is stopped, `finalize` and `mark-blocked` call `index::best_effort`, which builds one search body (`ham_core::runsearch`,
  at most 32 KiB) and writes it with one UpdateItem into the run's chat item (`PK = OWNER#<sha256 of the Run item's owner ARN>`, `SK = CHAT#<createdAt>#<runId>`: the run index's item, `SRCH#`, is read whole by the run list and stays
  small; only the body's attributes are set, never `ownerPrincipalArn`, so the item stays out of GSI1; a repeat writes the same values). It skips a discarded run and
  a run whose Agent item registered no `transcript.v1` (`Store::transcript_supported`, a raw read of `features`). The transcript prefix is one the engine can write, so it lists with
  sizes, never fetches an object over 1 MiB (`Blobs::get_bounded`: refused by length and while streaming), reads at most 256 chunks inside 30 s (the newest first until the tail of the
  body is full, then the oldest until the head is full), decodes each with the read route's whole-chunk checks, and passes every string, the objective and the user's answers
  (`Store::user_answers`: `Instruct` controls from the user that carry text) through `harness_core::refusal::redact`. It never fails the run: a failure, or 60 s, is one log line
  (`"op":"index"`, a bounded outcome, a coverage word and counts, never text from the conversation) and the run is searched on its prompt, repository and model. No new IAM: the role
  already reads `agents/direct/turns/*`, lists the bucket and updates the table (`infra/test/transcript-access.test.ts`). The new `Store` and `Blobs` methods default to unavailable
  (or to no transcript). Tests: `tests/chat_index.rs` (13, over the fakes) and `tests/chat_index_aws.rs` (6, recorded exchanges).
- `compute`: which machine a run's session starts on. `choose_compute(request.compute, Config.compute.policy)` takes the user's `microvm` or `instances`, else the stage policy (`ComputePolicy`, env `COMPUTE_POLICY`, default the ONE constant `DEFAULT_COMPUTE_POLICY` = `Microvm`). `start-session` reads the Agent item first: a run that has one keeps what it records (`recorded`), so no deploy between two attempts moves a run; otherwise it chooses, and writes `AgentItem.compute` and `capacityProviderId` before the first invoke. The provider's id comes from `Sessions::capacity_provider_id`: the SSM parameter named by `CAPACITY_PROVIDER_ID_PARAMETER` (the stack that creates the provider publishes the id, so the function holds a name and never the id), read each time an Instances session starts and never cached, like the runtime ARN; a parameter that is absent or holds no provider id is `RunSessionInvalid` "the Instances capacity provider is not set up", any other failure is `Unavailable` and is retried. The id on the Agent item is the one the end uses. An `instances` run reads the runtime ARN through `Sessions::instances_runtime_arn` (SSM parameter named by `INSTANCES_RUNTIME_ARN_PARAMETER`; absent: `RunSessionInvalid` "the Instances worker runtime is not deployed"), claims one of `COMPUTE_MAX_ACTIVE` slots with `Store::claim_instances_slot` (one DynamoDB item `STAGE#instances`/`ACTIVE` holding the run ids as a string set, a condition on its size; a full stage is `RunSessionInvalid` naming `--compute microvm`), pins the Instances runtime's `live` endpoint like the microVM's or, when it has none, `DEFAULT`, and invokes it. `end_session` stops the session, then (Instances only) `Sessions::delete_provider_session` (`DeleteCapacityProviderSession`; gone is fine, any other failure fails the op and leaves the Agent item open while a machine may still bill), then releases the run's slot for every run, a microVM run and a run with no Agent item too (`Store::release_instances_slot`: one DELETE of the run's own id, harmless when the run holds none, whatever `COMPUTE_MAX_ACTIVE` says now: a cap removed by a deploy, or an attempt that claimed a slot and was followed by one that chose the microVM, would otherwise leave the id in the set for good), and ends the Agent item; `run-ended` reaches the same function for a run whose execution failed. `compute::from_lookup` reads the variables and names the wrong one; a policy of `instances` needs both parameter names (`InstancesParameters`: `INSTANCES_RUNTIME_ARN_PARAMETER` and `CAPACITY_PROVIDER_ID_PARAMETER`). `start-session` reads the run again after it wrote the Agent item and before the invoke, and once more when the invoke has returned, whatever it answered, an error or an unreadable acknowledgement included, because a call can time out after the machine was created (`end_if_discarded`): a run that is no longer active (a discard landed meanwhile; the reaper it started may have found nothing to end) has its session ended by `end_session`, tried twice at once because an aborted execution retries nothing, and the op returns `RunSessionInvalid`. When both tries fail the op returns that error and the Agent item stays open: the reaper repeats the end if it has not finished yet, and if it has, only the session's own idle and lifetime limits end the machine (the residual risk). - `wiring::wire` makes no AWS calls. It fails only for missing or empty environment variables, naming them. The function leaves `Config.runtime_arn` empty. `Sessions::runtime_arn`, the runtime lookup method, defaults to `Ok(None)`. `AgentCoreSessions` implements it through `aws::resolve_runtime_arn` and `runtime_parameter: Option<RuntimeParameter {client: aws_sdk_ssm::Client, name}>`. `start-session` calls it each attempt when `Config.runtime_arn` is empty. Warm functions therefore see parameters written later. Configured ARNs skip lookup. Missing parameters or empty runtime ARNs produce `RunSessionInvalid`, without retry. The reason includes "the worker runtime is not deployed: ..." and the parameter name. Other SSM failures produce retried `RunSessionUnavailable`. Lookup precedes credential minting and Agent writes. `StartSession`'s Catch, `Plan`, and `Blocked`, the blocked state, end the run blocked with that reason.
- `run-ended`, the reap operation, clears runs to `cleared` with `run.aborted` for `FAILED`, `TIMED_OUT` and `ABORTED` executions, keeping the execution's error and cause, and stops the session; repeating it is harmless. The EventBridge rule starts the Standard machine `hamh-direct-run-ended` (`statemachines/direct-run-ended.asl.json`), whose one Task calls `run-session` with the event as input. A refusal (`RunSessionInvalid`: an event of another machine, a status that is not an end) goes to `Dropped`; every other failure, whatever its name, is retried after 300 s up to 1000 times (3.5 days of waiting), then the execution fails in `ReaperGaveUp`. This is the bounded reconciler: it needs no table scan and no new dependency. It reaps what an event announces; it cannot find a run whose status event never arrived.
- When `mark-blocked` cannot answer, `Blocked`'s Catch reaches Fail state `RunMachineFailed`. Its Error is `RunSessionUnreachable`; Cause comes from `$.blockedFailure.Cause`. Execution fails with the real cause. The reaper clears the run once the function answers. `tests/machine.rs` checks every Task catches `States.ALL` and each Lambda failure. It checks dead-function failure, reaping, and missing-runtime blocking naming the parameter. `tests/reaper_machine.rs` walks the reaper file using the real operation. - Harness event ids are deterministic (`ulid_from(ms, "<runId>/<type>/<n>")`, `events.rs`), so a retried Lambda writes the same items. They also ascend in the order a flow writes them: a reader keeps the largest id it has read per
  shard and asks for the ids above it, so an event written after a larger id was readable, with a smaller id, is never returned to it. The end and blocked events have distinct milliseconds (offsets from `plannedAtMs`). The two start events share the
  Turn's `startedAtMs`: `goal.status` (active) takes the lower half of the 80 random bits and `session.started` the upper half (`events::Half`, `ordered_ulid`); with the hash alone `session.started` could sort below `goal.status`
  and a card lost the model name. `tests/event_order.rs` pins every flow against the order of its writes (the fake store logs them: `Mem::event_writes`, `assert_event_writes_ascend`); a new event is
  given an offset or a half above the event written before it. The one order a writer cannot give is across writers (control-api's cancel `goal.status` takes the id of the write time, the Lambdas date theirs at an earlier moment); the client
  reads the harness shard from its start while a run is open (`ham-core` `poll.rs`) for that.
- The run index. Tests: `tests/run_index_touch.rs`, `tests/aws_run_index.rs`. `finalize`, `mark-blocked` and the reaper (`run-ended`) record run endings. They update the run's search item through `Store::touch_run_index(run, outcome, lastActivity)`. `finalize` supplies the outcome label and the delivery plan's time. `mark-blocked` supplies the plan's outcome label when there is one. It supplies the time of the plan's events. The reaper supplies no outcome. It supplies the execution's stop time. The DynamoDB adapter uses `UpdateItem` with key `OWNER#<sha256 of the run's owner>`, `SRCH#<createdAt>#<runId>`. It sets `runId` and `createdAt` with `if_not_exists`. It sets `lastActivity` and sets `outcome` when given. It never touches the prompt head, model or repository. Its condition is `attribute_not_exists(lastActivity) OR lastActivity < :t OR (lastActivity = :t AND (attribute_not_exists(outcome) OR outcome = :o))`. This makes a delayed earlier attempt lose to a later time, and an equal time replace nothing but a missing or identical outcome. A failed condition counts as success. The write is an upsert. It works in any order with control-api's start write and the backfill. It creates a partial item when the run's own item is missing. A failed touch produces one log line: `warning: run-index`. It never fails the end of a run. A discarded (cleared) run is not touched. The role needs no change. It already holds `UpdateItem` on the table.

- Messages at the end of a run: `finalize::end_session` first calls `Store::close_messages(run)`. Only then does it stop the session.
  `finalize`, `mark-blocked`, and `run-ended` all call `finalize::end_session`. So does `plan-delivery` for a lost session. The `Store` port gains `close_messages`, which defaults to closing nothing.
  `DynamoStore` runs `Ledger::close(CloseReason::Finalize)` from the `message-ledger` crate. Closing creates the run's message control item when none exists. A message admitted afterwards finds admission closed.
  Closing rejects pending or held messages as `run-sealed`. It changes a message agentd holds in `dispatching` to `delivery-unknown`. It never rejects a delivered message.
  Repeating the close is harmless. A failed close fails the op before anything stops. The machine's retry runs it again while the session remains up.
  The role needs GetItem and UpdateItem on the table. It already has both permissions. This needs no PutItem permission.
- `name-run` names a run. `Name`, the first state of `hamh-direct-run`, sends it as an asynchronous Lambda call (`InvocationType` `Event`) and never waits for the answer. Until a model-written name is stored, clients show a seed that they build from the stored prompt head; the seed is never stored. The op answers `{"named": <outcome>, "reason": <code>}`. Outcomes: `ai`; `ai_squeezed` (the model's 8 to 10 words were cut to 7 or fewer); `seed` (the run keeps the name built from its prompt); `kept` (a name is already stored); `off` (the setting is off); `skipped` (no run or no goal). `reason` is `-` for a written name, otherwise a fixed code of `ham_core::runname::Reason` (`short_prompt`, `disabled`, `no_run`, `kept`, `timeout`, `throttle`, `service_error`, `config_error`, `op_deadline`, `stop_<reason>`, `no_text` or a judge code).
- Flow of `name-run` (`name_run.rs`): a disabled setting or a missing client returns `off` with `disabled`, without reads or calls. The op reads the Run item and the root Goal (either missing returns `skipped` with `no_run`), then `Store::run_name`, a consistent read of the stored name (a name that exists returns `kept`). `ham_core::runname::plan` returns `seed` with `short_prompt` for fewer than 4 words. Otherwise `ham_core::utility::request_body` builds the request over `runname::system_text()` and the plan's escaped, redacted excerpt, `runname::judge` decides whether the reply may become a name (a rejection returns `seed` with its code), and one conditional `Store::put_run_name` stores it (`false` means another invocation won: `kept`).
- Limits of `name-run` (`NameBudget`, from `UtilityPurpose::RunName`): 6 s per attempt, at most 2 attempts at the same route, 200 to 400 ms between them, 30 s overall. Only `timeout`, `throttle` or `service_error` earns the second attempt; `config_error`, `no_text`, a stop reason other than `stop_sequence` and every judge rejection do not. Every failure of the model side is an `Ok` answer with `seed` and its reason code (`op_deadline` included); only a failure of the store is an error (`RunSessionUnavailable`), so Lambda runs the event again. The name is write-once, so duplicate events, redrives and retries after a lost answer return `kept` without another model call.
- Isolation of the branches. `tag_run::tag_run(deps, run, excerpt, budget) -> TagReport` never returns an error, never touches the name branch and never waits past `TagBudget::total` (20 s, inside the 30 s of the op; the whole branch, reads and writes included, is under it). Only a store error of the name branch fails the op (Lambda runs the event again, the tag branch then answers `kept` without a call); the tag branch's line is printed whatever happened to the name. The branch reads its own item state (`Store::tag_state`, a consistent read of two attributes) and does not share the name's read, so a read error in the tags is a tag outcome. `Namer.tag_budget` holds the limits (`TagBudget::production()`: vocabulary 2 s, attempt 6 s, 2 attempts, 200 to 400 ms between tries; tests use units of tens of milliseconds).
- Flow of the tag branch, in order: (1) the catalog row must hold a passing smoke record for `run-tags` (`UtilityModel::selectable_for`), else `skipped` with `not_smoked` and no read; (2) `tag_state` (one try again after a store error): a marker `runTagsAt` ends the branch (`kept`: a duplicate event, a redrive, a rerun after the name failed); (3) a follow-up (`run.continue_from`) reads its parent (`Store::parent_tags`: the parent's Run item for its `createdAt`, then its search item in the follow-up's own owner partition; a parent of another principal, a missing run or a missing item is no parent) and copies the parent's user and off lists once with `put_run_tags_inherit` before any model call; a lost copy (a person's edit or an earlier copy came first) leaves the item as it is and the branch reads it again, so a tag removed since the first read does not take one of the six places; a failed read or copy ends the branch with nothing written, because the automatic write bumps `runTagsRev` and a revision makes the copy impossible for good; (4) fewer than four words ask no model (`is_short`); otherwise `Store::tag_vocabulary` (one eventually consistent Query of the owner's 200 newest search items, within 2 s; a failure or a stall means `(none yet)`, the reason `vocab_unavailable`) and one Converse call (`ham_core::runtag::judge::request`, thinking off, no sampling field, stop sequence `</tags>`); (5) `judge_reply` (the whole reply: stop reason `stop_sequence`, at most 16 KiB, no control, invisible or credential-shaped text anywhere, then the list; compact `["a","b"]` and spaced lists are alike; then each tag against the grammar, the policy words, the off lists of the item and of the parent, the vocabulary spelling and the quotas); a reply refused as a whole keeps nothing and is never cleaned, a reply that parses is an answer even when every tag was refused; (6) `compose_auto`: the model's kept tags, then the parent's automatic tags, none on an off list, up to six; (7) `put_run_tags_auto` with the condition `attribute_not_exists(runTagsAt)` (a lost condition is `kept`; one try again after a store error, then `store_error`).
- What the tag branch writes: `runTags` (the list, left out when empty), `runTagsAt` (the marker: the automatic step finished), `runTagsModel` and `runTagsVer` (only when the model answered), `runTagsRev` (incremented in the store with `if_not_exists`), and for a follow-up `runTagsUser`, `runTagsOff` and `runTagsInh` (the copy), plus `runId` and `createdAt` with `if_not_exists` where the item is new. It never names the off list of a run it did not copy, the time, the outcome, the head or the name, so the person's removal wins on every read (`ham_core::runtag::effective`) whatever order the writers run in. A model failure on a plain run writes nothing (a later catch-up can fill the run); a follow-up whose model failed or whose prompt was short still gets the parent's automatic tags and the marker without `runTagsVer`. The expressions are the specs of `ham_core::runtag::dynamo`, sent as they are by the adapter (`aws.rs`) and applied by the in-memory fake after `dynamo::expr_rejects`; `tests/aws_run_tags.rs` pins the wire.
- The vocabulary read is narrow: `PK = OWNER#<sha256 of the stored run's owner ARN>` (never from the payload, which carries the run id only), `begins_with(SK, "SRCH#")`, newest first, `Limit` 200, `Select SPECIFIC_ATTRIBUTES`, a projection of exactly `runTags`, `runTagsUser` and `runTagsOff`, no filter expression, aliased names. Its items decode with a type of their own (`VocabRow`, never the run-index item); an item that does not decode is skipped and counted (`vocabSkipped` in the log). The role needs the statement `TagVocabulary` (`infra/lib/stacks/orchestration-direct.ts`); without it the read is refused, the branch tags without a vocabulary and the reason says so.
- Log line of the tag branch (counts and fixed words only; no prompt, excerpt, reply, tag or hash): `function`, `op`, `purpose` (`run-tags`), `promptVersion` (`rt-1`), `runId`, `outcome` (`written`, `inherited`, `none`, `kept`, `skipped`, `off`), `reason` (`-` for a written list, otherwise a fixed code: `short_prompt`, `disabled`, `no_run`, `not_smoked`, `kept`, `store_error`, `vocab_unavailable`, `no_tags`, `op_deadline`, the model's `timeout`, `throttle`, `service_error`, `config_error`, `no_text`, or a reason of `ham_core::runtag::grammar::Reason` such as `stop_refusal`, `control_chars`, `credential_shape`, `bad_json`); when known `route`, `attempts`, `callMs`, `stopReason`, `inputTokens`, `outputTokens`, `promptWords`, `excerptChars`, `ageS`, `vocabLines`, `windowRuns`, `topShareBp`, `proposed`, `keptN`, `reused` (kept tags the vocabulary already held), `new`, and `rejected` (a count per judge reason code).
- Model calls live in `utility.rs` only: the trait `UtilityClient` and its adapter `BedrockConverse`, which signs `POST /model/<encoded profile id>/converse` for the service `bedrock` with the function's own role credentials over `agentd::http::SignedHttp`. A worker session's credentials are never used for them. A later helper function is a new op that calls the same client.
- `UTILITY_MODEL` is read once at start by `lambda::utility_from_lookup`. Absent, blank or `off` leaves helper calls off; an id or alias of a selectable built-in row whose Region is the stage's selects that row; any other value leaves them off and prints one `utility-model-invalid` line. An unusable setting never stops the function, because a run does not depend on its name.
- Writes and log of `name-run`: the name branch writes only `runName`, `runNameSource` (`ai`) and `runNameModel` on the run's search item, plus `runId` and `createdAt` with `if_not_exists` where the item is new (the attribute is `runName` because NAME is a DynamoDB reserved word). The op writes no other item, event or object (the tag attributes above are the only other writes), and no delivery code reads the name (`tests/name_run.rs`). One JSON line per op goes through the `Namer` log (standard output in the Lambda) after the per-invocation line: always `function`, `op`, `purpose` (`run-name`), `promptVersion`, `runId`, `outcome`, `reason`; when known `route`, `attempts`, `callMs` (last attempt), `stopReason`, `inputTokens`, `outputTokens`, `promptChars`, `excerptChars` (characters sent to the model), `promptWords`, `nameWords`, `nameCols`, `ageS` (seconds since the run was created). It holds no prompt, excerpt, reply, name or hash of them; a failed store call prints no such line (the per-invocation line carries the error).
- Research settings (`lambda::research_from_lookup`): present when the function has `RESEARCH_TABLE_NAME` and `RESEARCH_PROVIDER`. The word goes into the policy row of each run that the research route reads, with the stage's default limits unless `RESEARCH_LIMITS_JSON` gives a full set. A stage without the two variables runs with research off; an unknown word stops the function at start (`tests/research_policy.rs`).
- `slices.rs` is the session loop. `plan_first` writes `runs/<run>/slices/1.json`. `next_slice` (op `next-slice`) classifies how session n ended (`classify`), stops its machine, picks the best head (`best_head`: the final bundle when its key is the expected one and exists, else the last snapshot, else the head the session restored), applies `decide` and writes `<n>-end.json` and the next plan, both create-only, so a retry returns the first decision. `decide`: a handoff continues; a lost session is replayed until three in a row have been lost (stalled, `session_lost`); three handoffs in a row that left the head as they found it stop the run (stalled, `no_progress`); a session that could not restore the earlier work counts as lost (`restore_failed`); no time for another session stops the run (paused, `total_time`). `plan_timing` fits the sessions into `maxRunS` (reserve 900 s per session, least engine time 900 s); `slice_cap_s` is the microVM lifetime less the reserve, or the stage's `HAMH_SLICE_DEADLINE_S` test limit. `start_session.rs` moves the Agent item to the session's turn (new runtime session id, nonce, the hash of the completion key made from that nonce, and generation in one conditional write) and invokes with the `slice` member and the earlier session's last message as `brief`; `plan_delivery.rs` delivers the best head of the last session; `finalize.rs` `run_stop` maps the end to `paused` or `stalled` with a stored reason and the resume mode `follow_up`, and a silent Cline or a lost session also ends `stalled`. Tests: `tests/slice_rules.rs` (the pure rules), `tests/slice_loop.rs` (the state machine over fakes, with a clock).

## Work Guidance

- TDD: a failing test first; `tests/support/fakes.rs` is one in-memory world behind every port (its `fail`/`pass` queues inject faults per call,
  `race_status` makes the next status write lose a race, `stop_gone` makes the session already ended); `tests/support/asl.rs` walks the real
  `statemachines/direct.asl.json` (and, in `tests/reaper_machine.rs`, `statemachines/direct-run-ended.asl.json`) over fakes of its four Lambdas, parsing every payload into the real request types of `crates/delivery`.
- A change to an op that changes a payload or an event changes the machine walker's expectations in the same commit.
- `tests/support/fakes.rs` also holds `ScriptedUtilityClient`, which replays a queue of answers and refuses what Bedrock refuses (`ham_core::utility::bedrock_rejects_with`), and a model of the search item that `touch_run_index`, `put_run_name` and the tag writers write. The client keeps a second queue for the tag requests (told apart by their stop sequence `</tags>`) and yields at every call, so two ops of one test interleave. The tag writers of `Mem` run the very `UpdateSpec` the adapter sends: `dynamo::expr_rejects` first, then the spec's own condition and update expression are applied to the item (`SET a = :v`, `if_not_exists`, `+ :one`, `REMOVE`), so a wrong expression in `ham_core::runtag::dynamo` shows in the state a test reads. `Mem::enable_tagging` turns both purposes on and makes the start's search item; `seed_parent`, `seed_other_item`, `seed_tag_item`, `before_tag_write` (another writer acts between the branch's read and its write), `stall` and `fail` arrange the rest. `tests/support/asl.rs` sends a call with `InvocationType` Event to `Lambdas::event`, so an asynchronous call never moves the call indexes of the synchronous ones.

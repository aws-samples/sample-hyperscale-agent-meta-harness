# crates/control-api

## Purpose

The Lambda behind the public `/v1` API starts direct runs from one prompt. It lists and reads the caller's runs with their cost. It supports cursor reads of a run's event log. It lists the run's artifacts and provides presigned download URLs. It reads a run's events from the end with the user's answers, keeps the run index behind the run list's title, model and filters, and gives a download URL for the latest snapshot of a run. It reads a run's stored conversation page by page and searches the caller's chats. It changes the tags a person puts on their runs. It starts a blocked run again with the request it was started with. It supports cancel, the answer to a stuck run's question, the model list, the repository allowlist, and `whoami`.

## Ownership

`crates/AGENTS.md` owns this crate. It deploys as `hamh-<stage>-control-api` on arm64. Build it with `cargo lambda build --release --arm64`. Its environment includes `TABLE_NAME`, `BUCKET_NAME`, `RUN_STATE_MACHINE_ARN`, and `ACCOUNT_ID`. It also includes `DEPLOYMENT_PARAMETER_PREFIX` with `/hamh/<stage>`, and `OPERATOR_PRINCIPALS`.

## Local Contracts

- The caller is the API Gateway IAM identity (`requestContext.identity.userArn`); a request without
  one is 403. Every run route loads the Run item and treats another caller's run as absent (404).
- A request body is parsed in one place, `body::parse_body(what, body)`, by the five JSON-body routes (`StartDirectRunRequest`, `SendMessageRequest`, `RepoAdminRequest`,
  `InputAnswer`, `TagEditRequest`). A body that does not parse is a 400 `bad-request` whose message is `<Type>: <fixed phrase> (line <n>, column <n>)` and nothing else: no byte of serde's text and
  none of the body, because serde quotes the value or member name the caller sent (and a custom `Deserialize` quotes its own input). The phrase is one of eight (not valid JSON, ends early, number
  out of range, a required member is missing, a member this API does not know, a member twice, wrong type or a value not accepted, any other mismatch); an empty body is `<Type>: the body is empty`.
  The kind is chosen from `serde_json::Error::classify` and the first words of serde's text, which are read and dropped; a wording that changed falls back to "the body does not match the request format".
  Line and column are 1-based, the column counts bytes and sits just after the offending token. A new handler that reads a body calls `parse_body`: a test fails on any call of `from_str`, `from_slice` or `from_reader`
  outside `body.rs` whose arguments mention `body` (`req.body`, `r.body`, `request_body`; a turbofish; a call wrapped over lines; every `.rs` file under `src/`). It reads the name only: a body copied to a variable
  without `body` in its name is not found, and bytes that are not a request body (an S3 object) are bound to a name without `body` before they are parsed. The scan has its own tests, and a body of a mebibyte,
  of multi-byte characters or nested past the parser's depth gets the same short ASCII answer (`tests/bad_body.rs`). Do not log the parse error or the body. A client may match the fixed phrase "a member this API does not know" (a stage that predates a new request member says it); the old stages' own
  text, `unknown field` with the member name, is still what `ham` maps for `engineConfig` (`crates/ham/src/api.rs`). The refusal of a tag edit's run id (`WireError::BadRunId`) names the rule and
  not the id (`tags::wire_words`). Messages of the checks that run after the parse (`invalid-*`, `bad-input`, 422) are the checks' own words and are not part of this rule.
- Routes include `POST /v1/direct/runs` and `GET /v1/direct/models`. `GET /v1/runs` uses GSI1 and lists newest first. Its opaque `nextToken` is bound to the caller. A bad token returns 400. Routes also include `GET /v1/runs/{runId}` and `GET /v1/runs/{runId}/events?shard=&after=&tail=&before=`. The events route requires shard 0-31. `after` is a ULID. The route returns up to 500 events. `nextAfter` is the last `eventId` or the incoming cursor. `tail` and `before` read from the end (below). Routes also include `GET /v1/runs/{runId}/artifacts` and `POST /v1/runs/{runId}/artifacts/{artifactId}/download-url`. Other routes are `POST /v1/runs/{runId}/cancel`, `POST /v1/runs/{runId}/input`, the four message routes (`POST` and `GET /v1/runs/{runId}/messages`, `GET /v1/runs/{runId}/messages/{messageId}` and `POST /v1/runs/{runId}/messages/{messageId}/withdraw`), `GET /v1/models`, and `GET /v1/repos`. Routes also include `POST /v1/admin/repos` and `GET /v1/whoami`. Routes also include `GET /v1/runs/{runId}/transcript`, `GET /v1/runs/{runId}/head` and `GET /v1/search`, below. The chat-client routes are `POST /v1/runs/index` and `POST /v1/runs/{runId}/snapshot/download-url`. The tag route is `POST /v1/tags/edit` (below). Other methods on these paths return 405. Other paths return 404.

- Cancel keeps the work; see `controls.rs`. A live agent has an Agent item neither `stopped` nor `failed`. Without `?discard=true`, cancel queues one `Cancel` control per live agent. It changes nothing else when a live agent exists. agentd ends the prompt within 10 s. It then runs its end sequence. The run machine delivers what exists with label `Cline stopped: you stopped the run`. `?discard=true` clears the run; its value must be exactly `true`. A run with no live agent also clears. There is nothing to keep in that case. The Run item and root Goal move to `cleared` at their next versions. The harness event `goal.status {status, phase}` is written in the same transaction. This uses `Store::update_run` with conditions on `version`. A lost race returns 409 `conflict`. Then `controls::stop_run_work` queues the `Cancel` controls. It stops the `run` execution `<runId>` through `Execution::stop`. A missing execution counts as stopped. `complete` returns 409 `run-finished`. Canceling a cleared run again re-sends the stop. This lets a retry after a failure finish the job. A failure there returns 503 with "retry ham cancel".
- Answering a stuck run: `POST /v1/runs/{runId}/input` takes an `InputAnswer` (`requestId`, `action`, `text`, `model`; unknown members are a 400 `bad-request`, so a client cannot set `origin`; control-api writes `user`) and queues ONE `Instruct` control for the `direct` agent whose control id IS the request id (the nonce: one answer per question). Checks in the order of the response table: body (400 `bad-input` for a blank or over-long text, 8,000 characters and 32,000 bytes, or the wrong members for the action), catalog (`try_model` names a route, the model's own or an alternate one, of a row with a smoke record, else 422 `unknown-model`), owner (404), run not `complete` or `cleared` (409 `run-finished`), a live `direct` agent (409 `no-live-session`), the request id names a blocking `needs-input` event of the direct agent of this run (404 `no-such-request`: a run on an image that cannot raise the question never gets an `Instruct`), the window (410 `request-expired` after `expiresAt` plus 30 s), then the conditional put (202 `queued`). A control that already exists for the request decides before the clock: another answer is 409 `already-answered` naming the winner, the same answer is 200 `already-queued`, and the same answer agentd took 12 s or more ago with no `input-received`, `input-ignored` or `input-closed` after the request is re-armed (`Store::rearm_control` removes `deliveredAt`; 202 `re-queued`). Whether the action is among the question's `options` and the model among its `models` is agentd's to judge (`input-ignored bad-action` / `bad-model`). `Store` gains `get_event`, `get_control`, `rearm_control` and `latest_events` (defaults answer unavailable). `GET /v1/runs` rows of `active` non-probe runs carry `needsInput` (`requestId`, `reason`, `title`, `expiresAt`) from a tail read of 200 events of the direct agent's shard folded with `harness_protocol::direct_input::fold_input`; a failed read leaves the field off, logs the reason and never fails the list. No IAM change.

- Transcript: `GET /v1/runs/{runId}/transcript?after=&before=&limit=`.
  The owner check comes first (another caller's run, a missing run and a malformed id are all 404 before a parameter is read or an object touched). The chunks sit in a prefix
  the worker's engine can write, so nothing in one is trusted: the route lists `runs/<run>/agents/direct/turns/1/transcript/` with StartAfter (only a key of exactly twelve
  digits plus `.ndjson.gz` is a chunk; other keys are skipped and counted; at most 20,000 keys per request), reads at most `limit` chunks (default 32, 1 to 64) with
  `Blobs::get_object` bounded to 1 MiB (by length, while streaming, and by the listing's ETag with If-Match), decodes each whole with `decode_chunk`, and returns every record as
  engine origin with strings redacted again by `ham_core::redact::redact_tokens`. `after` is the opaque cursor of `cursor.rs` (chunk and record, bound to the run and the caller by
  a hash, at most 2 KiB; a listing that met its cap also carries the last key), `before` is `end` or a chunk number; both exclude each other. A page stops at 3 MB of records
  (inside a chunk if it must), at 10,000 records, at 256 gaps or at the 8 s budget, with `more: true` and a `next` cursor; a page that examined nothing yet always reads one
  chunk, so every request progresses; a record over 256 KiB becomes an omission record (`kind: omitted`). Gaps are `TranscriptGap {kind, code, fromSeq, toSeq}`: a missing chunk, an
  unreadable one (`bad-gzip`, `bad-json`, `bad-header`, `seq-mismatch`, `version`, `too-many-records`, `record-order`, `depth`, `too-large`), a writer that returned after another
  wrote (`interleaved`, kind conflict, nothing removed), a changed object, the listing cap, and a tail the worker declared (`lastTranscriptSeq`) that the prefix lacks. State: the
  Agent item's raw `features` (`transcript.v1`) and the Turn item's raw `transcript` summary (`Store::transcript_facts`) with the Run item's status decide `unsupported` (no
  bucket call), `empty`, `live`, `complete` (ended, a valid summary that declares nothing but exclusions) and `incomplete` (ended otherwise; a summary that is absent or invalid
  counts as none, with a synthesized `tail-unknown`); `purged` is reserved. Nothing from a chunk, no cursor and no query value reaches a log: chunk faults are logged by code and
  number. IAM: `s3:GetObject` on the transcript prefix and `s3:ListBucket` under an `s3:prefix` inside it. `Blobs::list_objects` and `get_object` and `Store::transcript_facts`
  default to unavailable. Tests: `tests/transcript_route.rs` (31, over `tests/support/mod.rs`: an in-memory bucket that refuses what S3 and the role policy refuse), `tests/cursor.rs`,
  `tests/transcript_aws.rs` (recorded exchanges); the chunk files are the hex texts in `crates/ham-core/tests/fixtures/transcript/` (`ham_core::gzip::unhex` turns one into the chunk object).
- Search: `GET /v1/search?q=&since=&limit=&after=`. One Query sequence on the caller's own partition
  `OWNER#<sha256 of the caller's ARN>` (`Store::search_items`, newest first, eventually consistent, no filter, no scan, no bucket call): every word of `q` (up to 8 words of 200
  characters) must occur in a run's body, prompt, repository or model; one hit per run with a one-line snippet (redacted again) and, for a chat match, the chunk and record where
  the piece starts and an `open` cursor to pass as `after` to the transcript route. At most `limit` runs (default and maximum 200) newer than `since` (a date or UTC time; default
  the first run) are examined, 20 Queries at most, and a 10 s deadline returns `partial: true`; `more: true` and `next` (pass as `after`) say older runs remain. `partialCoverage` counts
  examined runs whose chat is only partly indexed. `q` is never logged. Each page reads the caller's run index items and then their chat items (`CHAT#`, written by run-session, `index.rs`: the body) with a Query per about 30 bodies (at most 12), because the run list reads the index items whole and a body in each would make a page read up to 3.2 MB; a run with no chat item is searched on its index fields (`DynamoStore::search_items` joins them). Tests: `tests/search_route.rs` (19, with a counting store that mimics DynamoDB's 1 MB pages: 1,000 runs cost at most 8 reads of the store and 200 items) and `tests/transcript_aws.rs` (the adapter's recorded exchanges: a read is one Query for the run index page and one per page of bodies).
- Tag edit: The route is `POST /v1/tags/edit`. It changes two lists on the caller's run search item. `runTagsUser` holds tags added. `runTagsOff` holds tags removed. The edit writes only `runTagsUser`, `runTagsOff`, `runTagsRev`, `runId` and `createdAt`. It never writes `runTags`, the automatic list. It never writes any other attribute. Any other verb on the path returns 405. `/v1/tags` returns 404. The caller is the IAM identity, as for every route. Without that identity, the route returns 403. Unknown body members are ignored. The owner is never read from the body. `ham_core::runtag::wire::TagEditRequest` is the request type. `TagEditResponse` is the answer type. The answer has one result per edit, in request order. Each result has status `ok`, `unchanged`, `invalid`, `not-found` or `conflict`. Each result includes the effective tags after the edit. An `invalid` result also includes the rule text. A body outside `TagEditRequest` returns 400 before any read. This includes a body missing `edits`, the edit list. Breaking a wire limit also returns 400 before any read. The request allows at most 40 edits. Each edit allows at most 12 tags across `add` and `remove`. A run id must have 1 to 64 plain characters. A run cannot appear twice in one request. A request with no edit returns 200 with no result. Edits run eight at a time, using `EDIT_GROUP` and `join_bounded`. First, the run must exist and belong to the caller (`owned`). A foreign run returns `not-found`. A missing run returns `not-found`. An id that is not a ULID returns `not-found`. These cases all return the same body. Nothing more is read or written in these cases. This holds even when the tags are invalid. Every read and write uses partition `OWNER#<sha256 of the caller>`. The sort key is `SRCH#<the run's createdAt>#<runId>`. This is the key the start writes. `Store::get_run_tag_state`, the tag state read, makes one consistent `GetItem`. It projects seven attributes: `runId`, `createdAt`, `repository`, `runTags`, `runTagsUser`, `runTagsOff` and `runTagsRev`. A missing item means an empty state. The derived project's repository comes from the item's own `repository`. Otherwise, it uses the run's target text through `RunIndexItem::tag_repository`. `ham_core::runtag::edit::apply_edit`, the list planner, plans the lists. A tag that breaks a rule makes the edit `invalid`. A list past its cap also makes the edit `invalid`. A plan matching stored state returns `unchanged`. This is a replay. Neither `invalid` nor `unchanged` writes anything. Otherwise, `Store::put_run_tags`, the tag writer, sends an `UpdateItem`. It uses `ham_core::runtag::dynamo::edit_update`, the edit update spec, as given. The write is conditional on `runTagsRev`. It creates the item when the start's write has not landed. That new item includes `runId` and `createdAt`. The start or backfill completes the item later. That completion touches no tag attribute. A failed condition produces `StoreError::Conflict`, a failed write condition. The route reads again once after that failure. It plans again from the new state. - Retry: `POST /v1/runs/{runId}/retry` starts a run that ended `blocked` again with the request it was started with. A blocked run delivered nothing, so `continueFrom` has no head to start from (409 `no-delivered-head`), and the run rows hold no prompt, rules or switches; the one full copy is the stored `runs/<id>/input/request.json`. Order of the checks, all before any claim, blob or run: `Idempotency-Key` (400 `idempotency-key-required`, 400 `bad-request`), the owner (another caller's run, a missing run and a malformed id are 404 alike, and nothing is read from S3 before this is known), the status (only `blocked`: `active` is 409 `run-active`, every other status 409 `run-not-blocked`), the read of the stored request with `Blobs::read_prefix` (at most 8 MiB; an absent object, one over the cap, text that is not JSON and an unknown member are 422 `stored-request-unreadable`, whose words name the run and none of the content; a read that fails, a missing S3 grant included, is 503 and claims nothing, so the same key works once it is back), then `direct::prepare`, the checks of a fresh start: the model list (422 `unknown-model`), the rules, the limits, and for a request that was itself a follow-up its base run and head (409 `no-delivered-head`, `head-mismatch`). `direct::start_prepared` then claims the key, stores the canonical form of the stored request (the same bytes for a request this service stored) as the new run's request, writes the Run item with `continue_from` = the blocked run, the root goal and `run.created`, starts the execution and writes the search item; the reply is the 201 `StartRunResponse` of a fresh start. The link is the Run item's alone: the stored request keeps its own `continueFrom` (with its head) when the blocked run was a follow-up and has none otherwise, so agentd and run-session start the new run exactly as they started the blocked one. `run-session`'s tag step reads the item's link, so the retry inherits the tags the person put on the blocked run. The client chooses the key (`ham` sends `retry-<blocked run id>`): a repeat returns the run the first retry started, so the terminal app starts one retry per blocked run (if it blocks too, the new run is retried); the service holds each key to one run and does not limit the keys a caller may use. A repeat is checked like a fresh start before the claim is read, so a repeat after the stage dropped the model answers the refusal, not the first run. The claim compares `sha256("retry\0" + blocked run id + "\0" + request bytes)`, so one key never returns the retry of another run and a key of a fresh start (the hash of the request alone) is never a retry. No `harness-protocol` member and no agentd change: the worker image key does not move. The role gets `s3:GetObject` on exactly `runs/*/input/request.json` (statement `ReadRunRequests`, `infra/lib/stacks/control.ts`, pinned by `infra/test/control.test.ts`); a stage whose Lambda is newer than its IAM answers 503 for the retry and nothing else changes.

  The `message-ledger` crate supplies message state rules. This module handles HTTP. The `Store` trait gains `message_admit`, `message_get`, `message_list`, `message_withdraw` and `message_close`.   `SendMessageRequest` is the body. An unknown member returns 400 `bad-request`. Clients cannot set the state or the principal. The client mints a ULID message id. That id is the idempotency key. Body checks come first. A bad id returns 400 `bad-input`. Blank or over-long text returns 400 `bad-input`. The text limit is 262,144 bytes and there is none in characters. The owner and run check comes next and returns 404.

The text answers that question through `POST .../input`. A failed question read is logged. The message then goes on.
  The ledger check comes last. A new message returns 202 `accepted`, with the message `pending`. 202 means durably accepted. It does not mean Cline has read the message.
  Ledger refusals keep their status and code. 409 codes are `run-sealed`, `too-many-pending`, `run-limit`, `not-held`, `epoch-changed`, `confirm-mismatch`, `already-dispatching`, and `not-withdrawable`. `too-many-pending` limits outstanding messages to 3. `run-limit` limits totals to 100 messages or 4 MiB; `tests/messages.rs` sends the 101st message and the message past 4 MiB through the route and expects 409 `run-limit`. 429 `rate-limited` allows 10 a minute for the run.   Withdrawing a pending or held message returns 200 `withdrawn`. Repeating the withdrawal returns 200 again. A message claimed by agentd returns 409 `already-dispatching`.
  `MessagesPage` is the list response. It contains messages in the order admitted. It includes the current session `epoch` and `epochNo`. It also includes `admission` and `watermark`. A run without any messages returns an empty open page.
  `controls::cancel` closes messages first. It then queues the Cancel control. This order applies with or without `?discard=true`.

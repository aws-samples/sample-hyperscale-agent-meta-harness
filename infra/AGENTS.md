# infra

## Purpose

The CDK v2 TypeScript app (L1 constructs) that deploys stage `direct` of the harness: nine stacks `hamh-direct-<name>` into the `accounts.json` entry `HAMH_AWS_PROFILE` selects: unset, the one `active` entry; a `history` or `test` entry only by its profile name. The committed
`accounts.json` holds one neutral `active` entry; `setup.sh` writes the file of a person's own account. The tests that need every role build a file with a history, an active and a test entry from `test/accounts-three.ts`
(the same file as `scripts/tests/fixtures/accounts-three.json`; `test/accounts-three.test.ts` compares them).

## Ownership

Owned by the root contract. Stack contents follow (network and credentials) (stack table) (CodeCommit
delivery) and (the run machine and `run-session`). `statemachines/` holds the two machine definitions the orchestration stack reads;
`scripts/deploy.sh` and `scripts/teardown.sh` run the app.

## Local Contracts

- The run-session role reads the version agentd recorded for its three end-of-run objects, so `orchestration-direct.ts` grants `s3:GetObjectVersion` on `turns/*/bundle`, `turns/*/summary.json` and `turns/*/test-report.json` of the direct agent
  (`PinnedAgentOutputs`), and `delivery.ts` grants it to the bundle validator on the direct agent's `turns/*/bundle` (`ReadPinnedBundleVersions`). No version of any other key is read and no version is deleted.

- `setup-runner.yaml` and `setup-runner-policy.json` are not part of the CDK app. The template is plain CloudFormation that `setup.sh` deploys with the AWS CLI as the stack `hamh-setup-runner`: a versioned, encrypted bucket `hamh-setup-<account>-<Region>` for the source archive, the generated account file, the results and the client files, the CodeBuild project `hamh-setup-runner` (Linux x86_64, privileged because `scripts/node.sh` needs the Docker daemon) that runs `scripts/setup/runner-build.sh`, its log group, and the runner role with its permissions boundary. Outputs: `SetupBucket`, `BuildProject`, `LogGroup`, `RunnerRoleArn`. The policy file holds the runner role's statements, its boundary and the table of every AWS CLI call the runner's scripts make; `scripts/tests/test_setup_runner_template.py` and `test_setup_runner_policy.py` hold the template, the file and the scripts together. The CDK bootstrap roles the runner assumes (the CloudFormation execution role is `AdministratorAccess` unless the account's bootstrap says otherwise) are not bounded by the template, and the permissions boundary caps only the calls the runner role makes itself; the header says so. Three parameters have no default and `setup.sh` passes them at every install: `InstallerPrincipal` and `InstallerPrincipalWithPath` (the identity that runs `setup.sh`, as the two `aws:PrincipalArn` patterns it matches: exact for a user, the root user and a federated user, the role with and without a path for a role session) and `AuthorityExpires` (a UTC time, 12 hours ahead by default, `HAMH_SETUP_AUTHORITY_HOURS` 5 to 72). The bucket policy denies `s3:PutObject`, `s3:DeleteObject` and `s3:DeleteObjectVersion` to every principal except the runner role and those two patterns, so the archive the runner executes and the result `setup.sh` installs from are written by those two alone; the two statements of the runner role that assume a role (`AssumeCdkBootstrapRoles`, `AssumeGomodFiller`) hold only before `AuthorityExpires`, so a runner that is left behind cannot act as an administrator for longer than that. Whoever may call `codebuild:StartBuild` on the project can run commands as the runner role (IAM cannot restrict a buildspec override), so until that time that permission is administrator access; the header says that too. Tags: `project=hyperscale-agent-meta-harness` only. The bucket is emptied by `scripts/setup/empty-bucket.sh` before the stack is deleted. `setup.sh` also makes the CDK bootstrap stack `CDKToolkit` when the account has none, from a template that the runner's first build prints with the pinned CDK CLI (no template is committed; the pin is `engine/policy/cdk-bootstrap-template.pin`; the role may write `bootstrap/*` of the bucket for it), and a template it deploys must stay under 51,200 bytes (`aws cloudformation deploy` uploads no larger one without a staging bucket). The role holds no delete, stop or IAM permission and the runner script has no teardown action: `setup.sh --teardown` runs on the caller's machine with the caller's own credentials, deletes this stack and its bucket before it deletes the stage, and opens no authority window.
- Node runs only through `scripts/node.sh`; never `npm`/`npx` on a host. Exact version pins in `package.json`;
  `pnpm-lock.yaml` committed; `pnpm-workspace.yaml` keeps dependency build scripts off (`allowBuilds`).
- `lib/config.ts` reads the repository's `accounts.json` once at load: `selectTarget(doc, env)` applies `scripts/lib/aws_target.py`'s rules
  (selector `HAMH_AWS_PROFILE`, or the word an accounts file generated before the rename carries: both words are read and the file is never rewritten; unset or empty the one `active` entry, `AWS_PROFILE` never selects, an unknown profile or a malformed file
  throws; each entry names `azs.direct` and `azIds.direct` (the AZ names of the Region paired one to one with the AgentCore VPC AZ IDs, such as us-east-1b = use1-az1 in an account where that holds); `role` is active, history or test and only `active` is the default) and gives
  `TARGET`, `ACCOUNT`, `REGION` and `PROFILE`. The only stage is `direct` (`Stage`); `stageConfig("live")` and `("drill")` throw
  `unknown stage ... expected direct`, and `cdk.json` defaults the context `stage` to `direct`. The stage: prefix `hamh-direct`, VPC
  10.50.0.0/16, one AZ, log retention 30 days, a worker lifetime of 28,800 s with 1,800 s idle, `engineRouting` `run` and `routeLadder` `off`.
- The operator identity: an `accounts.json` entry may carry `operator`, an object `{"kind": "role" or "user", "name": "<IAM name>"}`
  (a role by its name as it appears in the assumed-role ARN of the caller, an IAM Identity Center role `AWSReservedSSO_<permission set>_<hash>` included; a user by its user name; 1 to 64 letters, digits or `+ =. @ _ -`; no
  path, no wildcard, no comma; no other key). `selectTarget` parses it (`parseOperator`, the same words and refusals as `scripts/lib/aws_target.py`) and gives `Target.operator` and `OPERATOR`. An entry without it keeps the IAM role
  `Admin` and every template is what it was, byte for byte. With it the stage trusts exactly that identity wherever `Admin` was written: `OPERATOR_PRINCIPALS` of control-api (`callerArnPatterns`: the sessions of the role, or the
  user with and without a path; comma separated), the minters of the `harness-worker-session` role, the E2E second principal and the Go module store's filler role (`deployingTrust` in `lib/stacks/security.ts`: the account root narrowed
  by `aws:PrincipalArn` to `principalArnPatterns`, the role or user without and with any path, because IAM rejects a role principal that does not exist and a session ARN carries no path) and the store's delete exception
  (`deployingPrincipalArns`). The setup runner's role `hamh-setup-runner-role` (`SETUP_RUNNER_ROLE`, the name `setup-runner.yaml` creates) is added to the filler trust and the delete exception only, because the runner fills and empties the
  store with its own role; no other statement names it. The identity needs `sts:AssumeRole` in its own policy (an administrator has it).
- The repository-name rule (`lib/repo-names.ts`, `test/repo-names.test.ts`, the shared table `test/fixtures/repo-names.json`): The rule is nonempty `HAMH_REPO_NAMES` (comma-separated, spaces dropped), else the entry's `repoNames`, else `["hamh-e2e-*"]`. It is a list of 1 to 10 entries; an entry is a repository name (1 to 100 letters, digits, `.`, `_` or `-`), such a prefix of up to 99 characters followed by `*`, or `*`; no entry twice. `REPO_NAMES` in `lib/config.ts` is read once when the app loads. The control-api function (`OPERATOR_PRINCIPALS` beside it) and the delivery functions get it as `HAMH_REPO_NAMES`, and the control stack prints it as the output `RepoNames`, which `setup.sh` reads so that an update keeps the rule. The Rust reader `crates/harness-protocol/src/accounts.rs` ignores the field, so the worker image key does not move. `scripts/lib/aws_target.py` applies the same rules (`repo_names_of`, `repo_name_allowed`) and `crates/control-api/src/repo_names.rs` and `crates/delivery/src/repo_names.rs` hold the Rust copies of the matcher.

  and the `packages` aggregate; the Go module store), `control` (the private `/internal` API behind `worker-api` and the public `/v1` API behind
  `control-api`; and the research route, below), `runtimes` (the worker ECR repository, the image-build CodeBuild project, and with an image the runtime, the requireMMDSV2 custom
  resource, the `live` endpoint and the runtime ARN parameter; the runtime resources carry no `description`, because AgentCore makes a runtime version for every change of a runtime's

  (phase 1); with digest-pinned images (`<repo>@sha256:<64 hex>`, else the app throws) the runtime, its custom resource and endpoint, and the delivery
  functions deploy (phase 2). `lib/entry.ts` reads the settings of one deploy, and every variable the app reads (these twelve, the account selector, the accounts file, the owner, the repository-name rule and the AgentCore storage accounts) goes through `lib/env.ts`: `HAMH_LAMBDA_DIR` (required; it must hold
  `worker-api`, `control-api`, `run-session`, `research-api` and `research-job` bootstraps, else the entry throws; there is no silent fallback to the fixture),
  `HAMH_RESEARCH_PROVIDER`,
  `HAMH_TAVILY_ALARMS` (`on` or `off` in any letter case with ASCII whitespace ignored; unset or empty means `on`), `HAMH_TAVILY_KEY_MAX_AGE_DAYS` (a whole number of days from 1 to 365, digits only; unset or empty means 30) and `HAMH_RESEARCH_ALARM_TOPIC_ARN` (optional; an SNS topic ARN of any Region, partition or kind, a FIFO topic included; the error names the variable and never repeats the value) are the three settings of the Tavily key alarms; `resolveResearchAlarms` in `lib/config.ts` resolves them and `buildApp` resolves them again,
  `HAMH_UTILITY_MODEL` (an id or alias of a row of `crates/ham-core/assets/utility-models.json`, or `off`; unset or empty keeps the catalog default; any other word throws and names the setting),
  `HAMH_UTILITY_PURPOSES` (a comma list of `run-name` and `run-tags`; unset or empty means every purpose the model's row has a smoke record for; any other word throws and names the setting),
  `HAMH_TOOLS_MODE` (`off` or `on` in any letter case with surrounding ASCII whitespace ignored; unset or empty keeps `off`; any other word throws and names the setting),

The control-api and delivery functions accept the repositories the rule covers, and IAM lets them reach the same ones: each entry of the rule is a resource pattern of its own (an exact name stays exact, `prefix*` stays a prefix, `*` covers the account and Region). The list is the `Resource` of the `ReadE2eRepositories`, `PushHarnessBranches` and `PullRequests` statements of repo-gateway, of the `ReadE2eRepositories` and `ApproveAndComment` statements of the PR check build role and, as an event pattern, of the EventBridge rule that starts the check (a prefix entry and `*` are `prefix` filters, an exact name is the whole ARN; the rule's description does not list the entries). The statements that create a repository, a branch or a default branch and the allowlist writes name only the `hamh-e2e-new-` and `hamh-e2e-ntier-` prefixes. A rule of eight entries of 100 characters keeps both inline policies under the IAM size limit and the event pattern under its limit (`test/delivery-repo-names.test.ts`).

- The control-api role has the statement `InstancesRuntimeArnParameter`: `ssm:GetParameter` on `/hamh/<stage>/worker-python-instances-runtime-arn` only. A start-run request that names `--compute instances` makes control-api ask whether the stage has an Instances worker runtime by reading that parameter (`DEPLOYMENT_PARAMETER_PREFIX`, `crates/control-api/src/aws.rs` `instances_available`), and an absent parameter is a 422 the user can act on. The grant does not depend on `HAMH_COMPUTE_INSTANCES` (the control template is the same for off and on): a role without it would answer AccessDenied on a stage that merely leaves Instances off. `test/control.test.ts` pins the statement.
- The control-api role has the statement `DeployLockParameter`: `ssm:GetParameter` on `/hamh/<stage>/deploy-lock` only. A stage that is being updated starts no new runs: control-api reads the stage's deploy lock right before it creates a run (`crates/control-api/src/admission.rs`) and answers 409 `stage-updating` while a deploy holds it. The role can neither write nor delete the parameter, and no SSM statement of the role names a wildcard. A role without the grant (a function that is newer than its role) answers AccessDenied, and control-api then lets the run start. `test/control.test.ts` pins the statement and the three SSM statement ids of the role.
